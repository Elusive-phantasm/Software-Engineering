# 架构分工与接口所有权表

> 适用：拾光二手（campus-trade），4 人组 + 组长。
> 依据：《软件架构设计说明书》§3～§7、《接口与关键设计说明书》模板 D、《架构设计后确认与分阶段实现操作指引》§四/§六。
> **原则**：分工分的是**架构视图**（设计阶段）与**接口所有权**（实现阶段），不是"谁写哪个文件"。
> 状态：AI 起草，待组长确认后生效；成员与接口的对应关系可按实际能力调整，但**每条接口必须恰好一个 owner**。

你们在《需求规格说明书 V2.1》里已经这样分过：

| 成员 | SRS 原分工 | 天然对应的架构视图 |
|---|---|---|
| 赵俊豪 | 功能需求（用例建模）§3 | **接口设计**：用例 → 接口契约、时序图 |
| 吕锦浩 | 业务规则与状态建模 §4、§7 | **构件级设计**：状态机、判定算法、规则落地 |
| 马歆远 | 数据、权限与质量 §5、§6、§8 | **数据设计**：表/约束/事务 + 权限边界 |
| 过振宇 | 原型与场景走查 §7.5、附录 A | **前端架构**：页面/路由/状态/UI 契约 + 走查证据 |

**继续用这套分工做架构，好处是**：每个人写的架构章节，正好是他在 SRS 里那章的"设计展开"，不用重新学上下文，答辩时也能说"需求我写的、设计也是我落的"。

## 二、设计阶段：架构文档的章节分工

产出物是《软件架构设计说明书》。**每人 1～2 章 + 2 条 ADR**，写不完的部分标"待细化"，不要留空。

| 成员 | 负责章节 | 具体交付 | 交付标准 |
|---|---|---|---|
| **林初仁（组长）** | §0 定位、§1 目标与约束、§3 体系结构、§10 冻结状态、§11 ADR 汇总、§13 限制 | C4 三张图、包依赖矩阵、ADR 清单 | 任何人看完能说出"分几层、依赖往哪走" |
| **赵俊豪** | §6 接口设计（6.1 契约总则、6.2 模板 D 示例） | 契约总则、**3 个代表性接口的模板 D**（发布/下单/举报）、2 张时序图 | 前端能照契约直接写调用，不用问字段 |
| **吕锦浩** | §7 构件级设计（7.2 状态机、7.3 算法、7.4 SOLID、7.5 模式） | 商品四态 + 认证四态状态机、幂等键设计、SOLID 逐条、模式取舍 | 每条规则能指到 SRS 编号与代码方法 |
| **马歆远** | §5 数据设计、§8 横切（权限/隐私部分）、§9 质量属性 | 17 表不变量表、事务边界表、权限矩阵落地、质量属性验证映射 | 每个不变量都有 DDL 或服务层兜底 |
| **过振宇** | §3.2 前端架构、§6.1 前端契约遵守、§12 演化（UI 部分） | 前端目录职责表、页面↔接口对照、走查证据清单 | 每个页面能指出调了哪些接口 |

**组长额外负责**：ADR 汇总与裁决、跨章节口径统一（同一件事不许两种说法）、最终签字。

**时间建议（3 + 1 天）**

| 天 | 动作 |
|---|---|
| D1 | 组长出 §3 骨架与目录，全员对齐术语；各自认领章节 |
| D2 | 各自写章节 + 2 条 ADR 草案（草稿直接进仓库，不进聊天） |
| D3 | 交叉评审（按 §五矩阵），组长合并冲突口径 |
| D4 | 冻结：签字、登记《基线索引》、冻结 S1 接口 |

| **M5 治理后台** | `AdminController`（举报处置/评价删除部分） | 3 | **吕锦浩** | UC-13 |

> 接口总数：**75**（统计口径：controller 注解静态扫描 + `POST /api/verifications` 无子路径那一条）。

### 3.2 「接口所有权」含 5 件事（缺一件就会扯皮）

| 要素 | 说明 | 举例（`POST /api/orders`） |
|---|---|---|
| ① 契约 | 入参/出参/错误码/状态变化 | 失败返回 3001「该商品已售出」，不产生订单 |
| ② 实现 | 代码谁写 | `OrderService#create` |
| ③ 测试 | 谁证明它对 | `tools/smoke.mjs` 下单与重复提交用例 |
| ④ 文档 | 改契约谁同步 | `接口与关键设计说明书` + Swagger |
| ⑤ 变更审批 | 别人想改找谁 | 找吕锦浩；跨模块再找组长 |

**调用方只有使用权，没有修改权。** 前端要加字段 → 向 owner 提，不能自己改后端契约。

### 3.3 公共件（禁止私自修改，改必须先评审）

| 公共件 | 作用 | Owner | 谁能改 |
|---|---|---|---|
| `PermissionService` | 鉴权唯一入口 | 林初仁 | 组长 + 1 名交叉审查 |
| `Views`（出参白名单） | 隐私唯一出口 | 林初仁 | 同上 |
| `ErrorCode` / `GlobalExceptionHandler` | 错误语义 | 林初仁 | 同上 |
| `schema.sql`（表与约束） | 数据不变量 | **马歆远** | 数据 owner + 组长 |
| `TimeProvider` | 唯一时间源 | 吕锦浩 | 规则 owner + 组长 |
| `NotificationService` | 通知扇入 11 | 过振宇 | 沟通 owner + 组长 |
| `CreditService` | 扣分幂等，扇入 7 | 吕锦浩 | 规则 owner + 组长 |
| `AppProperties` / `application.yml` | 业务参数 | 林初仁 | 组长 |

> 为什么这些必须唯一 owner：它们被 7～11 个服务依赖，改一处影响所有人。**谁都能改 = 谁都不负责。**

## 四、每个人到底要交什么（一页看清)

| 成员 | 设计阶段交 | 实现阶段交 | 不能碰 |
|---|---|---|---|
| **赵俊豪** | §6 接口设计 + 3 份模板 D + 2 张时序图 | M1 的 15 个接口：契约/实现/测试/文档 | 订单与信用的接口、`CreditService` |

| **马歆远** | §5 数据设计、§8 权限与隐私、§9 质量属性 | M2 共 16 个接口 + **`schema.sql` 唯一 owner** | 业务状态流转的判定规则 |

**交接物格式**：每个接口一份模板 D（字段见《接口与关键设计说明书》），写完即冻结；冻结后改契约必须"提 Q → 组长批 → 通知调用方 → 回归测试"。

| 产出物 | 作者 | 审查人 |
|---|---|---|
| §3 体系结构 / ADR 汇总 | 林初仁 | 马歆远 |

| §6 接口契约（M1） | 赵俊豪 | 过振宇 |

| §3.2 前端架构 / M4 接口 | 过振宇 | 林初仁 |

**审查只看四件事**：契约与 SRS 是否一致、权限与隐私是否有漏洞、事务边界是否正确、测试是否覆盖失败路径。**不要审代码风格。**

## 八、一句话总结

**设计阶段按"架构视图"分**（每人一章，正好是他 SRS 里写的那章的设计展开）；
**实现阶段按"接口所有权"分**（每个接口恰好一个负责人，含契约/实现/测试/文档/审批五件事）；
**公共件全部收归唯一 owner**，因为改一处影响 7～11 个服务。
