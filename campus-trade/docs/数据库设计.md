## 二、三个关键设计

### 1. 用「生成列 + 唯一索引」模拟部分唯一索引

MySQL 不支持 `WHERE` 条件的唯一索引，而需求要求：

- 同一商品**同时最多一条「有效」成交记录**（BR-06）
- 同一学生**同时最多一条「待审核」核验申请**（UC-02 辅事件流 E）

做法：

```sql
-- orders：只有「有效」的订单才参与唯一约束
valid_product_id BIGINT GENERATED ALWAYS AS
  (CASE WHEN status = '有效' THEN product_id ELSE NULL END) STORED,
UNIQUE KEY uk_order_one_valid (valid_product_id)
```

MySQL 的唯一索引允许多个 NULL，因此已撤销的历史订单不会互相冲突，
而两笔「有效」订单会直接撞唯一键 —— 并发抢购在数据库层就被挡住。

### 2. 状态一致性写进 CHECK 约束

| 约束 | 含义 |
|---|---|
| `ck_product_reason` | 已下架 ⇔ 必须有下架原因（§6.4.1） |
| `ck_product_reason_value` | 下架原因只能取五种，且与状态机一一对应 |
| `ck_order_cancel` | 有效时撤销字段全空；已撤销时前三者非空、判定与判定时间配套 |
| `ck_report_type_match` | 「收款不履约」不能举报商品；四类商品违规不能举报学生 |
| `ck_report_handle` | 待处理时处理人/结果/时间全空；已处理时三者必填 |
| `ck_credit_sign` | 评价加分必须为正，其余事件必须为负 |

这样即使服务层写漏，数据库也会拒绝半成品数据。

### 3. 金额与时间

- 金额一律存「分」（`price_cents`、`amount_cents`），避免浮点误差导致「成交金额 ≠ 标价」（BR-05）。
- 时间用 `DATETIME`，业务判定统一走 `TimeProvider.now()`（可整体偏移，用于演示 7 天 / 24 小时规则）。
- **会话有效期使用真实时钟**，不随演示时间偏移（否则时间旅行会把所有人踢下线）。

## 三、索引

| 索引 | 用途 |
|---|---|
| `ix_product_status (status, published_at)` | 首页只查在售并按时间排序 |

| `ix_order_buyer` / `ix_order_seller` | 我的订单 |
| `ix_msg_conv (product_id, created_at)` | 会话消息按时间排序 |

| `ix_notify_recipient` | 通知列表与红点 |
| `ix_audit_action` / `ix_audit_actor` | 审计检索 |
