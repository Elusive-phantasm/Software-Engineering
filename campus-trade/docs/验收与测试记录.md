## 二、NFR-01 商品列表性能（50 并发，15 秒）

| 指标 | 数值 |
|---|---|
| 总请求 | 11,124 |
| 吞吐 | 741.6 req/s |
| p50 / p95 / p99 | 106 / 223 / 249 ms |
| 最大 | **385 ms**（目标 ≤ 2000 ms） |
| 失败 | 96（0.86%，连接层重置，见「已知限制」） |

结论：**样本内全部满足 ≤2s**，最大值为目标的 1/5。正式验收仍需按 SRS §8.2 的 500 次有效样本口径复测。

## 三、NFR-02 下单成交时延（小样本 10 笔）

| 指标 | 数值 |
|---|---|
| 有效样本 | 10 笔（全部成功生成订单并转「已售出」） |
| min / p50 / max | 18 / 22 / **37 ms**（目标 ≤ 3000 ms） |

结论：单事务 3 次写（条件更新商品 + 插入订单 + 通知）在本机约 20ms。样本量小，**不作为正式验收结论**。

## 五、已知限制

1. **连接层失败 0.86%**：50 并发压测中出现 96 次连接重置。应用层无异常日志，判断为 Hikari 连接池（20）
   与压测客户端 50 连接之间的排队/超时。正式压测时应先调大 `spring.datasource.hikari.maximum-pool-size` 再复测。
2. **无单元测试**：当前为「接口级冒烟 + 浏览器冒烟」，未覆盖 service 层分支的细粒度单测；
   如需提升，可用 JUnit 5 + Mockito 对 `OrderService`、`CreditService` 补单测。
3. **浏览器冒烟覆盖 20 个检查点**，不等于全量 UI 回归；上传图片、富交互弹窗等仍建议人工点一遍。
4. **时间偏移对会话无影响**：会话 TTL 使用真实时钟，`+7 天` 演示不会把用户踢下线。

## 六、复现步骤

```bash
# 1. 启动 MySQL（独立实例 3307，见 README）
# 2. 启动后端
cd backend && mvn spring-boot:run

# 3. 后端冒烟
node tools/smoke.mjs

# 4. 启动前端
cd frontend && npm run dev

# 5. 浏览器冒烟（使用系统 Edge）
node tools/e2e.mjs

# 6. 性能抽样（可选）
node tools/bench.mjs
```
