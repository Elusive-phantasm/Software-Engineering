\section{这段代码如何执行？}
\textbf{输入：}学生 ID (studentId)、分值变动 (delta)、事件类型、原因，外加可选的幂等键 (sourceKey) 和订单号 (CreditService.java:41-42)；

\textbf{核心判断逻辑：}先用 sourceKey 查重，查到就直接返回 duplicated=true (43-49行)；找不到对应学生就结束 (51-53行)；把变动后的分数限制在 0~150 的边界内 (55-57行)；最后判断实际变动值 applied != 0 才去执行写库和发通知 (59-79行)；

\textbf{调用顺序：}幂等查重 $\rightarrow$ 查询学生记录 $\rightarrow$ 计算边界截断后的新分数 $\rightarrow$ updateById 更新学生分数 $\rightarrow$ 插入信用流水并发送站内通知 (43-77行)；

\textbf{会修改的数据：}学生表的当前信用分和更新时间、信用流水表新增一条记录、站内通知表新增一条消息 (60-76行)，另外整个 apply() 方法加了 @Transactional 事务控制 (40行)。

\section{我选择检查的质量要求是什么？}
{\bfseries 依据编号和规则：}主依据 BR-14（SRS.md:634）：每次变动必须生成一条信用记录；辅助依据 BR-13（SRS.md:633）：信用分范围在 0$\sim$150 之间，超出范围按边界截断，并把截断后的值写入记录。

{\bfseries 对应代码位置：}CreditService.java:40-79；SchedulerService.java:179-205、209-242；schema.sql:222-232。

\section{我的判断是什么？}
\textcolor{red}{\bfseries 已发现问题}

理由：

{\bfseries 在}\uline{多个请求并发修改同一名学生信用分的}{\bfseries 条件下，代码会}\uline{先读取旧分数并在内存中计算后直接执行整行 updateById（CreditService.java:55-62），既未带旧分数做条件限制也无乐观锁版本号（与类注释 18-19 行声称的“条件更新”不符），}{，\bfseries 因此}\uline{后提交的更新会覆盖先提交的结果，导致并发加扣分丢失。}

{\bfseries 在}\uline{携带相同 sourceKey 的请求并发进入的}{\bfseries 条件下，代码会}\uline{因 44-49 行的“先查后写”无法拦截并发请求，直接触发数据库 source\_key 唯一索引报错（schema.sql:232），且 apply() 未捕获唯一约束异常将其转为 duplicated=true}{，\bfseries 因此}\uline{异常会直接向上抛出导致调用方请求失败。}

{\bfseries 在}\uline{学生当前分数已达 150 分上限继续加分、或已降至 0 分下限继续扣分的}{\bfseries 条件下，代码会}\uline{因边界截断算出 applied == 0（CreditService.java:55-57）并直接跳过 59-79 行的写流水分支}{，\bfseries 因此}\uline{边界触发时不会生成信用记录，与 BR-14“每次变动必须生成一条信用记录”及 BR-13 的截断记录要求存在冲突。}

{\bfseries 缺少的信息或需要继续查看的代码：}需要查看 NotificationService.notifyStudent() 的具体实现（是为了确认其异常处理与事务传播级别），还需要查看举报处置等其他调用 CreditService.apply() 的上层业务代码，确认调用方是否自行捕获并处理了唯一键冲突异常；同时还缺少本地测试库的事务隔离级别配置及实际并发运行日志。

\section{如何验证:}
{\bfseries 前置条件：}基于代码基线 90a4327 搭建隔离的本地测试数据库并创建测试学生账号，记录初始信用分、流水记录条数及站内通知数量，准备两个独立的数据库连接用于模拟并发请求；

{\bfseries 输入或操作：}

A. 把初始分设成 100 分，用线程屏障同时发 2 个不同 sourceKey 的 +2 请求；

B. 把学生分数依次设成 149、150、1、0 分，分别执行 +2、+2、-10、-1 操作；

C. 用两个并发请求带着一样的 sourceKey 同时调 apply()；

D. 在 notifyStudent() 里手动抛一个未处理异常做故障测试；

E. 针对同一个超时订单，重复触发“未评价”和“撤销超时”两个定时任务；

{\bfseries 按需求应该得到：}

A. 最终分数变成 104 分，而且生成 2 条独立的信用流水（符合 BR-14）；

B. 分数一直卡在 0~150 之间，核对每次截断后的流水记录情况，确认 0 变动时的记账口径；

C. 同一个事件只加扣分一次，重复的并发请求正常返回 duplicated=true 不报错；

D. 确认站内通知报错时主事务会不会跟着回滚，从而确定最终的事务和异常处理方案；

E. 不会对同一笔订单重复扣分，且超期时间严格按连续 168 小时、到点即超期来算 (SRS.md:653-666)；

{\bfseries 还必须检查的数据或副作用：}学生表中的最终信用分与更新时间、信用流水表的记录总数及 source\_key / delta / event / reason / order\_id 等字段值、站内通知表的新增数量、接口返回的 HTTP 状态码、后台错误与异常堆栈日志、关联订单的状态流转结果以及数据库事务回滚情况。
