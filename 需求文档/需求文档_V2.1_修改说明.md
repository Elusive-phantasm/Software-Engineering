## 2. 修改动因：修 V2.0 的一个硬缺陷

V2.0 在 UC-10 主事件流第 6 步写着：

> 系统通知买卖双方成交结果，**并向双方互发展示对方可用于线下联系的渠道**

但同一份文档里：

| 位置 | 内容 |
|---|---|
| §6.5 / NFR-04 | 手机号「**均不可查看，含成交对家**」 |
| §6.2.1 商品实体 | **没有联系方式字段** |
| 全文 | **没有私信 / 留言 / 聊天功能** |

**结论：V2.0 里买卖双方成交之后，在平台上找不到任何一条路能联系上对方。** UC-10 第 6 步承诺了一个数据模型里根本不存在的能力，交易到手即断。

同时，这一缺陷与同类项目对照后更明显：校园二手平台的通行做法是「平台不碰钱、不碰货，那它交付给用户的唯一东西就是**让你联系上对方**」。缺了这一步，「让交易可信」（G-01）与「让交易便捷」（G-02）都落不了地。

**V2.1 的取舍：用「绑定商品的站内私信」补齐通道，而不是放开手机号可见性。**

考虑过两种方案，最终选了后者：

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 互开手机号 | 成交后双方可见对方手机号 | 直接推翻 NFR-04「成交对家亦不可见」的定案，隐私口径要重写；且注册时手机号本就非必填，可能为空 |
| **B. 站内私信（采用）** | 私信绑定具体商品，双方在站内沟通 | **NFR-04 口径零改动**，代价只多一个实体与两个用例 |

选 B 还带来一个副作用：**平台不再需要任何"联系方式"字段**，商品/学生实体都不用加字段，隐私面反而更干净。

## 3. 新增内容清单

### 3.1 新实体：私信（`私信`）

| 字段 | 说明 |
|---|---|
| 私信编号 | 唯一标识 |
| 商品编号 | **会话必须绑定一件具体商品**（BR-20） |
| 发送人学号 | 须为会话参与方；学生发送人须已认证 |
| 接收人学号 | 须为会话参与方；**接收人为管理员时，商品下架原因必须为「管理员违规下架」** |
| 内容 | 纯文本，1～500 字（建议值，待确认），不存附件、不写日志 |
| 发送时间 | 用于会话列表倒序与消息正序 |
| 已读状态 | `未读`／`已读`，仅接收人可置读 |

> **关键设计：不建「会话」表。** 会话 = 同一（商品，双方学号有序对）下的私信行聚合，列表、未读数、最后消息时间都由应用层算出。理由：私信本身已是完整事实，多建一层会话表只会产生两份需要保持一致的状态。因此**私信没有状态机**，也不进状态需求章节的转换表。

### 3.2 新用例（2 个）

| 编号 | 名称 | 覆盖内容 |
|---|---|---|
| **UC-29** | 联系卖家与沟通 | 发起会话、收发消息、协商取货；8 条辅事件流（未认证／自聊／已售出／已下架／空消息／重复进入／对方封禁／发送失败） |
| **UC-30** | 查看我的私信 | 会话列表、未读数、置已读、跳回商品；6 条辅事件流（无会话／商品失效／对方封禁／已非参与方／未读数异常／管理员越权） |

### 3.3 新业务规则

**BR-20 私信范围与准入**：必须绑定具体商品；参与者仅限该商品发布人、沟通过的已认证学生、以及（仅当下架原因为「管理员违规下架」时）管理员；只有已认证学生可发起；同一（商品，双方）只有一条会话；**平台不展示、不转交、不代填手机号与宿舍地址**；管理员仅可回复处置异议私信，不得主动发起；纯文本、无附件、无撤回、无群聊。

### 3.4 新质量需求

**NFR-09 站内消息可达性**：五条可测指标——① 提交成功后 5 秒内接收方可见（建议值，待确认）；② 未读数偏差为 0；③ 不重复投递；④ 正文不写入日志；⑤「显示已发送但实际未保存」的次数为 0。验收方式含第三方越权读取测试。

### 3.5 新场景

**SC-09 私信与沟通**：未认证被拒 → 已认证发起 → 通知与回复 → 下单成交 → 已售出后继续沟通 → 非成交买家被拒 → 卖家异议会话管理员可读 → 第三方读取返回 0 条正文。

### 3.6 新增 §4.3 禁售品类清单（关闭最大遗留缺口）

**背景**：BR-04 从 V1.2.1 起就写着「禁售品类在审核时拒绝」，但「什么算禁售品类」始终没有清单。后果是**审核用例（UC-06）没有判据、无法验收**——这是全文档最严重的一处空洞，历次修改说明里都只能写「待补充」。

**本次定义**：新增 **§4.3**，给出：

| 组成 | 内容 |
|---|---|
| 清单本体 | **18 个类目**，编号 A1–E2：A 法律法规禁止流通（7）、B 实名与资质管制（4）、C 侵权与隐私（3）、D 学术诚信（2）、E 校园安全（2） |
| 每类内容 | 类目名 + **典型物品举例（非穷尽）** + 禁售原因 |
| 判定口径 | **5 条**：①按物品主体判定不按卖家声明；②教材教辅允许（印制答案不算 D2）；③二手电子产品允许（须清数据、无账号、说明权属）；④虚拟商品一律禁止；⑤**清单为闭集，管理员不得扩容**，清单外违规走「清单外待裁定」上报 |
| 对应关系 | 醒目列出与 ST-03（审核拒绝）、ST-07（强制下架）、ST-08（重提）、UC-12→UC-13（举报）的映射 |
| 可测试性 | 明确验收方法：**按 18 个类目逐条构造测试商品，期望全部驳回并记录正确类目编号** |

**为什么这样设计**：只给「违禁品」三个字等于没给判据；但给一份无边界的大全，审核员又会自由裁量。所以采用**闭集 + 类目编号 + 边界口径 + 扩容纪律**四件套：既能逐条验收，又不允许管理员临时加码。

**连带改动**：
- BR-04 由「待确认/AI 候选」升为「**团队已复核**」，并直接引用 §4.3；
- UC-06 主事件流第 2 步改为「逐项比对 §4.3 清单」，第 5 步要求驳回原因**引用类目编号**；新增辅事件流 F 处理「清单外待裁定」；删除原文「已知缺口」提示；
- UC-12 补充「违禁品」举报类型与 §4.3 的对应关系；
- §5.3「审核商品」「下架违规商品」两行加入 §4.3 引用；
- §5.6 走查表新增 3 条输入，其中 2 条是**反向用例**（二手 iPad、含答案的教材应被放行），防止审核员过度拒绝；
- 附录 B「禁售品类」词条指向 §4.3；
- 遗留待确认项第 1 条关闭，改为「清单合法性依据待学校学工/保卫部门确认」。

### 3.7 新增「成交撤销」回滚回路（修 V2.0 的第二个硬缺陷）

**背景**：V2.0～V2.1 早期把 `已售出` 定为**硬终态**——「任何角色都不可再变更」。于是最常见的情形无解：

> 买家下单成交 → 双方私信约不上时间 / 买家反悔 / 卖家不卖了 → **商品被永久锁死在「已售出」**，卖家既不能重新上架，也拿不到任何救济。而 BR-07 只写「纠纷由双方自行协商」，协商不成即死局。

**这不是「功能不够全」，是「下单即成交」这个设计缺了自带的回滚路径**。状态机可以简化到只剩一个终态，但**终态本身必须能出来**，否则不是简化而是死锁。

**本次定义**：新增一套最小的撤销回路——

| 组成 | 内容 |
|---|---|
| 新用例 | **UC-31 撤销成交**（7 条辅事件流：对方拒绝／超时／已评价／重复撤销／卖家封禁／非当事人／记录保留） |
| 新规则 | **BR-21 成交撤销**：`有效 → 已撤销` **必须双方同意**，不支持单方强制；须双方均未评价；撤销后商品回 `在售`、原记录保留不删；**不扣任何信用分**，且不再触发「7 天未评价 −1」 |
| 状态转换 | **ST-10** `已售出 → 在售`（双方同意撤销）；**ST-11** `已售出 → 已下架`（撤销时卖家已封禁，下架原因＝`撤销后不可交易`） |
| 数据字段 | 订单增加 `成交状态`（`有效`／`已撤销`）、`撤销发起人学号`、`撤销原因`、`撤销时间` |
| 新场景 | **SC-10 成交撤销与重售** |
| 通知 | BR-15 增加「收到撤销成交申请」「撤销成交成立」两个事件 |

**关键取舍：这不是把订单状态机加回来。**

| | 原来的八状态订单机 | 现在的「有效／已撤销」 |
|---|---|---|
| 表达什么 | 钱到没到、货交没交 | **双方是否一致同意终止** |
| 平台能否确认 | ❌ 支付与交付都在站外 | ✅ 两人的一致意见是平台能确认的事实 |
| 状态数 | 8 | **2** |

区别在于：前者要求平台观测它观测不到的东西，后者只要求平台记录**双方是否同意**。

**连带改动**：
- `已售出` 从「硬终态」改为「默认终态 + 一条双方合意出口」（§7.1、§7.2）；
- §6.3「商品—订单」多重性由 **0..1** 改为 **0..***，并加约束「**任意时刻有效记录 ≤ 1**」——撤销后可重新成交，形成多条历史记录；
- BR-08 评价前置改为「**有效**成交记录」，已撤销记录不可评价；
- BR-14 明确「已撤销记录不适用第 ③ 项（7 天未评价 −1）」；
- UC-16 我的订单增加「申请撤销成交」入口与「已撤销」只读展示；
- §5.2 权限矩阵、§5.3 业务条件、§5.6 三条走查输入、§6.4.1 原子性约束、附录 B 术语、附录 C 映射全部同步。

### 3.9 边界条件补齐（第二轮）

对全文做了一次系统性边界检查（状态空间 → 用例异常路径 → 数值边界 → 并发竞态 → 数据约束）。以下为**结论明确、不涉及业务取舍**的部分，已直接修正：

| 编号 | 问题 | 处理 |
|---|---|---|
| **A1** | **商品实体缺「描述」字段**——UC-05 要求填写、举报类型有「虚假描述」、详情页要展示，但数据字典 10 个字段里没有 | 商品实体新增 `描述`（1～1000 字，纯文本，必填） |
| **A2** | **BR-09「已售出不可下架」与 UC-13 辅流 F「仍可执行强制下架记录」矛盾**，且 ST-07 的入口状态只有「在售」 | UC-13 F 改为「仅**记录处置结论**、扣分、封禁；**商品状态保持「已售出」不变**」 |
| **A3** | **举报记录缺唯一性约束**，导致 UC-12「重复举报不新增」在数据层无法保证 | 举报记录加 `(举报学生学号, 被举报商品编号) 组合唯一` |
| **A4** | **信用分越界未定义**：149 分 +2 = 151？1 分 −10 = −9？ | BR-13 补「**越界按边界值截断**」（上限 150、下限 0），且**截断值须与信用记录一致** |
| **B4** | **撤销申请等待期间对方提交评价**——申请时时都没评价，申请后才评，撤销还算数吗 | UC-31 新增辅流 C：**申请自动失效**；BR-21 同步 |
| **B5** | **双方各自提交撤销申请**——会互相等对方同意而卡死 | UC-31 新增辅流 E：**视为双方均已同意，撤销立即成立**，两条申请合并留档；BR-21 同步 |
| **B8** | **私信发给已封禁用户时「不投递」含义不明**（落不落库？显示「已发送」吗？） | UC-19 辅流 G 明确：**不落库、不通知、返回明确失败，不得显示「已发送」**（对齐 NFR-09 第 ⑤ 条） |
| **C4** | **时间边界口径不统一**——「7 天内」「24 小时内」是自然日还是连续时长？含不含截止时刻？影响 6 处期限 | 新增 **§4.1.1 时间期限的统一口径**：一律按**连续时长**、**左闭右开**（恰好到点即超期）、**服务端时间**，并逐条列出 6 个期限的起算事件 |
| **D** | **并发竞态只覆盖了 1 种**（两人同时下单） | §5.5 第 7 条改写为**并发总则**，覆盖 6 组并发对：双下单、下单 vs 下架、审核 vs 撤回、双管理员处理同一举报、双方各自撤销、撤销 vs 评价 |
| **E** | **商品状态与成交记录的双向一致性未表述** | §6.4.1 新增一致性表：`在售/待审核/已下架` 不得有有效成交记录；`已售出` 必须恰好 1 条；任意状态有效记录 ≤ 1 |

**这批的共同特征**：都是「文档内部不自洽」或「规则写了但数据层没支撑」或「边界值没界定」，**不改变任何已定的业务口径**，所以可以直接修。

### 3.10 待确认边界条件的决策与落地（已拍板）

| 决策项 | 结论 | 落地内容 |

| **封禁是否连带下架** | **是，封禁即下架其全部存量商品** | **BR-10** 增补「封禁须连带处置存量商品」；新增 **ST-13**（`在售/待审核 → 已下架`，与封禁同一处置动作原子完成）；UC-13 主事件流第 4 步补联动说明与走查输入 |
| **伪造证件查实是否强制封禁** | **是，强制封禁** | **BR-18** 由「**可**封禁」改为「**应**封禁」，并要求按 BR-10 连带下架其商品；**AT-08** 同步为「同一处置动作中必须封禁 + 下发 ST-13」。状态由「待确认」升为「团队已复核」 |
| **图片是否强制至少 1 张** | **是，改为 1～9 张必填** | 数据字典 `图片` 由「0～9 张、非必填」改为「**1～9 张、必填**」；UC-05 主事件流与辅事件流 E 同步（未上传图片即不生成商品） |

**为什么在售编辑必须重审（记录理由）**：若允许在售商品自由编辑，卖家可以**先发合规商品过审、再改成禁售品继续卖**，§4.3 的整个审核机制会被绕过。代价是改个错别字也要重新排队，但这是审核可信的必要成本。

**顺带修正的失效约束**：§7.2 原本把「`在售` → `待审核`」列为**不存在且视为缺陷**的转换，与新增的 ST-12 直接冲突，已改为合法转换，并把「`待审核` → `已售出`」补进缺陷清单。

### 3.11 撤销申请的状态承载（模型缺口修复）

上一轮补 UC-31 时写了三条辅事件流——「24 小时超时申请失效」「等待期间对方评价使申请失效」「双方各自申请视为双方同意」——但**数据模型里没有地方存放"当前有一条待确认的申请"这个事实**：订单的 `撤销发起人学号`／`撤销原因`／`撤销时间` 三个字段都只在**撤销成立后**才填写。

后果：这三条规则**全部无法实现**——系统不知道申请是否存在、何时提交，也就无法计时、无法判定冲突、无法识别"对方已申请"。

**修复**：为订单增加 **`撤销申请状态`**（`无` ／ `待对方确认`），并把原三个字段改为随申请一起记录：

| 字段 | 必填时机 |
|---|---|
| `成交状态` | 恒必填（`有效`／`已撤销`） |
| `撤销申请状态` | 恒必填（`无`／`待对方确认`） |
| `撤销申请发起人学号` | 有申请或已撤销时 |
| `撤销申请原因` | 有申请或已撤销时 |
| `撤销申请时间` | 有申请或已撤销时（**24 小时等待期的起算点**） |
| `撤销时间` | 仅已撤销时 |

并明确**两个标记正交、合法组合只有三种**（`有效+无`、`有效+待对方确认`、`已撤销+无`，`已撤销+待对方确认` 为非法），在 §6.4.1 加了三条一致性约束。

**同时把主事件流的判定写成可执行的分流**：发起方提交时读 `撤销申请状态` 三路分流——`无` 则创建申请、**发起人是本人**则拒绝重复、**发起人是对方**则直接判定双方同意并成立。这样「双方各自申请」不再是靠"合并留档"这种无法落地的说法，而是一个**明确的分支 3c**。

### 3.12 撤销模型改为「单方即时 + 事后记账」（方案 D）

**问题**：3.11 那套「双方同意才可撤销」有一个致命推论——**对方拒绝或失联，商品就永久卡在「已售出」**。给 `已售出` 开口子的初衷是解开死锁，结果又被"必须双方同意"锁了回去。

**根因**：平台既不碰钱也不碰货，**无法判断交易进行到哪一步**。于是"允许单方撤销"会让已履约方吃亏，"要求双方同意"又会死锁——两头都不对。

**参照真实项目的做法**：[ust-inform-trade-CCF](https://github.com/hhuang999/ust-inform-trade-CCF) 用的是 **「行为不设闸，声誉记账」**：物品交易任一方可随时取消，物品立即回到可售；服务预约单方取消则由对方判定「同意免责」或「计违规」，对方 7 天不表态默认计违规。**取消永不阻塞，成本落在声誉上。**

**本版采用同一思路**，把撤销模型整体换掉：

| | 旧（3.11 版） | **新（方案 D）** |
|---|---|---|
| 谁能撤销 | 一方发起 + 对方同意 | **任一方当事人单方即可** |
| 生效时机 | 对方同意后 | **提交即生效** |
| 对方能做什么 | 同意／拒绝（拒绝即死锁） | 只能事后判「已免责」或「计违约」 |
| 7 天不表态 | 申请失效，商品仍锁死 | **自动计违约，撤销方 −2** |
| 死锁风险 | **存在** | **不存在** |
| 记录字段 | `撤销申请状态`（无／待对方确认） | **`撤销免责判定`（待判定／已免责／计违约）+ `免责判定时间`** |

**具体改动**：

1. **订单字段**：删除 `撤销申请状态`，新增 `撤销免责判定`（`待判定`／`已免责`／`计违约`）与 `免责判定时间`；`撤销发起人学号`／`撤销原因`／`撤销时间` 改为「已撤销时必填」，**不再有"申请中"的空窗期**。
2. **BR-21** 重写为「单方即时生效 + 事后记账」：撤销即时生效、不可回滚；对方 7 天内判定，超时**默认计违约**；平台不判断是否已实际交付，一方主张已履约的走 UC-13 交易争议。
3. **BR-14 新增第 ④ 项**：**单方撤销且被判 `计违约` → 撤销方 −2**（每笔成交最多一次；`已免责` 不扣）。信用记录 `变动值` 枚举相应加入 `−2`。
4. **ST-10 / ST-11** 执行角色由「发起＋对方同意」改为「买家**或**卖家（单方）」，目标结果增加 `撤销免责判定` 置 `待判定`。
5. **UC-31** 主事件流改为「校验 → 即时撤销 → 通知对方可判责 → 对方判定／7 天超时自动判违约」；辅事件流从 9 条精简重写，新增「主张已履约走 UC-13 争议」一条。
6. **UC-16 我的订单** 辅流 F/G 改为按身份展示不同视图：被撤销方看到「同意免责／计违约」按钮与剩余天数，撤销方看到「等待对方判定，7 天后默认计你违约」。
7. **§4.1.1 时间表**：「撤销申请等待 24 小时」替换为「**免责判定 7 天**（自 `撤销时间` 起算，满 168 小时自动计违约）」。
8. **§5.2 / §5.3 / §5.6**：「须对方同意」全部删除；走查输入「单方强制撤销应被拒」改为「单方撤销**允许**、即时生效」。
9. **§6.4.1** 一致性约束按新字段重写，并明确「**免责判定只影响信用分，不回滚撤销**」。
10. **SC-10** 改为覆盖三条路径：判计违约、7 天超时自动计违约、已评价后撤销被拒。
11. **术语表**：新增「撤销免责判定」「违约（撤销）」两个词条，`撤销成交` 定义改为「单方即可、即时生效」。

**与 ust 项目的差异（有意为之）**：他们把物品交易做成**零成本取消**（`ItemDeal` 无 `liabilityAgreed`，`ViolationSource` 也没有物品取消），只有服务预约才记账。本版**物品交易也记账**（−2），因为我们的信用分直接挂钩发布与下单权限（<60 禁发布、<40 禁下单），**有约束才有意义**；他们 MVP 阶段只记录不惩罚，所以敢放宽。

**遗留风险（须如实说明）**：撤销即时生效 + 平台无法观测交付，意味着**已实际交货或已转账的一方，其救济只能是"判对方违约 + 提交交易争议"，无法追回货物或款项**。这是「平台不碰钱、不碰货」这条边界的必然代价，不是实现缺陷。该风险已在 §7 遗留项中标明。

### 3.15 举报模型扩展：支持举报「学生」（补上跑路救济路径）

**问题的由来**：追问「买家线下转账后卖家跑路，文档怎么处理」时发现，V2.1 的救济路径**根本不存在**：

- BR-21、术语表、遗留项都写「一方主张已履约的，**按 UC-13 提交交易争议由管理员核实**」
- 但 UC-13 的主事件流全是**举报处理**，前置条件要求「存在待处理举报」；而**举报对象当时仅限商品**
- 「收款跑路」是**人的行为**，用"举报商品"表达不了 → **那句救济路径是悬空引用**

顺带对比了 [ust-inform-trade-CCF](https://github.com/hhuang999/ust-inform-trade-CCF)（CCF 获奖项目、已上线）：它的 `ReportReason` 里有 `SUSPECTED_FRAUD`，`ReportTargetType` 里有 **`USER`**，主页**公开违规次数**。**它靠「举报人 + 声誉公开」兜，而不是靠流程锁死。**

**本次照此扩展举报模型：**

| 改动 | 内容 |
|---|---|
| **举报对象类型化** | 举报记录新增 `被举报对象类型`（`商品`／`学生`）；`被举报商品编号` 与新增的 `被举报学生学号` **恰好一个非空** |
| **举报类型加 `收款不履约`** | 由五值扩为**六值**：违禁品、虚假描述、价格欺诈、站外导流、**收款不履约**、其他。前四类只能举报**商品**，`收款不履约` 只能举报**学生**，`其他` 两者皆可 |
| **受理条件** | 举报学生时，**须与举报人存在过成交记录或私信会话**，否则不受理（防止无凭据举报陌生人） |
| **唯一性泛化** | 由 `(举报人, 商品)` 改为 **`(举报人, 对象类型, 对象编号)` 组合唯一** |
| **新增公开计数** | 学生实体加 **`被核实争议数`**：对人举报经核实成立的累计次数，**公开显示在主页**（只显示计数，不公开具体内容与举报人）→ 让下一个买家能看见风险 |
| **UC-12 扩展** | 改名「举报违规商品**或学生**」，主事件流按入口确定对象类型；辅事件流由 4 条扩为 7 条（新增无关系不受理、不能举报自己、类型与对象不匹配） |
| **UC-13 扩展** | 主事件流第 4 步按对象类型分流处置：**对象为学生时不含「强制下架商品」**，但 `收款不履约` 成立时**应封禁并按 ST-13 联动下架其在售商品**；辅事件流由 6 条扩为 9 条 |
| **BR-04 / BR-14 同步** | BR-04 补「举报对象可为商品或学生，对人的举报仅限与该学生的成交或沟通行为」；BR-14 ② 由「卖家 −10」改为「**被举报方 −10**」（对象为学生时为该学生） |
| **BR-21 / UC-31 辅流 H / 术语表** | 「按 UC-13 提交交易争议」全部改为**「通过 UC-12 举报该学生（类型 `收款不履约`）」**，悬空引用消除 |

**这样修完之后，「买家转账后被跑路」在文档里第一次有了完整闭合的路径：**

```
撤销成交（即时脱身，商品回在售）
  → 举报该学生 · 收款不履约
  → 管理员核实私信与成交记录
  → 成立：对方 −10、封禁、ST-13 下架其在售商品、被核实争议数 +1（公开可见）
  → 不成立：不留痕、不扣分、不公开
```

**仍然做不到的**：追回资金。这一点没有变，也变不了——平台不碰钱。但现在的差别是：**买方有入口、有留痕、有公开后果，卖家跑路不再是"零成本无记录"。**

### 3.16 与 ust 项目第二轮对照：8 项补齐

再次对照 [ust-inform-trade-CCF](https://github.com/hhuang999/ust-inform-trade-CCF) 的 PRD 与 schema 逐层核查，发现 8 处问题并全部修复。**其中前两项是第二轮边界检查时已识别、当时说要修但实际没修的**。

| # | 问题 | 修复 |
|---|---|---|
| **1** | **学生实体缺「真实姓名」**——UC-03 要求「核对证件姓名与账号所填姓名一致」，但账号侧没有姓名字段，**核验动作无法执行** | 学生实体新增 `真实姓名`（必填，仅本人与核验/处置管理员可见）；UC-03 队列与核对项、§5.3 同步 |
| **2** | **以学号作登录账号存在抢注**——知道他人学号即可抢先注册占位，本人反而注册不了 | **改为邮箱登录**：学号不再参与登录；注册填邮箱+昵称+真实姓名，学号在 UC-02 提交核验时**申报**、核验通过后才绑定且全局唯一。涉及 §2.1 身份边界、学生实体、认证申请实体（新增 `申报学号`）、UC-01/02/03、AT-01/02、NFR-05、术语表 5 个词条 |
| **3** | **「个人主页」被 4 处引用却无定义**（UC-14「在对方主页展示评价」、UC-15「在他人主页查看信用分」、术语表「公开显示在其主页」） | 新增 **UC-33 查看个人主页**，明确公开字段（昵称、认证标识、信用分、评价数、被核实争议数、在售商品、已公开评价）与不公开字段（真实姓名、手机号、宿舍地址、成交记录、举报明细），7 条辅事件流覆盖封禁/未认证/游客/空态/争议展示 |
| **4** | **举报处置手段是自由文本**，无法统计「下架多少次、封禁多少人」 | 举报记录新增 `处置手段`（**枚举集合**：警告/强制下架商品/限制发布/封禁账号/扣信用分，可多选）；对象为学生时不得包含「强制下架商品」 |

### 3.17 新增邮箱验证码（注册 + 找回密码）

**起因**：团队提议"加邮箱验证码防刷号"。核查后发现，**它真正的价值不是防刷，而是补第 9 个悬空引用**——UC-01 辅流 B 写着「引导**找回密码**」，但全文没有任何找回密码的用例，**学生一旦忘记密码，账号就永久废掉**。

| 改动 | 内容 |
|---|---|
| **新增 UC-34 找回密码** | 邮箱验证码 → 校验 → 重置新密码 → **该账号所有会话立即失效** → 双通道通知。10 条辅事件流，含**账号枚举防护**（邮箱存在与否返回同一提示）、频控、错误作废、新旧密码不得相同、封禁账号可重置但登录仍拒 |
| **UC-01 注册加验证码** | 主事件流插入「获取验证码 → 填写 → 校验通过才创建账号」；辅事件流由 6 条扩为 **10 条**（新增验证码错误/过期、请求过频、邮件发送失败、注册中邮箱被抢注） |
| **新增 NFR-10 邮箱验证码安全** | 6 位／10 分钟／一次性；**只存哈希，不进日志、审计、导出、错误提示**；**60 秒 1 次 + 24 小时 10 次**双重频控；错误 5 次作废；**防账号枚举**（响应时间均值差 ≤ 100 毫秒）；重置后既有会话立即失效 |
| **新增 `邮箱验证码` 实体** | 验证码编号、邮箱、用途（注册／找回密码）、验证码哈希、生成时间、过期时间、已使用、失败次数（8 字段） |
| **术语表 +2** | `邮箱验证码`、`找回密码` |
| **关闭遗留项** | 「登录密码找回方式待确认」已被 UC-34 覆盖；新增两条待确认（NFR-10 建议值、SMTP 依赖） |

**关于"防刷"的如实说明**（这段建议在答辩时主动讲）：

> 邮箱验证码**防不住伪造学生证**——平台的准入门槛是人工核验，不是邮箱。它真正的价值有三：① **账号找回**（原本完全缺失）；② **邮箱真实性**（否则找回邮件发不出去）；③ 抬高**低成本刷号**的门槛（未认证账号虽不能交易，但能收藏，可刷虚假热度）。
>
> 换句话说：**验证码让"账号"变真，学生证核验让"人"变真，两者不能互相替代。**

**新增外部依赖**：邮箱验证码需要 SMTP 邮件服务，这是本项目**唯一的外部服务依赖**，已在遗留项中标明。
