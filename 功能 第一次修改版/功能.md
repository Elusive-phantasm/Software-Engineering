## 〇、编写口径（先看这一节，方便合稿检查）

| 项目 | 约定 |
|---|---|
| 参与者 | 用例图里只有两个参与者：**学生**、**管理员**。买家、卖家、捐赠者、领取人、出借人都是「学生」这个参与者在不同用例中的角色，**不单独画小人**；自提点、代收点、回收点是**外部组织，不建模为参与者**，也不是系统用户 |
| 参与者写法 | 「学生（买家）」「学生（卖家）」表示角色；一条用例需要两方时，写「主要：学生（买家）；次要：学生（卖家）」 |
| 账号状态 | 未认证 / 已认证 / 受限 / 封禁（术语表 §二）。「实名认证 / 身份核验」是**过程名**可用；账号状态的词一律写「**已认证 / 未认证**」，不写「已实名」 |
| 商品状态 | **只有 5 个**：待审核 / 在售 / 已预订 / 已售出 / 已下架。审核不通过 = 「已下架」+ 下架原因写「审核不通过」，不新增状态；「谁下架的」（卖家主动 / 管理员强制）记在**执行角色**，不新增状态 |
| 订单状态 | **定案 8 个**：待支付 / 已支付 / 待交付 / 待确认 / 已完成 / 已取消 / 退款中 / 已退款。买家点「我已付款」、卖家点「确认已收款」是 **待支付 → 已支付 的转换条件**，不是独立状态 |
| 物品流转状态 | 捐赠：待领取 / 已预约 / 已转交 / 已取消；借用：申请中 / 借用中 / 已归还 / 逾期。**与商品 5 状态、订单 8 状态互不占用**，状态图由吕锦浩出，本稿状态名与他保持一致 |
| 编号引用 | 共用 `UC` `BR` `ST` `SC` `PV` `V` `NFR` `E` `AI` `G` `C` `AS` 体系，**不新增前缀**。系统主动发通知的规则写成**一条 BR 业务规则**（编号待吕锦浩在 BR 表顺延） |
| 通知怎么写 | 拆成两件事：**用户查看消息 = 用例 UC-23**；**系统主动发通知 = BR 规则**（由系统触发，不是参与者发起，画不进用例图） |
| 失败分支写法 | 被拒绝 / 失败的分支必须写清**状态保持**（如"不生成订单，商品保持「在售」"），不能写成转换成功 |
| 粒度 | 只写用户看得见的行为，不写系统内部实现（不用"加密""缓存""接口"这类说法） |
| 一件功能一件事 | 发现一条里塞了两个动作就拆开；本稿已按此检查过 |

**相对原 19 条清单的改动**（均已写进下面的正文）：

1. **UC-14 由「下架商品（管理员）」改为「下架自己的商品（卖家）」** —— 原清单漏了卖家撤下自己商品这个用户行为。
2. **UC-15 扩为「处理举报、申诉与违规处置」** —— 承接管理员下架违规商品的能力，并补上申诉的受理与复核（UC-13 误判、UC-16 扣分、UC-20 取消纠纷、UC-22 被下架都要有承接）。
3. **UC-07 把「买家标记已付款 → 卖家确认收款」写成 `待支付 → 已支付` 的转换条件** —— 不再新增中间状态，避免状态数失控。
4. **新增 UC-20 取消订单** —— UC-07、UC-08、UC-09 三条辅事件流都在调用它，原清单里没有这条功能。**退款不单列为用例**，它是取消订单的一个场景，订单状态机增加「退款中 / 已退款」。
5. **新增 UC-21 查看我的订单、UC-22 查看我的商品** —— 取消、退款、确认收货、评价、下架都要从这两个列表进入。
6. **新增 UC-23 查看消息通知**，并把「系统主动发通知」写成**一条 BR 业务规则**（不作为用例，不新增 FR 前缀）。
7. **拆分 UC-17 与 UC-19**：UC-17 只保留"提交捐赠 + 入库确认"，领取拆为 **UC-24**；UC-19 改为「申请借用」，归还拆为 **UC-25**；"发布可借物品"并入 UC-02（发布时增加"出借"类型）。
8. **按 10 月 23 日清单统一口径**：订单 8 状态、商品 5 状态、UC-01 改名并改为统一身份认证、账号状态改「已认证」、举报范围收窄到商品、自提点/代收点/回收点不建模为参与者、取消 FR-01。

## 二、UC-01 ~ UC-19 功能说明

### UC-01 通过统一身份认证登录并核验身份

| 字段 | 内容 |
|---|---|
| 参与者 | 学生 |
| 目标 | 进入平台并完成学号身份核验 |
| 前置条件 | 已通过学校统一身份认证登录 |
| 触发条件 | 学生点击「登录」 |
| 主事件流 | 1. 学生点击「登录」<br>2. 系统跳转学校统一身份认证<br>3. 学生在学校认证页完成认证<br>4. 系统接收学校返回的学号与身份信息<br>5. 首次登录自动建档<br>6. 账号状态标记为「已认证」，可发布与购买 |
| 辅事件流 | A. 学校认证未通过或学生取消 → 返回登录页，账号保持「未认证」<br>B. 学校返回的学号已绑定其他账号 → 提示「该学号已绑定其他账号」，转身份核验申诉由管理员人工处理，账号保持「未认证」<br>C. 未认证学生尝试发布/下单/评价 → 拦截并提示「请先登录并通过身份核验」，账号保持「未认证」（UC-02、UC-06、UC-11 引用此流）<br>D. 学生在校信息变更（转专业、换院系）→ 以学校返回信息为准，下次登录自动更新，无需重新认证<br>E. 统一身份认证服务不可用 → 提示「认证服务暂不可用，请稍后再试」，账号保持「未认证」 |
| 后置条件 | 账号状态为「已认证」，可发布和购买；认证记录留档 |
| 发生频率 | 上课日 9:00–23:00 约 1200 次/天（含既有账号每次登录） |
| 关联 | BR-待定（一学号一账号）、NFR（单点登录响应时间、个人信息保护） |

### UC-02 发布二手物品

| 字段 | 内容 |
|---|---|
| 参与者 | 学生（卖家） |
| 目标 | 卖家把要卖的物品或要出借的物品挂到平台，审核通过后对外展示 |
| 前置条件 | 已登录、已认证；账号未被限制发布 |
| 触发条件 | 卖家在「我要卖」页点击「发布」 |
| 主事件流 | 1. 选择发布类型（出售 / 出借）<br>2. 填写标题、分类、价格或押金、成色、描述<br>3. 上传物品图片（1–9 张）<br>4. 选择可交付方式（见面交付 / 送到自提点）<br>5. 提交<br>6. 系统生成一条「待审核」商品，提示「等待管理员审核」 |
| 辅事件流 | A. 必填项缺失或价格非法（≤0、超过上限）→ 就地提示，**不生成商品**，页面保持编辑中<br>B. 图片格式/大小不符，或含水印联系方式 → 提示重新上传，**不生成商品**（是否禁止联系方式由 BR 定）<br>C. 未认证 → 走 UC-01 辅事件流 C，**不生成商品**<br>D. 与已有商品高度重复（同图同描述）→ 提示「疑似重复发布」转人工复核，**商品保持「待审核」**<br>E. 卖家在待审核期间想改 → 可撤回后重新提交（沿用原商品编号，是否计入发布次数由 BR 定）<br>F. 发布类型选了「出借」但未填可借时段、押金或归还要求 → 提示补全，**不生成商品** |
| 后置条件 | 生成一条「待审核」商品；此时不对外展示 |
| 发生频率 | 上课日 9:00–23:00 约 260 次/天，开学季 800 次/天 |
| 关联 | BR-待定（价格上限、违禁品清单、图片张数）、ST（待审核 → 在售 / 已下架）、UC-14、UC-19、UC-22 |

### UC-03 搜索商品

| 字段 | 内容 |
|---|---|
| 参与者 | 学生 |
| 目标 | 快速找到想买的商品 |
| 前置条件 | 无（未登录可浏览；下单才需要登录与认证） |
| 触发条件 | 在首页搜索框输入关键词并搜索，或提交筛选条件 |
| 主事件流 | 1. 输入关键词，或选择筛选条件（分类、价格区间、成色、交付方式、排序）<br>2. 系统检索处于「在售」的商品<br>3. 返回结果列表（图片、标题、价格、成色、发布时间）<br>4. 学生点击进入商品详情页 |
| 辅事件流 | A. 无匹配结果 → 提示「没有找到相关商品」，推荐相邻分类或建议放宽筛选，列表为空<br>B. 关键词为空 → 提示先输入关键词，**不发起检索**<br>C. 结果中混入已售出/已下架商品 → 不展示<br>D. 浏览期间商品被他人下单 → 详情页提示「该商品已被预订」，购买按钮置灰，**商品状态不变**<br>E. 关键词为敏感词/违规内容 → 按 BR 过滤并提示，**不发起检索** |
| 后置条件 | 无（只读操作） |
| 发生频率 | 上课日约 6000 次/天（人均约 15 次） |
| 关联 | BR-待定（只展示在售、排序规则） |

### UC-04 按分类浏览商品

| 字段 | 内容 |
|---|---|
| 参与者 | 学生 |
| 目标 | 按分类逐层浏览，发现想买的商品 |
| 前置条件 | 无（未登录可浏览） |
| 触发条件 | 在首页点击分类入口 |
| 主事件流 | 1. 系统展示一级分类列表<br>2. 学生选择分类（教材书籍、电子数码、生活用品、代步工具等）<br>3. 系统列出该分类下「在售」商品<br>4. 可继续下钻子分类或切换排序 |
| 辅事件流 | A. 该分类下无商品 → 展示「该分类暂无商品」，推荐相邻分类<br>B. 分类入口被停用或合并 → 该入口不再展示<br>C. 分类与商品不符 → 学生可举报该商品（UC-12） |
| 后置条件 | 无（只读操作） |
| 发生频率 | 上课日约 3000 次/天 |
| 关联 | BR-待定（分类目录、只展示在售） |

### UC-05 收藏商品

| 字段 | 内容 |
|---|---|
| 参与者 | 学生 |
| 目标 | 把感兴趣的商品存起来，之后再决定是否购买 |
| 前置条件 | 已登录 |
| 触发条件 | 在商品详情页或列表页点击「收藏」 |
| 主事件流 | 1. 点击「收藏」<br>2. 系统把商品加入个人收藏夹并提示「已收藏」<br>3. 学生可在「我的收藏」查看、取消收藏、进入商品详情 |
| 辅事件流 | A. 重复收藏 → 提示「已收藏」，**不重复记录**<br>B. 收藏后商品被卖出或下架 → 收藏列表标记「已失效」，不可下单，**商品状态不变**<br>C. 未登录点击收藏 → 引导登录，**不生成收藏记录**<br>D. 收藏数量达到上限 → 提示先清理收藏（上限由 BR 定），**不新增收藏** |
| 后置条件 | 收藏关系已记录 |
| 发生频率 | 上课日约 400 次/天 |
| 关联 | BR-待定（收藏上限） |

### UC-06 下单

| 字段 | 内容 |
|---|---|
| 参与者 | 学生（买家） |
| 目标 | 买家锁定想要的商品并生成订单 |
| 前置条件 | 已登录、已认证、商品处于「在售」、不是自己发布的 |
| 触发条件 | 买家在商品详情页点击「立即购买」 |
| 主事件流 | 1. 点击「立即购买」<br>2. 系统检查商品状态与买家资格<br>3. 选择交付方式（见面交付 / 送到自提点）<br>4. 确认订单信息并提交<br>5. 系统锁定商品并生成订单 |
| 辅事件流 | A. 商品已被别人预订 → 提示「该商品已被预订」，返回列表，**不生成订单**，商品状态保持「已预订」<br>B. 买家未认证 → 提示「请先完成身份核验」（UC-01 辅事件流 C），**不生成订单**<br>C. 买家是自己 → 提示「不能购买自己发布的商品」，**不生成订单**，商品状态保持「在售」<br>D. 买家已有一笔该商品的**有效订单**（状态不是已取消/已退款）→ 提示「你已有一笔该商品订单，请先处理」，**不生成新订单**，原订单状态不变<br>E. 提交瞬间商品被他人抢先 → 以先提交者为准，后提交者**不生成订单**，回到辅事件流 A<br>F. 买家选择的交付方式卖家未提供 → 该选项置灰；若强行提交，**不生成订单**，商品状态保持「在售」 |
| 后置条件 | 商品变「已预订」；生成一条「待支付」订单，并记录交付方式 |
| 发生频率 | 上课日 9:00–23:00 约 200 次/天，开学季翻倍 |
| 关联 | BR-待定（下单资格、重复下单）、ST（在售 → 已预订；— → 待支付） |

### UC-07 完成支付

| 字段 | 内容 |
|---|---|
| 参与者 | 主要：学生（买家）；次要：学生（卖家） |
| 目标 | 买家把货款付给卖家，订单进入「已支付」状态 |
| 前置条件 | 订单已生成且处于「待支付」；买家已认证 |
| 触发条件 | 买家在订单页点击「去支付」 |
| 主事件流 | 1. 买家点击「去支付」<br>2. 系统展示卖家的收款方式（微信/支付宝收款码）<br>3. 买家在第三方平台完成转账<br>4. 买家回到系统点击「我已付款」<br>5. 订单**状态保持「待支付」**，系统通知卖家核对到账<br>6. 卖家核对到账后点击「确认已收款」<br>7. 订单状态转为「已支付」，系统通知卖家可以交付 |
| 辅事件流 | A. 买家已标记付款但卖家未收到 → 卖家拒绝确认，订单**状态保持「待支付」**并通知买家<br>B. 买家转错金额或转错人 → 双方协商后取消该订单（UC-20）并重新下单支付（平台不介入资金，退款口径见 BR-待定）<br>C. 买家 24 小时内未点击「我已付款」→ 订单由系统自动取消，商品回到「在售」并通知双方（BR-03，编号待与吕锦浩对齐）。注意：这是系统行为，**不经过 UC-20**<br>D. 买家已付款但卖家超过 48 小时未确认 → 系统再次提醒卖家；仍不确认则允许买家取消订单（UC-20）或上报管理员（UC-15），期间订单**保持「待支付」**<br>E. 支付期间卖家尝试下架商品 → 被拦截（见 UC-14 辅事件流 A），商品**保持「已预订」** |
| 后置条件 | 订单状态为「已支付」；商品保持「已预订」；系统通知卖家可以交付 |
| 发生频率 | 上课日 9:00–23:00 约 170 次/天（约为下单量的 85%） |
| 关联 | BR-03（支付超时自动取消）、BR-待定（平台不介入资金/退款口径）、UC-20、ST（待支付 → 已支付；待支付 → 已取消） |

### UC-08 约定见面交付

| 字段 | 内容 |
|---|---|
| 参与者 | 主要：学生（买家）；次要：学生（卖家） |
| 目标 | 买卖双方就见面交付的时间和地点达成一致，完成线下交接并留下记录 |

## 三、新增的 6 条用例 + 1 条业务规则（UC-20 ~ UC-25）

> **UC-20 ~ UC-23** 是走查前补的漏：取消订单是 UC-07 / UC-08 / UC-09 三条辅事件流共同依赖的分支；我的订单、我的商品是取消、退款、确认收货、评价、下架的实际入口；消息通知是用户主动看消息的行为。**UC-24、UC-25** 是从 UC-17、UC-19 拆出来的——原两条各塞了多个参与者的动作，违反"一件功能一件事"。

### UC-20 取消订单

| 字段 | 内容 |
|---|---|
| 参与者 | 主要：学生（买家 或 卖家）；次要：学生（对方） |
| 目标 | 在订单完成前终止本次交易，并把已付的货款处理清楚 |
| 前置条件 | 已登录；订单处于「待支付 / 已支付 / 待交付 / 待确认」之一，且尚未「已完成」（入口：UC-21 我的订单，或 UC-07 支付页） |
| 触发条件 | 任一方在订单详情页点击「取消订单」 |
| 主事件流 | 1. 发起方点击「取消订单」<br>2. 选择取消原因（不想要了、约不成、商品有问题、卖家不卖了等）<br>3. 系统判断订单当前状态<br>4. **未支付** → 订单置「已取消」，商品回到「在售」（若商品已下架则保持「已下架」），通知对方<br>5. **已支付** → 系统通知对方确认取消<br>6. 对方同意 → 订单进入「退款中」，双方线下退回货款<br>7. 收款方在系统内标记「已退回」，发起方确认收到<br>8. 订单变为「已退款」，商品回到「在售」（若已下架则保持「已下架」），系统通知双方 |
| 辅事件流 | A. 对方拒绝取消 → **订单状态保持原状**并通知发起方，发起方可上报管理员（UC-15）<br>B. 已支付后对方超时未回应（超过 BR 时限）→ 系统提醒，**订单保持原状态**；仍无回应可上报管理员（UC-15）<br>C. 商品已交付但买家未确认收货 → **不支持单方取消**；双方协商一致的可按本用例取消（需对方同意），否则上报管理员（UC-15）<br>D. 订单已「已完成」→ 不允许取消，只能上报管理员（UC-15），**订单保持「已完成」**<br>E. 一方已提交评价 → 不允许取消，**订单状态保持原状**<br>F. 因买家超时未付款由系统自动取消的，不经过本用例（见 UC-07 辅事件流 C / BR-03）<br>G. 无正当理由频繁取消 → 按 BR 扣减信用分（UC-16）<br>H. 商品处于「已下架」→ 订单可取消，但商品**保持「已下架」**，不回「在售」（下架原因为违规处置的，由 UC-15 决定是否恢复）<br>I. 对方同意取消但超过 BR 时限仍未标记「已退回」→ 系统提醒收款方，**订单保持「退款中」**；发起方可上报管理员（UC-15） |
| 后置条件 | 订单为「已取消」或「已退款」；商品回到「在售」，若商品处于「已下架」则保持「已下架」；双方收到通知；取消记录留档 |
| 发生频率 | 上课日 9:00–23:00 约 20 次/天，开学季上升 |
| 关联 | UC-07、UC-08、UC-09、UC-15、UC-16、UC-21、BR-03、BR-待定（退款口径、违约扣分）、ST（待支付 → 已取消；已支付/待交付/待确认 → 退款中 → 已退款） |

## 附录 C：前后置咬合链

主链：下单「已预订 + 待支付」→ 支付「待支付」→ 支付后置「已支付」→ 交付（UC-08 / UC-09）前置「已支付」→ 交付后置「待交付」→ 线下交接后「待确认」→ 确认收货前置「待确认」→ 后置「已完成 + 已售出」→ 评价前置「已完成」→ 反馈信用分（UC-16）。

取消分支（UC-20）：待支付 / 已支付 / 待交付 / 待确认 任一状态 → 已支付及以后需对方同意 → 退款中 → 已退款（或已取消），商品回到「在售」；若商品处于「已下架」，则保持「已下架」，不回「在售」。已「已完成」状态不可取消，只能上报管理员（UC-15）。

入口链：UC-21（我的订单）是支付、取消、确认收货、评价的入口；UC-22（我的商品）是下架、修改重提、申诉的入口；UC-23（消息）是通知落地处。

流转链：捐赠 UC-17「待领取」→ 领取 UC-24「已转交」（超期 → 「已取消」）；借用 UC-19「申请中」→「借用中」→ 归还 UC-25「已归还」（超期 → 「逾期」→「已归还」）；发布可借物品走 UC-02（出借类型），不在 UC-19 里重复。
