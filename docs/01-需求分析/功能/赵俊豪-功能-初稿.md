## 〇、编写口径（先看这一节，方便合稿检查）

| 项目 | 约定 |
|---|---|
| 参与者 | 用例图里只有两个参与者：**学生**、**管理员**。买家、卖家、捐赠者、出借人都是「学生」这个参与者在不同用例中的角色，**不单独画小人** |
| 参与者写法 | 「学生（买家）」「学生（卖家）」表示角色；一条用例需要两方时，写「主要：学生（买家）；次要：学生（卖家）」 |
| 商品状态 | 待审核 / 在售 / 已预订 / 已售出 / 未通过 / 已下架（卖家主动）/ 强制下架（管理员） |
| 物品流转状态 | 捐赠：待领取 / 已预约 / 已转交；借用：借用中 / 已归还 / 逾期。**这两组与商品状态机分开**——捐赠品和出借品不走"在售→已预订→已售出"那条链，需另出一张流转状态图 |
| 订单状态 | 待支付 / 待卖家确认收款 / 已支付 / 待交付 / 已完成 / 退款中 / 已退款 / 已取消 |
| 编号引用 | 全文共用 `UC` `BR` `ST` `SC` `NFR` `V` 一套编号。本稿凡写「BR-待定」「ST-待定」处，需与吕锦浩、马歆远的表对齐后回填 |
| 通知怎么写 | 拆成两件事：**用户查看消息 = 用例 UC-23**；**系统主动发通知 = 功能需求条目 FR-01，不画成用例**（用例必须由参与者发起，通知是系统主动发起的） |
| 新增编号说明 | 本稿新用了 `FR-01`（功能需求条目）。共用编号里原本没有 FR 前缀，若组长不同意另起，就并入 BR 或 NFR 体系，编号待定 |
| 粒度 | 只写用户看得见的行为，不写系统内部实现（不用"加密""缓存""接口"这类说法） |
| 一件功能一件事 | 发现一条里塞了两个动作就拆开；本稿已按此检查过 |

**相对原 19 条清单的改动**（均已写进下面的正文）：

1. **UC-14 由「下架商品（管理员）」改为「下架自己的商品（卖家）」** —— 原清单漏了卖家撤下自己商品这个用户行为。
2. **UC-15 扩为「处理举报、申诉与违规处置」** —— 承接原来挂在 UC-14 上的管理员强制下架能力（否则「没人举报的违规商品」将没有任何功能可以处置），并补上申诉的受理与复核（否则 UC-13 的"误判申诉"、UC-16 的"扣分申诉"、UC-20 的"取消纠纷"、UC-22 的"强制下架申诉"都没有承接）。
3. **UC-07 增加中间状态「待卖家确认收款」** —— 修正原稿"已支付"与辅流"保持待支付"的矛盾；UC-08 辅流 C 改为「到场一方在系统内上报未到场」（系统无法自行感知线下到场）。
4. **新增 UC-20 取消订单** —— UC-07、UC-08、UC-09 三条辅事件流都在调用"取消订单"，原清单里却没有这条功能，是全稿最大的一处断链。**退款不单列为用例**，它是取消订单的一个场景（已付款后取消 = 需退款），订单状态机增加「退款中 / 已退款」。
5. **新增 UC-21 查看我的订单、UC-22 查看我的商品** —— 取消、退款、确认收货、评价、下架都要从这两个列表进入，没有入口，上面这些功能实际上没法用。
6. **新增 UC-23 查看消息通知**，并把「系统主动发通知」写成需求条目 **FR-01** —— 发通知由系统发起，不是用例。
7. **拆分 UC-17 与 UC-19**（原来这两条各塞了多个参与者的动作，违反"一件功能一件事"）：UC-17 只保留"提交捐赠 + 管理员接收登记"，领取部分拆为 **UC-24 领取捐赠物品**；UC-19 改为「申请借用」，归还部分拆为 **UC-25 归还借用物品**；"发布可借物品"并入 UC-02（发布时增加"出借"类型）。原有编号一律不动。

## 二、原有 19 条功能说明（UC-01 ~ UC-19）

### UC-01 学号实名认证

| 字段 | 内容 |
|---|---|
| 参与者 | 学生 |
| 目标 | 确认使用者是在校学生，取得平台交易资格 |
| 前置条件 | 已注册并登录账号 |
| 触发条件 | 学生首次使用发布/下单/评价等交易功能时点击「去认证」，或在「我的」页主动认证 |
| 主事件流 | 1. 学生进入实名认证页<br>2. 填写真实姓名、学号，选择院系与年级<br>3. 提交，系统与学校学籍数据比对<br>4. 校验通过，账号标记为「已实名」并回显认证信息 |
| 辅事件流 | A. 姓名与学号不匹配 → 提示「信息校验未通过，请核对后重试」，认证不通过<br>B. 该学号已被其他账号认证 → 提示「该学号已被使用」，引导提交**身份申诉**由管理员人工核验（与 UC-15 的处置申诉不是一类）<br>C. 未实名用户尝试发布/下单/评价 → 拦截并提示「请先完成学号实名认证」（UC-02、UC-06、UC-11 引用此流）<br>D. 学生转专业或换院系 → 需重新提交认证（是否允许修改由 BR 定）<br>E. 学籍数据源不可用 → 提示「认证服务暂不可用，请稍后再试」，账号保持未实名 |
| 后置条件 | 账号状态为「已实名」，可进行交易；认证记录留档 |
| 发生频率 | 上课日 9:00–23:00 约 40 次/天，开学季 500 次/天以上 |
| 关联 | BR-待定（一学号一账号）、NFR（学籍校验响应时间、个人信息保护） |

### UC-02 发布二手物品

| 字段 | 内容 |
|---|---|
| 参与者 | 学生（卖家） |
| 目标 | 卖家把要卖的物品或要出借的物品挂到平台，审核通过后对外展示 |
| 前置条件 | 已登录、已实名；账号未被限制发布 |
| 触发条件 | 卖家在「我要卖」页点击「发布」 |
| 主事件流 | 1. 选择发布类型（出售 / 出借）<br>2. 填写标题、分类、价格或押金、成色、描述<br>3. 上传物品图片（1–9 张）<br>4. 选择可交付方式（见面交付 / 送到自提点）<br>5. 提交<br>6. 系统生成一条「待审核」商品，提示「等待管理员审核」 |
| 辅事件流 | A. 必填项缺失或价格非法（≤0、超过上限）→ 就地提示，不允许提交<br>B. 图片格式/大小不符，或图片含水印联系方式 → 提示重新上传（是否禁止联系方式由 BR 定）<br>C. 未实名 → 走 UC-01 辅事件流 C<br>D. 与已有商品高度重复（同图同描述）→ 提示「疑似重复发布」并转人工复核<br>E. 卖家在待审核期间想改 → 可撤回后重新提交（重新提交沿用原商品编号，是否计入发布次数由 BR 定）<br>F. 发布类型选了「出借」，但未填可借时段、押金或归还要求 → 提示补全后才能提交 |
| 后置条件 | 生成一条「待审核」商品；此时不对外展示 |
| 发生频率 | 上课日 9:00–23:00 约 260 次/天，开学季 800 次/天 |
| 关联 | BR-待定（价格上限、违禁品清单、图片张数）、ST（待审核 → 在售 / 未通过）、UC-14、UC-19、UC-22 |

### UC-03 搜索商品

| 字段 | 内容 |
|---|---|
| 参与者 | 学生 |
| 目标 | 快速找到想买的商品 |
| 前置条件 | 已登录（未登录能否浏览由 BR 定） |
| 触发条件 | 在首页搜索框输入关键词并搜索，或提交筛选条件 |
| 主事件流 | 1. 输入关键词，或选择筛选条件（分类、价格区间、成色、交付方式、排序）<br>2. 系统检索处于「在售」的商品<br>3. 返回结果列表（图片、标题、价格、成色、发布时间）<br>4. 学生点击进入商品详情页 |
| 辅事件流 | A. 无匹配结果 → 提示「没有找到相关商品」，推荐相邻分类或建议放宽筛选<br>B. 关键词为空 → 提示先输入关键词，不发起检索<br>C. 结果中混入已售出/已下架商品 → 不展示（展示策略由 BR 定）<br>D. 浏览期间商品被他人下单 → 详情页提示「该商品已被预订」，购买按钮置灰<br>E. 关键词为敏感词/违规内容 → 按 BR 过滤并提示 |
| 后置条件 | 无（只读操作） |
| 发生频率 | 上课日约 6000 次/天（人均约 15 次） |
| 关联 | BR-待定（只展示在售、排序规则） |

### UC-04 按分类浏览商品

| 字段 | 内容 |
|---|---|
| 参与者 | 学生 |
| 目标 | 按分类逐层浏览，发现想买的商品 |
| 前置条件 | 已登录 |
| 触发条件 | 在首页点击分类入口 |
| 主事件流 | 1. 系统展示一级分类列表<br>2. 学生选择分类（教材书籍、电子数码、生活用品、代步工具等）<br>3. 系统列出该分类下「在售」商品<br>4. 可继续下钻子分类或切换排序 |
| 辅事件流 | A. 该分类下无商品 → 展示「该分类暂无商品」，推荐相邻分类<br>B. 分类入口被管理员停用或合并 → 该入口不再展示<br>C. 分类与商品不符 → 学生可举报该商品（UC-12） |
| 后置条件 | 无（只读操作） |
| 发生频率 | 上课日约 3000 次/天 |
| 关联 | BR-待定（分类目录、只展示在售） |

### UC-05 收藏商品

| 字段 | 内容 |
|---|---|
| 参与者 | 学生 |
| 目标 | 把感兴趣的商品存起来，之后再决定是否购买 |
| 前置条件 | 已登录 |
| 触发条件 | 在商品详情页或列表页点击「收藏」 |
| 主事件流 | 1. 点击「收藏」<br>2. 系统把商品加入个人收藏夹并提示「已收藏」<br>3. 学生可在「我的收藏」查看、取消收藏、进入商品详情 |
| 辅事件流 | A. 重复收藏 → 提示「已收藏」，不重复记录<br>B. 收藏后商品被卖出或下架 → 收藏列表中标记「已失效」，不可下单<br>C. 未登录点击收藏 → 引导登录<br>D. 收藏数量达到上限 → 提示先清理收藏（上限由 BR 定） |
| 后置条件 | 收藏关系已记录 |
| 发生频率 | 上课日约 400 次/天 |
| 关联 | BR-待定（收藏上限） |

### UC-06 下单

| 字段 | 内容 |
|---|---|
| 参与者 | 学生（买家） |
| 目标 | 买家锁定想要的商品并生成订单 |
| 前置条件 | 已登录、已实名、商品处于「在售」、不是自己发布的 |
| 触发条件 | 买家在商品详情页点击「立即购买」 |
| 主事件流 | 1. 点击「立即购买」<br>2. 系统检查商品状态与买家资格<br>3. 选择交付方式（见面交付 / 送到自提点）<br>4. 确认订单信息并提交<br>5. 系统锁定商品并生成订单 |
| 辅事件流 | A. 商品已被别人预订 → 提示「该商品已被预订」，返回列表<br>B. 买家未实名 → 提示「请先完成实名认证」（UC-01 辅事件流 C）<br>C. 买家是自己 → 提示「不能购买自己发布的商品」<br>D. 买家已有一笔该商品的未完成订单 → 提示「你已有一笔该商品订单，请先处理」，可从 UC-21 进入处理<br>E. 提交瞬间商品被他人抢先 → 以先提交者为准，后者回到辅事件流 A<br>F. 买家选择的交付方式卖家未提供 → 该选项置灰不可选，只能选卖家声明过的交付方式 |
| 后置条件 | 商品变「已预订」；生成一条「待支付」订单，并记录交付方式 |
| 发生频率 | 上课日 9:00–23:00 约 200 次/天，开学季翻倍 |
| 关联 | BR-待定（下单资格、重复下单）、ST（在售 → 已预订；— → 待支付） |

### UC-07 完成支付

| 字段 | 内容 |
|---|---|
| 参与者 | 主要：学生（买家）；次要：学生（卖家） |
| 目标 | 买家把货款付给卖家，订单进入「已支付」状态 |
| 前置条件 | 订单已生成且处于「待支付」；买家已实名认证 |
| 触发条件 | 买家在订单页点击「去支付」 |
| 主事件流 | 1. 买家点击「去支付」<br>2. 系统展示卖家的收款方式（微信/支付宝收款码）<br>3. 买家在第三方平台完成转账<br>4. 买家回到系统点击「我已付款」<br>5. 订单进入「待卖家确认收款」，系统通知卖家核对到账<br>6. 卖家核对到账后点击「确认收款」<br>7. 系统把订单状态更新为「已支付」，并通知卖家可以交付 |
| 辅事件流 | A. 买家已标记付款但卖家未收到 → 卖家拒绝确认，订单退回「待支付」并通知买家<br>B. 买家转错金额或转错人 → 双方协商后取消该订单（UC-20）并重新下单支付（平台不介入资金，退款口径见 BR-待定）<br>C. 买家 24 小时内未点击「我已付款」→ 订单由系统自动取消，商品回到「在售」并通知双方（BR-03，编号待与吕锦浩对齐）。注意：这一条是系统行为，**不经过 UC-20**<br>D. 买家已付款但卖家超过 48 小时未确认 → 系统再次提醒卖家；仍不确认则允许买家取消订单（UC-20）或上报管理员（UC-15）<br>E. 支付期间卖家尝试下架商品 → 被拦截（见 UC-14 辅事件流 A） |
| 后置条件 | 订单状态为「已支付」；商品保持「已预订」；系统通知卖家可以交付 |
| 发生频率 | 上课日 9:00–23:00 约 170 次/天（约为下单量的 85%） |
| 关联 | BR-03（支付超时自动取消）、BR-待定（平台不介入资金/退款口径）、UC-20、ST（待支付 → 待卖家确认收款 → 已支付；待支付 → 已取消） |

### UC-08 约定见面交付

| 字段 | 内容 |
|---|---|
| 参与者 | 主要：学生（买家）；次要：学生（卖家） |
| 目标 | 买卖双方就见面交付的时间和地点达成一致，并留下记录 |
| 前置条件 | 订单已支付；买家下单时选择的交付方式是「见面交付」（本条只适用于订单，借用与归还只沿用同样的线下方式，不生成订单） |
| 触发条件 | 支付完成后系统提示填写见面安排，或双方在订单页点击「约见面」 |
| 主事件流 | 1. 买家填写建议的见面时间和校内地点<br>2. 提交后系统通知卖家<br>3. 卖家确认，或提出新的时间/地点<br>4. 双方达成一致后，系统记录并通知双方<br>5. 订单进入「待交付」 |

| 字段 | 内容 |
|---|---|

## 附录 C：前后置咬合链

主链：下单「已预订 + 待支付」→ 支付「待支付」→ 支付后置「已支付」→ 交付（UC-08 / UC-09）前置「已支付」→ 交付后置「待交付」→ 确认收货前置「待交付」→ 后置「已完成 + 已售出」→ 评价前置「已完成」→ 反馈信用分（UC-16）。

取消分支（UC-20）：待支付 / 待卖家确认收款 / 已支付 / 待交付 任一状态 → 已支付及以后需对方同意 → 退款中 → 已退款（或已取消），商品回到「在售」；若商品处于「已下架 / 强制下架」，则保持原下架状态，不回「在售」。已「已完成」状态不可取消，只能走举报（UC-12）。

入口链：UC-21（我的订单）是支付、取消、确认收货、评价、举报的入口；UC-22（我的商品）是下架、修改重提的入口；UC-23（消息）是通知落地处。

流转链：捐赠 UC-17「待领取」→ 领取 UC-24「已转交」；借用 UC-19「借用中」→ 归还 UC-25「已归还 / 逾期」；发布可借物品走 UC-02（出借类型），不在 UC-19 里重复。
