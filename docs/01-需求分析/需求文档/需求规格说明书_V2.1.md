# 1 业务目标

## 1.1 项目愿景

在校内建立一个**可信、便捷**的闲置物品交易平台，让学生手中闲置的教材、数码产品、生活用品，能够安全地在同校同学之间转手，减少资源浪费。

## 1.2 现状问题

| 编号 | 问题 | 具体表现 |
|---|---|---|
| P-01 | **信息分散** | 闲置信息散落在各类社交群与二手论坛，缺乏统一入口，商品是否还在售不透明 |
| P-02 | **信任缺失** | 交易双方互不了解身份，无法判断对方是否为同校学生，也无法评估历史交易表现 |
| P-03 | **违规无人管** | 违禁品、虚假描述商品缺乏审核与事后处置机制 |

> **P-03 说明**：V1.2.1 中的「流程无保障（交易全程无记录、交付与付款靠口头约定）」问题，在本版下线。平台只做**撮合与成交登记**，不介入资金与交付，因此不宣称解决该问题——这一点必须在答辩时讲清楚，不能把「不做的部分」说成「已解决」。

## 1.3 业务目标分解

| 编号 | 目标 | 达成方式 |
|---|---|---|
| **G-01** | 让交易可信 | 学生证人工核验准入 · 双向交易评价 · 信用分机制 · 违规商品举报与处置 |
| **G-02** | 让交易便捷 | 商品快速发布 · 关键词搜索与分类浏览 · **站内私信直接沟通** · 下单即成交流程最短 |
| **G-03** | 让闲置物品流转起来 | 通过校内学生之间的买卖，使闲置物品转手给有需要的同学 |

> 分解类型为**「与」分解（AND）**：三个子目标须同时满足，缺任一则总体目标不成立。

> ⚠️ **G-03 措辞变化（重要）**：V1.2.1 的 G-03 指「捐赠、回收、借用」三条非买卖路径，本版已删除，故 G-03 改为「通过买卖让闲置转手」。若评审问「为什么不做捐赠」，标准回答是：**学校不提供代收点、回收人员与仓库，捐赠与回收的实物归集环节不成立；平台的边界是不碰实物、不碰资金**。

## 1.4 主要成功指标

| 编号 | 指标 | 目标值 | 来源性质 | 确认状态 |
|---|---|---|---|---|
| M-01 | 完成学生证核验的学生数 | 首学期 1000 人 | 分析推导 | 待确认 |
| M-02 | 每月成交笔数 | 1000 笔 / 月 | 分析推导 | 待确认 |
| M-03 | 违规商品平均处置时长 | 24 小时内 | 分析推导 | 待确认 |

> **口径对齐说明**：M-02 的 1000 笔/月与 §3 中下单用例「约 50 次/天」（按 30 天约 1500 笔）同量级；M-01 的 1000 人与 §3 中注册「约 40 次/天」同量级。**指标与用例发生频率必须保持同一数量级**，这是 V1.2.1 存在的问题之一。

# 2 范围

## 2.1 系统边界声明

本平台是一套**校内专用**的二手交易系统。以下五条边界为本版**组内定案**，全文所有需求均以此为前提：

| 边界项 | 声明 |
|---|---|
| **资金** | **平台完全不涉及资金**。平台**不托管、不代收、不代付、不记录收款状态**，也不采集、不存储任何支付信息（支付密码、卡号、验证码、收款码一律不进入平台）。商品价格只是**标价展示**，用于成交金额留档 |
| **交付** | **平台不提供物流，也不做交付确认**。下单成交后，取货时间、地点、方式由买卖双方**在站内私信（UC-29）中约定**，平台记录沟通内容但**不记录交付事实**、不校验、不担保。因此「成交」只表示**下单成功**，不表示货物已交接 |
| **沟通** | **沟通只在站内进行**。平台**不展示、不转交买卖双方的手机号与宿舍地址**，双方通过**绑定具体商品的站内私信**联系（BR-20）。用户自行在消息正文中交换联系方式属个人行为，平台不校验、不担保 |
| **身份** | **平台自建账号体系**。学生以**邮箱**为唯一键、用**密码**注册与登录（**学号不参与登录**，避免他人抢注学号阻塞本人）；须**申报学号并上传学生证**，由管理员**人工核验**学籍，通过后才取得发布与下单资格、学号才与账号绑定。**平台不接入任何学校统一身份认证或学籍数据库接口** |
| **实物** | **平台无任何物理节点**。不设代收点、自提点、回收点、仓库，也不配备工作人员或回收人员。平台只承载**信息与记录**，实物全程在学生之间直接流转 |
| **售后** | **平台不介入纠纷的资金与实物处置**。成交后的质量问题、纠纷由双方自行协商；平台只处理**平台内的违规内容**（下架商品、限制账号、扣信用分） |

> 上述边界直接决定本版没有订单状态机（§7.1）：平台拿不到支付回调，也没有交付确认，任何「已支付 / 待交付 / 待确认 / 退款中」的状态都**无法被平台观测到**，写进需求就是无法实现的空条款。

## 2.2 目标范围

### 2.2.1 目标内

| 范围块 | 内容 |
|---|---|
| 身份 | 注册、登录、学生证上传与管理员人工核验 |
| 交易 | 商品发布、管理员审核、关键词搜索、分类浏览、收藏、下单成交 |
| 治理 | 违规商品举报、管理员巡查与处置、信用分、交易评价 |
| 支撑 | 我的订单、我的商品、消息通知、**站内私信（联系卖家 / 沟通）** |

### 2.2.2 目标外

| 不在范围内 | 原因 |
|---|---|
| 在线支付、平台代收代付、担保交易、资金池 | 需支付牌照与商户资质；且平台无支付回调，无法观测真实付款 |
| **支付状态与收款确认（标记已付款 / 确认收款）** | 平台不碰钱，无权也无能力判定「钱是否到账」，该状态无法被验证 |
| **交付流程与交付确认（约见面、交付记录、确认收货）** | 交付全程线下，平台无任何观测点；强行记录只能得到不可信的自述数据 |
| **订单取消、退款、退款中 / 已退款状态** | 依赖已付款事实，本版不存在付款事实，故无退款可退 |
| 物流配送、快递对接 | 交付全程线下完成 |
| 对接学校统一身份认证、学籍数据库 | 属学校信息化部门管辖的外部系统，需审批、注册应用与密钥，本项目不具备接入条件 |
| **捐赠、回收、借用三条物品流转路径** | **学校不提供代收点、回收人员与仓库**：捐赠需实物归集与保管，回收需接收方与处理渠道，两者都依赖平台不具备的物理节点；本期整体删除，不保留空壳 |
| 跨校交易 | 仅限本校学生 |
| 议价 / 竞价 | 平台不做议价，下单即以标价成交 |
| 商品推荐算法、广告位 | 非本期目标 |
| 账号注销 | 本期不做。账号只能被封禁或限制，不提供学生自助注销与物理删除 |
| 举报人对处置结果的申诉、卖家对下架的申诉 | 本期不做独立申诉流程。卖家可在**该商品的站内私信**中向管理员提出异议（BR-20），由管理员在处置队列中人工复核，不设申诉实体与申诉状态 |
| **语音 / 视频通话、图片与文件消息、群聊、消息撤回** | 站内私信本期**只支持纯文本单聊**，绑定单件商品：不做实时音视频、不传附件、不建群、不可撤回。理由是课程周期内先把「能联系上、有留痕」做扎实，不做通信产品 |
| **通讯录、加好友、跨商品的全局聊天** | 私信**必须绑定一件具体商品**，不做社交关系链，也不做独立聊天窗 |

## 2.4 需求优先级

> 按 Kano 三层划分，判据是**「缺失时平台还能不能用」**，不是「重不重要」。
> **基本需求**＝缺了就无法完成一笔交易或无法治理平台；**期望型需求**＝缺了平台仍可用，但用户明确期待、实现了明显提升满意度；**兴奋型需求**＝用户未预期、实现后显著提升信任。

| 优先级 | 判据 | 用例 | 业务规则 |
|---|---|---|---|
| **基本需求**（17 个用例 / 17 条规则） | 缺失则交易或治理**无法完成** | UC-01 注册与登录、UC-02 提交核验、UC-03 审核学生证、UC-04 管理员登录、UC-05 发布商品、UC-06 审核商品、UC-07 搜索商品、UC-08 分类浏览、UC-10 下单成交、UC-11 下架商品、UC-12 举报、UC-13 处理举报与处置、UC-16 我的订单、UC-17 我的商品、UC-18 消息通知、UC-29 联系卖家与沟通、UC-30 查看我的私信 | BR-01 核验准入、BR-02 在售上限、BR-03 发布待审核、BR-04 禁售与处置、BR-05 价格合法、BR-06 下单即成交、BR-07 平台不碰钱货、BR-09 下架权限、BR-10 封禁与联动、BR-11 搜索与收藏、BR-12 成交统计、BR-15 主动通知、BR-16 核验期限、BR-17 重提上限、BR-18 伪造处置、BR-19 认证与账号状态分离、BR-20 私信准入 |
| **期望型需求**（5 个用例 / 5 条规则） | 缺失仍可交易，但用户**明确期待** | UC-09 收藏商品、UC-14 评价交易、UC-15 查看信用分、UC-31 撤销成交、UC-32 编辑商品 | BR-08 评价规则、BR-13 信用分定义与阈值、BR-14 信用分变动、BR-21 成交撤销、BR-22 商品编辑与重审 |
| **兴奋型需求**（本期为空） | 用户未预期 | — | — |

**几点说明（答辩会被问）**

1. **为什么私信是「基本」而不是「期望」**：本版平台不展示、不转交任何手机号（BR-20、NFR-04），**私信是买卖双方唯一的沟通渠道**。缺了它，成交后无法约定取货，交易实际上走不完——所以是基本需求，不是锦上添花。
2. **为什么举报处置是「基本」而不是「期望」**：审核（UC-06）只能拦住发布前的问题，**上架后的违规只能靠举报 + 处置**。缺了它，§4.3 禁售清单对已上架商品完全失效。
3. **为什么撤销成交是「期望」而不是「基本」**：撤销缺失时交易仍能跑完（只是买家反悔时商品会锁死），所以按判据归期望型；但它**承担着"已售出可回退"这一风控职责**，实答应按基本需求的测试强度验收。
4. **为什么本期没有兴奋型条目**：这是**有意取舍**，不是遗漏。团队把预算放在把基本与期望型做扎实（含 §4.3 禁售清单、私信、撤销回滚三块硬骨头），不再叠加惊喜功能。
5. **最接近兴奋型的设计**是 **BR-21 的「免责判定」机制**——撤销后由对方判是否违约、7 天不表态默认计违约。用户不会预期到这种设计，但它把"取消"从自由行为变成有声誉成本的行为。该机制作为 BR-21 的一部分交付，不单列。

> **优先级与确认状态是两回事**：优先级回答「能不能砍」，确认状态回答「有没有人签字」。一条**基本需求**完全可能是**待确认**状态（例如 BR-16 的 7 天/24 小时阈值）——这不矛盾，走查时要分别标注。

### UC-02 提交学生证核验申请

| 字段 | 内容 |
|---|---|
| 参与者 | 主要：学生；次要：管理员（接收申请） |

| 参与者 | 管理员 |

### UC-06 审核商品

| 字段 | 内容 |
|---|---|
| 参与者 | 管理员 |
| 目标 | 在商品上架前把住准入关，拦住违规与信息不完整的商品 |
| 前置条件 | 管理员已登录；存在「待审核」商品 |
| 触发条件 | 管理员进入审核队列，或收到新发布提醒 |
| 主事件流 | 1. 系统按提交时间展示待审核商品队列<br>2. 管理员查看商品信息与图片，**逐项比对 §4.3 禁售品类清单（A1–E2，共 18 类）**<br>3. 管理员选择「通过」或「不通过」<br>4. 通过 → **商品变为「在售」**并对外展示，通知卖家<br>5. 不通过 → **商品变为「已下架」，下架原因记为「审核不通过」**，填写原因**并引用清单类目编号**（如「A1 管制刀具」），通知卖家 |
| 辅事件流 | A. 商品命中清单任一类别 → 商品「已下架（审核不通过）」，驳回原因**必须引用类目编号**，卖家可删除违规内容后重新提交（ST-08）<br>B. 队列积压超过 24 小时 → 系统提醒管理员，队列按等待时长排序，**商品保持「待审核」**<br>C. 管理员误判 → 卖家可联系管理员复核，复核通过按 ST-09 恢复为「在售」<br>D. 卖家在待审核期间撤回 → 商品转为「已下架（卖家撤回）」，从队列移除（ST-04）<br>E. 同一卖家连续多条待审 → 按发布顺序依次处理，不合并<br>F. **商品疑似违规但无法归入清单任何类目** → 管理员可驳回并标注「清单外待裁定」，同时提交组长复核（§4.3.2 第 5 条）；**不得长期以「其他违规」为名拒绝** |

| 发生频率 | 约 60 次/天（与发布量一致） |

### UC-12 举报违规商品或学生

| 字段 | 内容 |
|---|---|
| 参与者 | 学生 |
| 目标 | 把违规的商品、或交易对手的不当行为上报给管理员 |
| 前置条件 | 已登录、**已认证** |
| 触发条件 | 在**商品详情页**点击「举报」（举报商品），或在**成交详情页／私信会话页**点击「举报该用户」（举报学生） |
| 主事件流 | 1. 系统按入口确定 `被举报对象类型`：商品详情页 → `商品`；成交／私信页 → `学生`<br>2. 选择举报类型 —— 对象为 `商品` 时可选（违禁品 / 虚假描述 / 价格欺诈 / **站外导流** / 其他）；对象为 `学生` 时可选（**收款不履约** / 其他）<br>3. 填写说明，可选上传证据（截图、图片或私信记录）<br>4. 提交<br>5. 系统生成一条「待处理」举报，并提示处理时限（建议值，待确认：24 小时） |

| 发生频率 | 约 8 次/天（其中对学生的举报预计占少数） |
| 关联 | BR-04、BR-14；UC-13；ST-07、ST-13 |

> **为什么举报对象要扩展到「学生」**：收款不履约、失联、私下交易后反悔——这些是**人的行为**，不是商品的属性，用"举报商品"表达不了。若只能举报商品，买家在成交后被卖家跑路时**没有任何可用入口**，BR-21 里「提交交易争议由管理员核实」就成了一句空话。扩展后，「交易争议」这一救济路径才真正落地。

> **举报类型口径变更（V2.1）**：V2.0 的「联系方式引流」与新增的站内私信存在语义冲突——在本版里，双方在私信中互留电话是**正常履约**，不是违规。故该类型更名为**「站外导流」**，定义收窄为：*在商品描述或图片中发布与本次交易无关的联系方式或广告（加群、卖课、代购等），把流量引出平台*。**不包含**交易双方在私信内为完成取货而互留电话。

> **「违禁品」举报类型与审核清单的关系**：举报类型中的「违禁品」直接对应 **§4.3 禁售品类清单（A1–E2）**——举报人选「违禁品」后，管理员须按清单核实并判定具体类目编号，不得只写「违规」。清单以外的违规（虚假描述、价格欺诈、站外导流）走各自类型。

> **关联缺口说明**：BR-14 是信用分变动规则，本条举报本身不扣分；扣分只在 UC-13 处置成立并显式执行时发生（BR-14 ②）。此关联仅用于说明"举报成立可触发卖家信用分变动"这一链路。

### UC-13 处理举报与违规处置

| 字段 | 内容 |
|---|---|
| 参与者 | 管理员 |
| 目标 | 对举报以及巡查中发现的违规商品或违规学生作出处置，维持平台秩序 |
| 前置条件 | 管理员已登录；存在待处理举报（对象为商品或学生），或管理员在巡查中发现违规商品 |

| 辅事件流 | A. 举报不成立 → 标记「已驳回」并通知举报人，**商品状态保持原状**<br>B. 无人举报但管理员巡查发现违规 → 直接选择处置手段并记录原因，**下架执行角色记为管理员**（ST-07）<br>C. 被下架的卖家**在该商品的站内私信中**向管理员提出异议（BR-20：管理员仅可回复此类异议私信，不得主动发起）→ 管理员复核原处置依据，**复核不成立则维持「已下架」，复核通过则按 ST-09 恢复「在售」**；本期不设独立申诉流程与申诉状态（§2.2.2）<br>D. 同一商品被多次举报 → 合并到同一条处理记录，避免重复处置<br>E. 举报超过建议时限（24 小时）未处理 → 系统持续提醒管理员<br>F. 举报成立且商品**已被售出** → 仅**记录处置结论**、扣信用分、封禁账号；**商品状态保持「已售出」不变**——BR-09 禁止对已售出商品执行下架<br>G. **对象为学生且举报类型为 `收款不履约`，核实成立** → 记一条「经核实的交易争议」：卖家信用分 −10（按 BR-14 ② 的违规处置口径）、**应封禁账号**，并按 ST-13 下架其在售与待审商品；若该卖家此前已封禁，只补记争议与扣分，不重复封禁<br>H. **对象为学生的举报不成立** → 标记「已驳回」并通知举报人，**不产生任何处置记录、不扣分、不公开**；同时提示恶意举报可能被反向处置<br>I. **同一学生的多条举报** → 若均针对同一卖家且类型相同，合并到同一条处理记录，避免重复扣分（BR-14），ST-07 的入口状态也只有「在售」。已成交订单不因事后处置而回滚 |
| 后置条件 | 举报状态为「已处理」或「已驳回」；**对象为商品时**被处置商品为「已下架」（下架原因＝`管理员违规下架`）；**对象为学生且成立时**该学生 `被核实争议数` +1、按 BR-14 扣分、按需封禁并联动下架其在售商品；记录留档 |
| 发生频率 | 约 8 次/天（与举报量一致） |
| 关联 | BR-04、BR-09、BR-10、BR-14；ST-07、ST-09；UC-06、UC-10、UC-12、UC-15 |

> **处置手段口径统一**：V1.2.1 中 UC-15 的手段清单（警告 / 下架 / 限制发布 / 封禁）与术语表「处置」定义（强制下架 / 扣信用分 / 驳回举报）互不一致，且清单里**漏了扣信用分**，而 BR-21 又规定违规下架要扣 -10。本版在 UC-13 与附录 B 中使用**同一份五项清单**：警告、强制下架、限制发布、封禁账号、扣信用分。

### UC-31 撤销成交

| 字段 | 内容 |
|---|---|
| 参与者 | 主要：学生（买家或卖家，撤销方）；次要：学生（对方，负责免责判定） |

| 辅事件流 | A. 对方同意免责 → `已免责`，**撤销方不扣分**，仅保留撤销记录<br>B. 对方判定计违约 → `计违约`，撤销方 **−2** 并写信用记录<br>C. 对方 7 天内未表态 → **系统自动计违约**（自 `撤销时间` 起算满 168 小时，§4.1.1），撤销方 −2；**该判定只影响信用分，不回滚已生效的撤销**<br>D. 任一方在撤销前已提交评价 → 不允许撤销，提示「评价已提交，成交不可撤销」，状态不变<br>E. `成交状态` 已是「已撤销」→ 不允许重复撤销，提示「该成交已撤销」；**不重复产生免责判定，也不重复扣分**<br>F. 撤销时卖家账号已封禁 → `成交状态` 置「已撤销」，但**商品不回到「在售」**，转「已下架」（下架原因＝`撤销后不可交易`，ST-11）<br>G. 非当事人尝试撤销他人成交 → 拒绝，**成交记录与商品状态均不变**<br>H. **一方主张已实际交付或已付款** → **撤销仍生效、不回滚**；主张方应通过 **UC-12 举报该学生（类型 `收款不履约`）**，由 UC-13 核实私信与成交记录后处置，并在对方主页计入 `被核实争议数`；平台不冻结本次撤销（BR-21）<br>I. 撤销后原成交记录**保留为历史，不删除**（与 BR-07「成交只表示下单成功」一致） |
| 后置条件 | `成交状态` 为「已撤销」；`撤销免责判定` 为 `已免责` 或 `计违约`（7 天内可为 `待判定`）；商品回到「在售」（或按辅事件流 F 转「已下架」）；双方收到通知；撤销与判定记录留档 |
| 发生频率 | 约 15 次/天 |
| 关联 | BR-06、BR-07、BR-08、BR-14、BR-21；ST-05、ST-10；UC-10、UC-13、UC-16、UC-29 |

> **为什么必须补这一条**：V2.0～V2.1 早期把 `已售出` 定为**硬终态**（任何角色不可再变更），于是「买家下单后不来 / 反悔」这一最常见情形**没有出口**——商品被永久锁死，卖家无法重新上架，而 BR-07 只写「纠纷由双方自行协商」，协商不成即死局。UC-31 是「下单即成交」这个设计**必须自带的回滚路径**，不是功能扩张。
>
> **为什么不用「双方同意」**：早期版本要求对方同意才可撤销，会制造新的死锁——**对方拒绝或失联，商品就永久卡在「已售出」**，等于把刚打开的口子又锁回去。本版改为 **「行为不设闸、声誉记账」**：撤销**即时生效**，对方只能事后决定「这次撤销算不算违约」，7 天不表态默认算。这样既有成本约束（违约方 −2），又不会因为一方失联而卡死。
>
> **它不是订单状态机**：订单仍然没有「待支付 / 已支付 / 待交付 / 待确认 / 退款中 / 已退款」这些依赖站外支付与站外交付的状态；只有「`有效`／`已撤销`」与「撤销免责判定」两个标记。区别在于：前者要求平台观测它观测不到的东西，后者只要求平台记录**谁撤的、对方认不认**——那是平台能够确认的事实。

| 主事件流 | 1. 系统加载商品当前内容进入编辑页；**发布人、商品状态、下架原因、发布时间以只读展示，不可修改**<br>2. 卖家修改标题、描述、价格、成色、图片或分类<br>3. 提交，系统校验必填项、价格区间（BR-05）与图片数量 1～9 张<br>4. 校验通过后按商品当前状态分流：<br>　4a. **商品为「在售」** → 商品转为**「待审核」**（ST-12），立即从搜索与分类列表移除，刷新发布时间与审核排队时间<br>　4b. **商品为「待审核」** → 保持「待审核」，刷新发布时间与审核排队时间（24 小时审核时限重新起算）<br>5. 提示「修改已提交，需重新审核通过后才对外展示」，通知历史收藏过该商品的买家 |
| 辅事件流 | A. 必填项缺失、价格非法或图片不在 1～9 张 → 就地提示，**不保存修改，商品状态与原内容均不变**<br>B. 商品为「已售出」→ 拒绝编辑，提示「已售出商品不可修改」；**撤销成交回到「在售」后方可编辑**<br>C. 商品为「已下架」→ 不走本用例，按 UC-05 修改后重新提交（ST-08），能否重提受下架原因限制<br>D. 非本人商品 → 拒绝，**商品状态与原内容均不变**<br>E. 卖家账号已封禁 → 拒绝编辑（BR-10）<br>F. 卖家在「在售」商品被买家成交的同一时刻提交编辑 → 以服务端先成功者为准：成交先成功则商品已「已售出」，编辑按辅事件流 B 拒绝；编辑先成功则商品已回「待审核」，不再可被下单<br>G. 尝试修改发布人、商品状态、下架原因或发布时间 → 这些字段不可写，**修改被丢弃**，其余字段照常保存 |
| 后置条件 | 「在售」商品变为「待审核」；或「待审核」商品保持「待审核」并刷新排队时间；商品编号不变；编辑内容已保存 |
| 发生频率 | 约 30 次/天 |
| 关联 | BR-03、BR-05、BR-22；ST-08、ST-12；UC-05、UC-06、UC-17 |

> **为什么在售编辑必须重审**：如果允许在售商品自由编辑，卖家可以**先发一件合规商品通过审核，再把它改成禁售品继续卖**——§4.3 的整个审核机制就被绕过了。因此本版定案：**「在售」商品任何编辑都回到「待审核」重审**（BR-22 ①）。代价是改个错别字也要重新排队，但这是审核可信的必要成本。
>
> **注意与「已下架」编辑的区别**：已下架商品走 **ST-08**（重新提交，可沿用原编号，但能否重提受下架原因限制）；在售商品走 **ST-12**（先降级为待审核）。两者都不新增商品编号。

| 字段 | 内容 |
|---|---|
| 参与者 | 学生（本人或他人） |
| 目标 | 查看某位学生的公开信任信息，判断是否值得与其交易 |

| 发生频率 | 约 200 次/天 |
| 关联 | BR-10、BR-11、BR-13、BR-14；§6.5；NFR-04；UC-11、UC-14、UC-15、UC-29 |

> **为什么必须补这一条**：V2.1 早期有 4 处引用「主页」——UC-14「在对方主页与商品页展示评价」、UC-15「在他人主页查看对方信用分」、术语表 `被核实争议数`「公开显示在其主页」——**但既没有这个用例，也没有定义主页包含哪些字段**。补上后，这些引用才有落点，也才能回答「买家怎么在成交前判断卖家靠不靠谱」。

### UC-34 找回密码

| 字段 | 内容 |
|---|---|
| 参与者 | 学生 |
| 目标 | 在无法用密码登录时，通过邮箱验证码证明身份并重置登录密码 |
| 前置条件 | 已注册；**能访问注册时填写的邮箱** |
| 触发条件 | 登录页点击「忘记密码」，或由 UC-01 辅事件流 B 引导 |
| 主事件流 | 1. 学生输入注册邮箱并提交<br>2. 系统**无论该邮箱是否存在，均返回同一提示**「若该邮箱已注册，验证码已发送，请查收」（防账号枚举）；邮箱存在时发送 **6 位验证码（有效期 10 分钟，一次性）**<br>3. 学生填写验证码与新密码<br>4. 系统校验：验证码正确且未过期、新密码符合强度要求、**新密码不得与当前密码相同**<br>5. 重置密码（只存新哈希），**该账号的所有登录会话立即失效**<br>6. 向该邮箱发送「密码已重置」通知，并生成一条站内通知（消息类型＝`核验`） |
| 辅事件流 | A. **邮箱不存在** → 仍返回统一提示，**不发送、不创建记录**，界面无任何差异（防枚举，NFR-10）<br>B. 验证码错误或已过期 → 提示「验证码错误或已失效，请重新获取」，允许重试<br>C. **验证码累计错误 5 次** → 本次验证码作废，须重新获取<br>D. **验证码请求过于频繁** → 同一邮箱 60 秒内只允许 1 次、24 小时内最多 10 次，超出时提示等待<br>E. **新密码与当前密码相同** → 拒绝，提示「新密码不能与当前密码相同」<br>F. 新密码强度不足 → 就地提示，**不重置**<br>G. **账号已封禁** → **仍允许重置密码**（找回凭据不等于解封），但重置后登录仍被拒绝并说明封禁<br>H. 邮件发送失败 → 提示「验证码发送失败，请稍后重试」<br>I. **管理员账号不适用本用例** → 管理员账号由系统预置，密码重置须由系统维护方执行，界面提示联系维护方<br>J. 重置成功但学生未收到通知邮件 → 站内通知仍会送达，可在「消息」中查看 |
| 后置条件 | 密码已更新为新哈希；该账号所有会话失效；重置通知已发送（邮箱 + 站内） |
| 发生频率 | 约 5 次/天 |
| 关联 | NFR-05、NFR-10；UC-01 |

> **为什么必须补这一条**：V2.1 早期 UC-01 辅流 B 写着「引导**找回密码**」，但全文**没有任何找回密码的用例**——学生一旦忘记密码，账号就永久废掉，只能换邮箱重新注册再走一遍核验。这是与「交易争议」同类的悬空引用。
>
> **为什么用邮箱验证码而不是安全问题或密保手机**：邮箱是注册时的唯一标识且**已经过验证码验证**（UC-01），是唯一可用的可信回信道；安全问题可被社工，密保手机在注册时非必填。

| BR-20 | **私信范围与准入**：站内私信**必须绑定一件具体商品**，参与者仅限该商品的发布人、与该商品沟通过沟通过的已认证学生，以及（**仅当该商品下架原因为「管理员违规下架」时**）管理员。**只有已认证学生可发起私信**；同一（商品，双方）只存在一条会话，重复进入复用既有会话，不得新建第二条。**平台不展示、不转交、不代填买卖双方的手机号与宿舍地址**，一切沟通在站内进行；用户自行在消息正文中交换联系方式属个人行为，平台不校验、不担保。管理员**仅可回复**针对违规下架商品的异议私信，**不得主动发起私信**。私信仅支持纯文本，无附件、无撤回、无群聊 | 分析推导 | 团队已复核 |

| BR-21 | **成交撤销（单方即时生效 + 事后记账）**：任一方当事人**可单方撤销**，**不需要对方同意，且即时生效**——`成交状态` 由 `有效` 置 `已撤销`、商品由 `已售出` 回到 `在售`（ST-10），原成交记录**保留为历史、不删除**。撤销须满足：本人为当事人、`成交状态` 为 `有效`、商品为 `已售出`、**双方均未提交评价**。撤销成立时 `撤销免责判定` 置 `待判定`；**对方有 7 天**（自 `撤销时间` 起算，§4.1.1）选择「同意免责」或「计违约」，**7 天内未表态由系统自动置 `计违约`**。被判 `计违约` 时撤销方信用分 **−2**（BR-14 ④，每笔成交最多一次），`已免责` 则不扣分。**撤销一律不可回滚**；撤销后**不得再对该记录评价**，且该记录此后不再触发任何信用分变动（含 BR-14 ③ 的「7 天未评价 −1」）。**平台不判断交易是否已实际交付或已付款**——一方主张已履约的，应通过 **UC-12 提交「对象＝学生 · 类型＝`收款不履约`」的举报**（详见 UC-12 辅事件流 C 的受理条件），由 UC-13 核实私信与成交记录后处置（计入对方的 `被核实争议数`）；平台不因此冻结或撤销本次撤销 | 分析推导 | 团队已复核 |
| BR-22 | **商品编辑与重审**：卖家可编辑**本人**商品的标题、描述、价格、成色、图片、分类；**发布人学号、商品状态、下架原因、发布时间为系统字段，卖家不得编辑**。编辑后按商品当前状态分流：①「**在售**」→ 商品回到「待审核」并**重新排队审核**（ST-12），编辑提交后立即从搜索与分类列表移除，直至重新通过；②「**待审核**」→ 保持「待审核」，刷新 `发布时间` 与审核排队时间（使 24 小时审核时限重新起算）；③「**已下架**」→ 按 ST-08 重新提交，能否重提仍受下架原因限制；④「**已售出**」→ **不可编辑**（含撤销后尚未重新上架期间，须先经撤销回到「在售」）。编辑内容须重新满足 BR-05 价格区间与图片 1～9 张；**编辑不得改变商品编号** | 分析推导 | 团队已复核 |

> **口径修正（重要）**：V1.2.1 中 BR-05 与 BR-21 **重复定义**了信用分初始值、范围与阈值，且措辞略有差异（「已发布和进行中的订单」vs「既有发布和订单」）。本版拆为 **BR-13（分值定义与阈值）+ BR-14（变动事件）**，两者不重叠，术语表只引用 BR-14。

### 4.1.1 时间期限的统一口径

> 适用于 BR-08（评价期 7 天）、BR-14（成交后 7 天）、BR-16（注册后 7 天、审核 24 小时）、BR-21（免责判定 7 天）及各条 NFR。

1. 文中所有「**N 天**」「**N 小时**」均指**自起算事件发生时点起算的连续时长**，**不按自然日 0 点切换**。7 天 = 168 小时，24 小时 = 24 小时。
2. **判定区间为左闭右开**：`起算时刻 ≤ t < 起算时刻 + N`。**恰好到达**「起算时刻 + N」的那一刻即视为**超期**。
3. 各期限的**起算事件**必须具名，不得含糊：

| 期限 | 起算事件 | 终止判定 |
|---|---|---|
| 评价资格 7 天 | 该成交记录的 `成交时间` | t ≥ 成交时间 + 168h 时不得再评价 |
| 未评价 −1 分 | 该成交记录的 `成交时间` | 满 168h 且该方未评价时扣分（已撤销记录不适用，BR-14） |
| 撤销免责判定 7 天 | 该成交记录的 `撤销时间` | t ≥ 撤销时间 + 168h 时系统**自动判 `计违约`** 并扣 2 分（BR-14 ④、UC-31 辅事件流 C） |
| 核验提交 7 天 | 学生账号的 `注册时间` | t ≥ 注册时间 + 168h 起每日提醒（AT-07） |
| 核验审核 24 小时 | 认证申请的 `提交时间` | t ≥ 提交时间 + 24h 起计入超时统计（AT-06） |
| 商品审核 / 举报处理 24 小时 | 商品的提交时刻 / 举报的 `举报时间` | 同左，仅提醒，不自动通过 |

4. 起算时刻与判定时刻**均以服务端时间为准**，不采信客户端时间；时间戳精度到秒。

### 4.3.2 判定口径（5 条，用于消除二义性）

1. **以物品主体判定，不以卖家声明的用途判定。** 主体本身即属禁售的直接拒绝；主体名义合法但**主要功能**指向违规用途的（如伪装成充电宝的偷拍设备），按实际功能判定为禁售。
2. **教材与教辅允许售卖**，但不得随附他人已填写的作业、实验报告或考试答案（D2）；**教材内印制的正常习题与答案不属于违规**，不得据此驳回。
3. **二手电子产品允许售卖**（手机、电脑、平板、相机、代步工具等），须同时满足：① 已清除个人数据并恢复出厂设置；② 不随附任何他人可登录的账号；③ 卖家在描述中说明来源与权属。涉嫌来路不明的，转管理员人工复核（UC-13 辅事件流 B），**不得仅凭「二手」二字驳回**。
4. **虚拟类商品一律禁止**（账号、卡券、优惠券、代练代刷、游戏币），因无法核验权属且违反第三方平台条款。
5. **清单为闭集，管理员不得自行扩容。** 遇到清单未覆盖但明显违规的物品，管理员可先行驳回并在原因中标注「清单外待裁定」，同时提交组长；组长裁定后**以新编号补入本表并升版本号**。**不得长期以「其他违规」为名默许清单外的拒绝**——那会让审核判据重新变成不可验收的形容词。

### 4.3.3 与状态机、举报的对应关系

| 场景 | 处理 | 对应转换 |
|---|---|---|
| 审核时命中清单 | 审核不通过，下架原因＝`审核不通过`，驳回原因引用类目编号 | ST-03 |
| 已上架商品被发现命中清单 | 管理员强制下架，下架原因＝`管理员违规下架`，卖家信用分 −10 | ST-07 |
| 卖家删除违规内容后重新提交 | 回到「待审核」 | ST-08（下架原因为 `审核不通过` 时可重提） |

> **可测试性说明**：每个类目都给了「典型物品」举例，审核走查时按清单**逐类目构造一个测试商品**（共 18 个），期望结果为全部驳回并记录正确类目编号。这是 BR-04 从形容词变成可验收需求的关键。

# 5 权限需求

## 5.1 角色及判定口径

游客为未登录访问者。学生账号的**认证状态**有四态：**未提交**（已注册、尚未提交核验申请）、**待审核**（已提交、管理员未出结论）、**已驳回**（未通过，可修改后重提）、**已认证**（核验通过）。另有一个**独立的账号状态**：**正常 / 受限 / 封禁**。管理员是独立管理角色，**不经过学生证核验**，也不把管理员自动视为已认证学生。

**权限矩阵按基础权限划分**：未提交、待审核、已驳回三态的**基础权限完全相同**（可浏览、可收藏，不可发布、下单、评价、举报），故在 §5.2 合并为「未认证学生」一列；三者只在**拒绝提示语**上有区别。**未认证学生可以收藏商品**，收藏不构成交易行为。

「允许」仅表示通过角色权限条件，仍需通过对象归属、数据可见范围与账号状态条件；「拒绝」表示基础角色无权。**认证状态与账号状态分开记录，互不替代**（BR-19）。

## 5.5 权限控制业务规则

1. **角色与对象校验**：每次实际操作都检查有效身份、角色、对象归属与字段可见范围。隐藏按钮只能辅助交互；直接指定他人编号、换入口或重复提交也必须受同样限制。默认不返回拒绝访问对象的手机号、地址、信用分明细或举报人身份。**私信还须校验「是否为该会话参与方」**：指定他人会话编号、猜测商品编号，均不得读到消息正文。
2. **权限拒绝不改变业务**：被拒绝时不创建商品、成交记录、评价、举报或信用记录，不变更商品状态与举报处理状态，不删除评价，不更新信用分；**不得因一次被拒绝操作扣信用分**。允许追加必要的安全审计记录。
3. **权限拒绝与状态拒绝区分**：角色无权时使用 §5.2 的提示语；角色有权但业务状态不满足时提示「当前业务状态不支持该操作」（如对已售出商品下单）。两类拒绝均保持操作前的业务数据与状态不变，审计原因分别记录。
4. **拒绝提示要准确**：未认证学生发布时提示完成核验（并区分未提交 / 待审核 / 已驳回），不能误报系统故障；管理员下单时提示角色无权，不能诱导管理员完成核验来绕过限制。
5. **必要审计**：记录权限拒绝、敏感个人信息读取与管理员审核 / 下架 / 删除 / 扣分等管理操作。审计至少含操作时间、操作者可得标识（游客使用会话标识）、有效角色、动作、目标可得标识、结果与原因类别；**不得写入登录密码、完整手机号、完整宿舍地址或学生证图片内容**。保留期限与审计访问权限待确认。
6. **登录失败是独立安全行为**：平台自建账号体系，登录失败计数与锁定由平台自行维护；连续失败 5 次锁定 15 分钟会改变计数与锁定截止时间。**不得顺带变更认证状态、商品状态、信用分或账号封禁状态**。
7. **并发操作一律「以服务端状态先到者为准」**：所有并发冲突按**谁先在服务端事务中成功，谁生效**处理；后到者按**业务状态拒绝**处理并提示当前状态，**不得两个都成功，也不得两个都失败**。具体覆盖：

| 并发对 | 判定 |
|---|---|
| 两人同时下单同一商品 | 先提交者成交；后提交者提示「该商品已售出」，不产生记录（ST-05、SC-03） |
| 买家下单 与 卖家主动下架 | 下单先成功则商品 `已售出`，卖家下架按 BR-09 拒绝（已售出不可下架）；下架先成功则商品 `已下架`，下单按「该商品不可购买」拒绝 |
| 卖家编辑在售商品 与 买家下单 | 下单先成功则商品 `已售出`，编辑按 UC-32 辅事件流 B 拒绝；编辑先成功则商品已回 `待审核`（ST-12），**不再可被下单**，下单按「该商品不可购买」拒绝 |
| 管理员封禁卖家 与 买家下单其商品 | 下单先成功则商品 `已售出`，封禁联动下架**不作用于已售出商品**（BR-09）；封禁先成功则商品已 `已下架`（ST-13），下单被拒 |
| 管理员封禁卖家 与 该卖家商品被撤销 | 先到者为准：撤销先成功且卖家已封禁 → 走 ST-11 转 `已下架（撤销后不可交易）`；封禁先成功则商品已 `已下架`，撤销仍可生效但**不再改变商品状态**（BR-21 只改成交标记） |
| 管理员审核通过 与 卖家撤回 | 两者都从 `待审核` 出发：先成功者决定结果（ST-02 或 ST-04），后到者按「当前业务状态不支持该操作」拒绝 |
| 两人同时接受同一举报 | 先处理者写入处理结果；后到者提示「该举报已被处理」，**不得重复扣分**（BR-14） |
| 双方同时撤销同一成交 | **先到者生效**：成交置 `已撤销`、商品回 `在售`；后到者提示「该成交已撤销」，**不重复撤销、不重复产生免责判定、不重复扣分**（BR-21、BR-14 ④） |
| 对方人工判定 与 7 天超时自动判定 | **先落库者为准**：人工判定先成功则采用其结论（`已免责` 或 `计违约`）；系统超时判定先成功则固定为 `计违约`。**`计违约` 的 −2 扣分每笔成交最多一次**，两条路径同时触发也只扣一次（BR-14 ④、UC-31 辅事件流 C） |
| 撤销 与 对方评价 | 评价先落库则撤销被拒（评价后不可撤销）；撤销先成立则评价被拒（BR-21、UC-31 辅事件流 D、E） |
| **两笔扣分同时作用于同一学生** | **必须累加，不得覆盖**：如同一卖家被两个举报分别判成立（各 −10），应得 −20 而非 −10。信用分更新一律用「原子增减 + 单条流水」，**禁止「读当前值→计算→写回」**（否则后写者覆盖先写者，即丢失更新） |
| **重复提交类幂等** | 同一动作重复提交只生效一次：下单（BR-06）、评价（BR-08）、举报（举报组合唯一）、核验申请（同一学生同时最多一条待审核）、收藏（组合唯一）、撤销、免责判定（BR-14 ④）——均以数据库唯一约束或事务内状态校验保证，**不依赖前端防抖** |

识别唯一有效成交记录的依据是商品状态「在售」与服务端事务，**不做客户端预占、不做分布式锁外的乐观判断**。
8. **处置的影响不混同于权限拒绝**：管理员下架、删除评价、扣分成功后的状态变化按 BR-04、BR-09、BR-14 执行；举报提交成功本身**不等于**违规已经成立，不得据此自动下架或扣分。

| 管理员审核「教材（含印制的习题答案）」 | **允许通过**（§4.3.2 判定口径第 2 条，正常答案不属 D2） | 商品转为「在售」 | 审核结果可追溯 |
| 信用分 55 的学生发布商品 | 信用分不足，暂不可发布新商品 | 不新增商品；信用分不变 | 业务状态拒绝 |
| 信用分 35 的学生下单 | 信用分不足，暂不可下单 | 不新增成交记录 | 业务状态拒绝 |
| 已认证学生下架他人商品 | 仅限本人发布的商品；权限拒绝 | 他人商品保持原状态 | 权限拒绝 |
| 已认证学生查看本人信用记录 | 允许，仅返回本人记录 | 不得读取他人记录 | 访问范围按权限判定 |
| 未认证学生查看消息通知 | 允许，仅返回当前账号通知 | 不得读取他人通知 | 访问结果可追溯 |
| 两名买家同时对同一在售商品下单 | 先提交者成功，后提交者提示「该商品已售出」 | 仅一条成交记录；商品「已售出」 | 并发只产生一次业务变动 |

# 6 数据需求

## 6.1 概念类图

> ⚠️ **图 6-1 待按 V2.1 重出**：旧图含「订单—交付方式」字段与物品流转相关结构，且不含私信、收藏、邮箱验证码，与本版冲突。本版共 **13 个实体类**：学生、认证申请、商品、分类、**收藏**、订单（成交记录）、评价、举报记录、信用记录、消息通知、私信、管理员、**邮箱验证码**。**本版以 §6.2 数据字典为准。**

关联要览（详见 §6.3）：学生 1—0..* 商品；学生 1—0..* 认证申请；管理员 0..1—1 认证申请（审核方）；学生 1—0..* 订单（作为买家）；学生 1—0..* 订单（作为卖家）；**商品 1—0..* 订单（其中「有效」最多 1 条）**；分类 1—0..* 商品；**学生 1—0..* 收藏；商品 1—0..* 收藏**；**订单 1—0..2 评价**；学生 1—0..* 评价（发出 / 收到）；学生 1—0..* 举报记录（提交）；商品 1—0..* 举报记录；管理员 0..1—1 举报记录（处理方）；学生 1—0..* 信用记录；订单 0..1—0..* 信用记录；学生 1—0..* 消息通知；**商品 1—0..* 私信；学生 1—0..* 私信（发送 / 接收）**。

> **两条约束必须记住**：① **一件商品同时最多一条「有效」成交记录**——`已售出` 期间不可再下单（BR-06）；但撤销后可重新成交，故同商品可有**多条历史成交记录**（BR-21）；② **一笔订单最多两条评价**（买卖双方各一条，BR-08）。这与 V1.2.1「同商品多笔历史订单」在字面上一致，但语义不同：V1.2.1 允许并行多笔，本版只允许**串行多笔、有效唯一**。
>
> **注意「会话」不是实体**：会话是**同一（商品，双方）下的私信行聚合**，由应用层聚合出列表、未读数与最后消息时间，不单独建表。见 §6.2.1「私信」的说明。

#### 订单（成交记录）

> **本实体只有一个两值标记，不是订单状态机。** 订单创建即成交，**不存在**「待支付 / 已支付 / 待交付 / 待确认 / 已完成 / 已取消 / 退款中 / 已退款」等任何依赖站外支付与站外交付的状态。唯一的 `成交状态` 只有 `有效`、`已撤销` 两个值，表达的是**「双方是否一致同意终止这笔成交」**——这是平台**能够确认的事实**，而不是平台无权观测的支付/交付事实（BR-21）。

| 字段名称 | 数据类型 | 业务含义 | 约束条件 | 是否必填 |
|---|---|---|---|---|
| 订单编号 | 文本 | 成交记录唯一标识 | 唯一、非空、由系统生成 | 是 |
| 商品编号 | 文本 | 本次成交涉及的商品 | 引用商品实体；**同一商品同时最多 1 条「有效」成交记录**（BR-06）；撤销后可再次成交，形成多条历史记录 | 是 |
| 买家学号 | 文本 | 下单成交的学生 | 引用学生实体；成交时应为已认证学生；**不得等于该商品的发布人学号**（BR-01） | 是 |
| 卖家学号 | 文本 | 该商品的发布人 | 冗余保存成交时的卖家，避免商品后续变更导致追溯失真 | 是 |
| 成交金额 | 数值 | 本次成交的金额 | **必须等于下单时商品的标价**（BR-05）；大于 0 且不超过 50000 元 | 是 |
| 成交时间 | 日期时间 | 订单创建与商品转为「已售出」的时刻 | 由系统记录；与商品状态更新为「已售出」在同一业务动作中完成（BR-06） | 是 |
| **成交状态** | 枚举 | 该笔成交是否仍有效 | 取值：`有效`、`已撤销`；**创建时恒为 `有效`**；任一方当事人**可单方**置为 `已撤销`（BR-21），**即时生效、不可回滚** | 是 |
| **撤销发起人学号** | 文本 | 单方发起撤销的一方 | 引用学生实体；须为该成交的买方或卖方；`已撤销` 时必填，`有效` 时为空 | 条件必填：已撤销时 |
| **撤销原因** | 文本 | 发起撤销时选择的原因 | 建议值，待确认：1～200 个字符；取值来自 UC-31 主事件流第 1 步的选项；`已撤销` 时必填 | 条件必填：已撤销时 |
| **撤销时间** | 日期时间 | 撤销生效的时刻 | 由系统记录；不早于 `成交时间`；**是「免责判定 7 天窗口」的起算点**（§4.1.1）；`已撤销` 时必填 | 条件必填：已撤销时 |
| **撤销免责判定** | 枚举 | 对方是否认可「本次撤销不构成违约」 | 取值：`待判定`、`已免责`、`计违约`；**仅 `已撤销` 时有效**（`有效` 时为空）；撤销成立时恒置 `待判定`，由对方判定或 7 天超时自动置 `计违约`（BR-21） | 条件必填：已撤销时 |
| **免责判定时间** | 日期时间 | 判定生效的时刻（人工判定或系统超时判定） | 由系统记录；`撤销免责判定` 为 `已免责` 或 `计违约` 时必填，`待判定` 时为空 | 条件必填：判定完成时 |

> **撤销的两个标记**：`成交状态` 决定「这笔成交还在不在」，`撤销免责判定` 决定「这次撤销要不要记账」。**撤销本身永远即时成立**——不存在"等对方同意"的中间态，因此也不会因为一方失联而卡住。对方能决定的**只是责任**，不是撤销能否生效（BR-21）。

| 成交状态 | 撤销免责判定 | 含义 |
|---|---|---|
| `有效` | **必须为空** | 正常成交，无撤销动作 |
| `已撤销` | `待判定` | 撤销已生效、商品已回到「在售」，**对方有 7 天时间决定是否计撤销方违约** |
| `已撤销` | `已免责` | 对方认可，撤销方**不扣分** |
| `已撤销` | `计违约` | 对方判定或 7 天未表态，撤销方**信用分 −2**（BR-14 ④） |

#### 私信

> **「会话」不是独立实体。** 会话是**同一（商品编号，双方学号有序对）下的私信行聚合**：会话列表、未读条数、最后一条消息时间均由应用层聚合得出，不单独建表。理由与参考实现一致——私信本身已是完整事实，多建一层会话表只会引入两份状态需要保持一致。因此本实体**没有状态字段**，每条消息只有「已读 / 未读」。

| 发送人学号 | 文本 | 消息发送方 | 引用学生或管理员实体；须为该商品会话的参与方；**发送人 ≠ 接收人**；学生发送人须为已认证 | 是 |
| 接收人学号 | 文本 | 消息接收方 | 引用学生或管理员实体；须为该商品会话的参与方；**接收人为管理员时，商品下架原因必须为 `管理员违规下架`**（BR-20） | 是 |
| 内容 | 文本 | 消息正文 | 建议值，待确认：1～500 个字符**纯文本**；不允许仅空白；不存附件、不存图片；不得写入日志 | 是 |

> **与 V2.0 的关系**：V2.0 没有任何沟通载体，导致成交后双方无法联系（见文档说明第 2 条）。本实体即为该缺口的最小补齐：**一个实体、七个个字段、不建会话表、不加状态机**。

| 订单—信用记录 | 订单 0..1；信用记录 0..* | 信用记录.关联订单编号 → 订单.订单编号 | 信用记录可无订单；每笔订单可被多条信用记录引用 |
| 学生—消息通知（接收） | 学生 1；消息通知 0..* | 消息通知.接收人学号 → 学生.学号 | 每条通知对应一名接收人；学生可收到多条通知 |
| 学生—邮箱验证码 | 学生 1；邮箱验证码 0..* | 邮箱验证码.邮箱 → 学生.邮箱 | 一名学生可产生多条验证码记录（注册、多次找回）；**验证码是临时安全记录，通过后作废，保留期建议 7 天**；邮箱不存在时也可能产生记录但**不得据此暴露账号是否存在**（NFR-10） |
| 商品—私信 | 商品 1；私信 0..* | 私信.商品编号 → 商品.商品编号 | 会话必须绑定具体商品（BR-20）；同一商品可有多个会话，各对应不同买家；商品状态变化不删除已产生的私信 |
| 学生—私信（发送） | 学生 1；私信 0..* | 私信.发送人学号 → 学生.学号 | 学生在该关系中扮演发送人；管理员作为发送人时仅限回复违规下架异议 |
| 学生—私信（接收） | 学生 1；私信 0..* | 私信.接收人学号 → 学生.学号 | 学生在该关系中扮演接收人；接收人须为该商品会话的参与方 |

## 6.4 关联字段与条件约束

- 一件商品关联一个发布学生和一个分类；一笔订单关联一名买家、一名卖家与一件商品。分类不再以枚举描述，统一用分类编号引用分类实体。
- 评价关联评价人、被评价人与一笔订单。订单一方是买家，另一方是卖家；「仅交易双方互评、成交后可评、每人每单一次、7 天内」由 BR-08 定案，此处的一致性条件为：评价人学号 ≠ 被评价人学号，且二者须分别等于该订单的买家学号与卖家学号。
- 举报学生学号必填，举报人只能是已认证学生；**举报对象为商品或学生，二者由 `被举报对象类型` 决定，对应编号字段恰好一个非空**。处理状态、处理结果、处理人与处理时间须相互一致：`待处理` 时三者为空，`已处理` 或 `已驳回` 时三者必填。
- 一名学生有零到多条信用记录，每条记录可选关联一笔订单。**信用分不以记录累加实时推导**，须存为学生实体上的当前值，并由 BR-14 的每次变动同时写一条信用记录。拒绝访问不产生信用扣分。
- 连续登录失败次数、锁定截止时间由平台自行维护，只约束登录，**不等同于封禁账号，也不改变认证状态**。
- **学生证图片属敏感个人信息**，仅审核职责内的管理员在核验时读取；不随公开商品、评价、订单或消息通知暴露，不进入日志、导出与审计正文（NFR-08）。登录密码只存不可逆哈希，学生与管理员各自独立。
- **账号状态与认证状态分开记录**（BR-19）：封禁不撤销认证，认证通过不解封。
- **收藏的一致性条件**：① `(学生学号, 商品编号)` **组合唯一**，重复收藏不新增记录；② 同一学生收藏数**上限 100 件**；③ 收藏**不锁定商品**，不参与任何商品状态流转；④ 商品转为 `已售出`／`已下架`／`已删除` 时**不级联删除收藏记录**，收藏列表按商品实际状态显示「已失效」（BR-11）。
- **私信的一致性条件**：① `私信.商品编号` 必填且必须指向存在的商品；② 发送人与接收人**都必须是该商品会话的参与方**，且发送人 ≠ 接收人；③ 同一（商品编号，双方学号有序对）下的消息构成一个会话，**会话不单独建表**；④ 学生作为发送人时须为已认证，接收人为管理员时该商品下架原因必须为 `管理员违规下架`（BR-20）；⑤ 商品被封禁处置后，私信记录保留可读，不级联删除。

### 6.4.1 状态联动数据约束

下单成交时，`订单` 记录的创建与 `商品.商品状态` 由「在售」改为「已售出」必须在同一事务中成功，失败则整体回滚，不得留下「有成交记录但商品仍在售」或「商品已售出但无成交记录」的半成品（BR-06）。

商品进入「已下架」时必须同时写入 `商品.下架原因`；进入「已售出」或「待审核」时不得有下架原因。**五种下架原因与 §7.2／§7.4.1 的转换一一对应**：`审核不通过`→ST-03、`卖家撤回`→ST-04、`卖家主动下架`→ST-06、`管理员违规下架`→ST-07／ST-13、`撤销后不可交易`→ST-11，**不允许出现转换表以外的原因取值**。其中 `撤销后不可交易` 只能由 ST-11 产生，且该原因为「已下架」时**不允许走 ST-08 重新提交**（须先由管理员解除账号封禁）。

信用分变动须同时写入 `学生.信用分` 的新值与 `信用记录` 的一条流水，两者不得分离（BR-14）。

**成交撤销须原子完成**：`订单.成交状态` 由 `有效` 改为 `已撤销` 与 `商品.商品状态` 由「已售出」改为「在售」必须在同一事务中成功；失败则整体回滚，不得留下「成交已撤销但商品仍已售出」或「商品回到在售但成交记录仍有效」的半成品（BR-21、ST-10）。撤销时若卖家账号已封禁，则商品改为「已下架」并把 `下架原因` 写为 `撤销后不可交易`（UC-31 辅事件流 G），而非回到「在售」。

**撤销与免责判定的五条一致性约束**（违反即为数据缺陷）：
1. `成交状态` 为 `有效` 时，`撤销发起人学号`、`撤销原因`、`撤销时间`、`撤销免责判定`、`免责判定时间` **必须全部为空**。
2. `成交状态` 为 `已撤销` 时，前三者**必须非空**；`撤销免责判定` 必须非空，且为 `待判定` 时 `免责判定时间` 必须为空、为 `已免责` 或 `计违约` 时 `免责判定时间` 必须非空。
3. **每笔成交最多产生一次撤销与一次免责判定**（`已撤销` 不可回滚、不可重复撤销），因此 `计违约` 扣分**每笔成交最多发生一次**（BR-14 ④）。
4. **`撤销免责判定` 与信用记录双向绑定**：为 `计违约` 时，**必须且只能存在 1 条**变动值 `−2`、关联该 `订单编号`、原因为撤销违约的信用记录；为 `已免责` 或 `待判定` 时，**不得存在**该条记录。二者不一致即为数据缺陷。
5. **判定与扣分必须原子完成**：`撤销免责判定` 置 `计违约` 与写入 `学生.信用分` 新值、插入信用记录，必须在同一事务中成功；失败整体回滚，**不得出现「判了违约但没扣分」或「扣了分但判定仍是待判定」**（含人工判定与 7 天超时自动判定两条路径）。

**商品编辑（ST-12）后的字段一致性**：
- 进入 `待审核` 时必须**清空 `下架原因`**，且 `发布时间` 刷新为本次提交时刻（使 24 小时审核时限重新起算）。
- `商品编号`、`发布人学号` **在任何编辑路径下都不得改变**；卖家可写字段仅限标题、描述、价格、成色、图片、分类。
- 编辑提交后，该商品**不得再存在指向它的「有效」成交记录**（`在售`→`待审核` 前必须已无有效成交，否则 ST-12 不成立）。

**商品状态与成交记录的双向一致性约束**（每次状态变更后须校验，违反即为数据缺陷）：

| 商品状态 | 对成交记录的要求 |
|---|---|
| `在售` / `待审核` / `已下架` | 该商品**不得存在任何「有效」成交记录** |
| `已售出` | 必须**恰好存在 1 条「有效」成交记录**，且其 `商品编号` 指向该商品 |
| 任意状态 | 同一商品的「有效」成交记录数 **≤ 1**（BR-06） |

**账号状态与商品状态的联动**：卖家账号为 `封禁` 时，其名下商品**不得处于「在售」或「待审核」**。本条为一致性校验规则；封禁时如何把商品转为「已下架」属于处置策略，见 §5.5 与遗留待确认项。

**私信不参与任何状态联动**：发送或阅读私信**不改变**商品状态、成交记录、信用分或举报处理状态；已售出商品仍可继续沟通（UC-29），下架商品的私信保留可读（UC-30 辅事件流 B）。唯一跨对象约束是：`私信.接收人学号` 指向管理员时，该商品的下架原因必须是 `管理员违规下架`（BR-20）。

> **本版数据字典的完整性声明**：V1.2.1 中「交付记录」「取消申请与同意记录」「退款标记」「物品流转记录（捐赠/借用/回收）」「人工处置标记」等实体与字段，因对应流程已删除而在本版**一并删除**，不是遗漏。反之，旧版被状态表反复引用却始终缺失的 `账号状态`、`订单—商品`的成交记录、`举报类型` 枚举，本版已补齐。

# 7 状态需求

## 7.1 状态定义与总体说明

本版只有**两套状态**：商品状态（§7.2，四态）与认证状态（§7.3，四态），外加一个独立的**账号状态**（三态，不是状态机）。**订单没有状态**；**私信也没有状态**。

| 对象 | 状态 | 含义 |
|---|---|---|
| 商品 | 待审核 | 已提交，尚未审核通过，只对发布者与管理员可见 |
| 商品 | 在售 | 审核通过，可被下单 |
| 商品 | 已售出 | 已被买家下单成交；**默认终态，但可经双方同意撤销回到「在售」**（ST-10 / ST-11，BR-21）；除此之外任何角色不可下架或重新提交 |
| 商品 | 已下架 | 审核不通过、卖家撤回、卖家主动下架或管理员违规下架，不可下单；必须保存下架原因 |
| 认证状态 | 未提交 | 已注册，尚未提交学生证核验申请；可浏览，不可发布与交易 |
| 认证状态 | 待审核 | 已提交学生证，管理员尚未作出结论；可浏览，不可发布与交易 |
| 认证状态 | 已认证 | 管理员核验通过；可发布、下单、评价、举报 |
| 认证状态 | 已驳回 | 核验未通过，可修改后重新提交；可浏览，不可发布与交易 |
| 账号状态 | 正常 / 受限 / 封禁 | 独立的管控标记，由管理员处置设置；**不是状态机**，不随商品或认证状态联动（BR-19） |
| 订单 | **（无状态机，两个标记）** | 订单即成交记录，创建即成交。**不存在待支付、已支付、待交付、待确认、已完成、已取消、退款中、已退款等任何依赖站外支付与站外交付的状态**。标记一 `成交状态`（`有效`／`已撤销`）表达「这笔成交还在不在」，**单方即时生效**；标记二 `撤销免责判定`（`待判定`／`已免责`／`计违约`）表达「这次撤销算不算违约」，由对方 7 天内判定，超时默认计违约（BR-21） |
| **私信** | **（无状态机，仅已读／未读）** | 每条消息只有 `未读`／`已读` 两个标记，由接收人置读。**会话不建表、无状态、不可关闭、不可撤回**（BR-20）。发送与阅读不改变任何商品、订单、信用分与举报状态 |

> **这是本版与 V1.2.1 差异最大的地方。** 旧版有订单八状态机（SM-01）、商品五状态（含「已预订」）、三条物品流转状态机（SM-03）。本版：**订单状态机整体取消**；商品由五态减为四态（删除「已预订」，因为下单即成交，不存在「被占用但未成交」的中间态）；**物品流转状态机整体删除**。

> **为什么可以删掉「已预订」**：旧版「已预订」存在的理由是「商品被下单但交易未完成，需要锁定」。本版下单即成交，商品立刻就是「已售出」，不存在锁定等待期，因此该状态没有存在意义。并发抢购由 BR-06 的「在售→已售出 原子切换」保证，不需要中间态。

## 7.2 商品状态机（SM-01）

> ⚠️ **图 7-1 待按 V2.1 重出**（旧图仍为五状态且含「已预订」）。**以本节文字与 §7.4 转换表为准。**

**状态集合**：`待审核`、`在售`、`已售出`、`已下架`（4 态）。

**允许的转换**：

1. `待审核` → `在售`：管理员审核通过（ST-02）
2. `待审核` → `已下架`：管理员审核拒绝（ST-03），或卖家撤回（ST-04）
3. `在售` → `已售出`：买家下单成交（ST-05）
4. `在售` → `已下架`：卖家主动下架（ST-06），或管理员违规处置（ST-07）
5. `已下架` → `待审核`：卖家修改后重新提交（ST-08，下架原因不得为「管理员违规下架」或「撤销后不可交易」）
6. `已下架` → `在售`：管理员撤销违规处置（ST-09，仅限下架原因为「管理员违规下架」）
7. **`已售出` → `在售`：买卖双方同意撤销成交（ST-10，BR-21）；若撤销时卖家账号已封禁，则改为 `已售出` → `已下架`（ST-11，下架原因＝`撤销后不可交易`）**
8. **`在售` → `待审核`：卖家编辑商品内容（ST-12，BR-22）——编辑后须重新审核才可再次对外展示**
9. **`在售` / `待审核` → `已下架`：账号封禁联动（ST-13，BR-10）——执行封禁时，该卖家名下这两类商品一并下架**

**终态**：**本版没有绝对终态。** `已售出` 默认即最终结果，但保留**唯一一条出口**——经双方同意撤销可回到 `在售`（ST-10）或转 `已下架`（ST-11），**除此之外任何角色都不能下架或重新提交**；`已下架` 非终态（可回到 `待审核` 或 `在售`）。

> **为什么给 `已售出` 开口子**：V2.0 把 `已售出` 定为硬终态，导致「买家下单后不来 / 反悔」无出口，商品永久锁死。这条口子只对**双方合意**开放，不对单方开放——见 BR-21。

**初始状态**：恒为 `待审核`。

**不存在的转换**（出现即为缺陷）：`已售出` → 除 `在售`（仅 ST-10）、`已下架`（仅 ST-11）之外的任何状态；`已售出` → `待审核`；`已下架` → `已售出`；`待审核` → `已售出`。

## 7.3 学生认证状态（SM-02）

> 认证状态与商品状态**完全独立**：任何一次认证状态转换都**不改变**商品状态与信用分（BR-19）；扣信用分只能由 BR-14 规定的事件触发。

**状态集合**：`未提交`、`待审核`、`已认证`、`已驳回`（4 态）。

**允许的转换**（详见 §7.4.2）：

1. 无账号 → `未提交`：提交注册（AT-01）
2. `未提交` → `待审核`：提交学生证核验申请（AT-02）
3. `待审核` → `已认证`：管理员核验通过（AT-03）
4. `待审核` → `已驳回`：管理员核验驳回（AT-04）

# 8 质量需求

## 8.1 验收测试共同前提

以下测试方案均为**未来验收设计，不是已经执行的真实系统测试**。建议测试前提、取样数量与观察窗口均为团队提议，不视为已有业务事实。

性能共同前提建议（待确认）：使用拟验收版本和同一套事先登记的测试环境，记录客户端／服务环境配置、浏览器版本、校园网络条件、往返时延与可用带宽；建议受控网络往返时延 ≤ 50 毫秒、每客户端可用带宽 ≥ 10 Mbps。使用不含真实隐私的测试数据；图片建议每张 ≤ 500 KB。所有端到端时间均从**用户动作发起**计至**明确结果呈现**，不能只量内部处理时间。系统异常、超时及失败必须保留并单列，不得只对成功样本宣称整体达标。

> **本版删除 NFR-05「支付信息安全」的原始形态**：平台已确定不涉及任何资金与支付信息（BR-07），该指标转为 §2.1 的边界声明与 §5.5 的审计禁令，不再作为独立 NFR。V1.2.1 的 NFR-05 自相矛盾（正文说「原文未明确平台是否提供在线支付」，而边界声明已定案不接入），本版一并消解。

## 8.11 NFR-10 邮箱验证码安全

| 项目 | 内容 |
|---|---|
| 需求编号 | NFR-10 |
| 需求名称 | 邮箱验证码安全 |
| 需求描述与依据 | **本条为分析推导，待确认。** 邮箱验证码是「邮箱真实性」与「账号找回」的唯一凭据。若可枚举、可重放、可绕频控，等于**账号可被他人接管**——这比交易纠纷严重得多 |

| 验收方式 | 用两个测试邮箱分别走注册与找回；核对验证码长度／有效期／一次性；检索存储、日志、审计、导出确认无明文；连续请求触发 60 秒与 24 小时双重频控；连续错误 5 次验证作废；对不存在邮箱与存在邮箱各请求 20 次，比对提示文案与响应时间分布；重置密码后用旧会话请求受保护资源，确认已被拒绝 |

## 三、商品

| 术语 | 定义 |
|---|---|
| **商品** | 学生发布的一件待售二手物品，是平台的核心交易对象 |
| **分类** | 商品所属的类别，**用分类实体承载**，一件商品属于且仅属于 1 个分类；同一分类下可有 0..* 件商品。分类**不分层（单层）** |
| **商品状态** | 商品在其生命周期中所处的状态，共 **4 种**（见下） |
| **在售** | 商品已通过审核、未被成交，可被下单 |
| **在售上限** | 同一学号可同时处于「在售」状态的商品数量上限，数值见 BR-02（5 件） |
| **成色** | 商品新旧程度，封闭四值：全新、九成新、七成新、其他 |
| **下架原因** | 商品进入「已下架」的原因，**五值**：审核不通过、卖家撤回、卖家主动下架、管理员违规下架、撤销后不可交易（与 §6.4.1 的转换映射一一对应） |
| **编辑** | 卖家修改本人「待审核」或「在售」商品的标题、描述、价格、成色、图片、分类（BR-22、UC-32）。**「在售」商品编辑后必须回到「待审核」重审**（ST-12），防止"先过审再改成禁售品"绕过审核 |
| **浏览数** | 某件商品被查看的次数，非负整数、公开字段；统计口径与是否冗余存储于商品实体待确认（建议值） |
| **收藏** | 学生对某件商品表达的保留意向，**不锁定商品、不产生订单、不要求认证**（BR-11、UC-09） |
| **收藏上限** | 同一学生可同时保有的收藏记录数量上限，数值见 BR-11（建议值 100 件） |
| **已失效** | 收藏列表中商品已「已售出」或「已下架」时的展示标记；**收藏记录本身不删除**，只标记不可下单（BR-11） |

### 商品状态取值（4 种，三处必须一致）

| 状态 | 含义 | 可否下单 |
|---|---|---|
| `待审核` | 已发布但尚未通过管理员审核，仅发布者与管理员可见 | 否 |
| `在售` | 已通过审核，可被下单 | **是** |
| `已售出` | 已被买家下单成交；**默认终态，可经双方同意撤销回到「在售」**（ST-10 / ST-11） | 否 |
| `已下架` | 审核不通过、卖家撤回、卖家主动下架或被管理员违规下架 | 否 |

> **初始状态恒为 `待审核`。** 一件商品**同时最多拥有一条「有效」成交记录**（BR-06）；`已售出` 默认即最终结果，**唯一出口是双方同意撤销**（BR-21），撤销后可再次成交，形成多条历史成交记录。

## 四、交易与订单

| 术语 | 定义 |
|---|---|
| **订单** | **成交记录**。买家对一件商品下单成功时生成的记录。**订单没有状态机**，只有 `成交状态`（`有效`／`已撤销`）一个标记，表达双方是否一致同意终止（BR-21） |
| **成交** | 买家下单成功的那一刻。**「成交」只表示下单成功，不表示已付款或已交货**（BR-07） |
| **成交金额** | 订单记录的金额，**必须等于下单当时商品的标价**（BR-05） |
| **自购** | 买家下单自己发布的商品，**平台禁止**（BR-01） |
| **价格** | 商品的标价。平台不做议价，下单即以标价成交；合法区间为大于 0 且不超过 50000 元 |
| **有效成交记录** | 一件商品**同时最多 1 条**；由商品状态 `在售`→`已售出` 的原子切换保证唯一性（BR-06）。撤销后该记录转为「已撤销」，商品可再次成交，此时同商品存在多条**历史**记录但有效记录仍 ≤ 1（BR-21） |
| **成交状态** | 成交记录上的标记，取值 `有效`、`已撤销`。**不是订单状态机**——它只表达「这笔成交还在不在」，不涉及支付与交付事实（BR-21）。`已撤销` 由任一方**单方即时**置入 |
| **撤销免责判定** | 成交记录上的第二个标记，取值 `待判定`、`已免责`、`计违约`，表达「这次撤销算不算违约」。**只由撤销方的对方作出**，7 天内不表态由系统自动置 `计违约`；`计违约` 时撤销方 −2 分（BR-14 ④） |
| **撤销成交** | 任一方当事人单方终止一笔已成交的交易，`成交状态` 置 `已撤销`、商品由 `已售出` 回到 `在售`（ST-10）。**单方即可、即时生效，不需要对方同意**；对方只能在事后决定是否计其违约。任一方已评价后不得撤销（BR-21、UC-31） |
| **违约（撤销）** | 撤销成交后由对方判定或超时默认产生的一次责任认定，公开计入信用分变动。**不等同于举报成立的违规处置**，也不等同于封禁 |
| **历史订单** | 超过保留期或已结束的成交记录（`已完成`／`已撤销`）的状态称谓，仅本人可查，不参与统计与评价（UC-16 辅事件流 D/E） |
| **保留期** | 各类记录在正常业务视图中保留的时长：成交记录 3 年、消息通知 90 天、认证申请留存期限待确认（NFR-08）。**到期后转入历史或匿名化，不等于物理删除**（逐项值均为建议值，待确认） |
| **归档** | 记录超过保留期后移出正常业务视图、仍可本人查阅的处理方式；**与删除不同**，归档不销毁数据 |

> ⚠️ **本版不存在「交付」「见面交付」「交付确认」「确认收货」「交付记录」「取消订单」「退款」「退款中」「已退款」「标记已付款」「确认收款」等术语。** 出现即为残留，必须删除。理由见 §2.1 边界声明：平台既拿不到支付回调，也没有任何交付观测点，这些状态无法被验证，写进需求就是不可实现的空条款。

## 五、信用与评价

| 术语 | 定义 |
|---|---|
| **信用分** | 反映学生交易行为的分数，用于限制其发布与下单权限。初始值 100，取值范围 0~150（BR-13）。**变动事件与幅度见 BR-14**，不由本条定义 |
| **信用分阈值** | `信用分 < 60` → **禁止发布新商品**（已发布商品仍可交易到底）；`信用分 < 40` → **禁止下单**（已有成交记录不受影响） |
| **信用记录** | 信用分的一次变动流水，含变动值、原因、时间、关联订单编号。**每次变动必须留一条**，不可直接改分数 |
| **评价** | 成交后，买方与卖方可对对方作出的文字评价。**双向**、每方每单 1 次、**不可修改**、**只有文字不设星级** |
| **评价资格** | 为该笔成交的买方或卖方，且距成交不超过 7 天，且尚未评价过该订单（BR-08） |

## 六、治理

| 术语 | 定义 |
|---|---|
| **举报** | 已认证学生对**商品**或**学生**发起的违规申告。**对象为商品**时用于违规内容处置；**对象为学生**时仅限「与该学生的成交或沟通中发生的行为」，不得举报无关个人 |
| **举报类型** | 封闭**六值**：违禁品、虚假描述、价格欺诈、**站外导流**、**收款不履约**、其他。前四类只能用于**商品**举报，`收款不履约` 只能用于**学生**举报，`其他` 两者皆可。**「站外导流」**指在商品描述或图片中发布与本次交易无关的联系方式或广告（加群、卖课、代购），把流量引出平台；**不包含**交易双方在站内私信内为完成取货而互留电话（V2.1 由「联系方式引流」更名并收窄） |
| **收款不履约** | 举报类型之一，专指**成交后收款却不交货或失联**的行为。只能作为对**学生**的举报提交，且须与举报人存在过成交记录或私信会话（UC-12 辅事件流 C）——这是买家线下转账后被跑路时**唯一可用的救济入口** |
| **被核实争议数** | 某学生名下的「对人举报经核实成立」的累计次数，**公开显示**在其主页，供他人在成交前识别风险。**只显示计数，不公开具体争议内容与举报人**（§6.5、BR-04） |
| **审核** | 管理员对 `待审核` 商品做上架前准入判断，结论：通过 / 不通过 |
| **处置** | 管理员对违规作出的处理，**手段固定为五项**：警告、强制下架、限制发布、封禁账号、扣信用分 |
| **强制下架** | 管理员处置导致的商品下架，与卖家主动下架**执行角色不同**，在转换表中分两行记录（ST-06 / ST-07） |
| **禁售品类** | 不允许在平台发布的商品类别。**完整清单见 §4.3（A1–E2 共 18 类，闭集）**，是本项目审核用例的核心判据。管理员审核时须按类目编号判定并引用 |
| **排队时间** | 商品提交审核后进入队列的等待时长，由 `发布时间` 起算（§4.1.1）。**编辑或重新提交会刷新该起算点**，使 24 小时审核时限重新计时（BR-22） |
| **交易争议** | 撤销成交后一方主张「已实际交付或已付款」而提出的异议，**通过 UC-12 举报对方学生（类型=`收款不履约`）**，由 UC-13 核实处置并计入 `被核实争议数`（BR-21、BR-04）。平台不冻结已生效的撤销，也不追回货物或款项 |

## 七、沟通（站内私信与消息通知）

> ⚠️ **「消息通知」与「私信」是两个不同对象，不得混用。** 前者是系统单向推送，后者是用户双向对话。

| 术语 | 定义 |
|---|---|
| **私信** | 学生与学生（或与管理员，仅限处置异议）之间围绕**一件具体商品**的双向文字消息。**必须绑定商品**、**只有已认证学生可发起**、**纯文本**、**无附件、无撤回、无群聊**（BR-20） |
| **会话** | 同一（商品，双方）下的全部私信消息构成的对话。**会话不是实体，不单独建表、无状态、不可关闭**（§6.2.1、§7.1），由应用层聚合出列表、未读数与最后消息时间 |
| **未读数** | 某会话中**发给本人且未被本人阅读**的消息条数。以会话侧统计为准，与通知红点不一致时取会话侧（NFR-09） |
| **联系卖家** | 已认证学生在商品详情页发起与该商品发布人的会话的入口动作（UC-29）。**不是「查看手机号」**——平台不提供这一能力 |
| **消息通知** | 由**系统**在 BR-15 事件发生时推送给用户的**单向**消息，见 UC-18。与私信分属两个实体、两个用例 |
| **消息类型** | 消息通知的分类，封闭六值：核验、商品审核、成交、处置、信用、**私信**。其中 `私信` 类通知携带会话定位，点击后跳转到会话（UC-30） |
| **通知红点** | 导航栏上的未读提示，数值等于该用户全部未读消息通知数；**与私信会话的未读数相互独立**，不一致时私信以会话侧为准（NFR-09） |
