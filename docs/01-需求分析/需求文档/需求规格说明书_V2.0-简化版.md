# 1 业务目标

## 1.1 项目愿景

在校内建立一个**可信、便捷**的闲置物品交易平台，让学生手中闲置的教材、数码产品、生活用品，能够安全地在同校同学之间转手，减少资源浪费。

## 1.2 现状问题

| 编号 | 问题 | 具体表现 |
|---|---|---|
| P-01 | **信息分散** | 闲置信息散落在各类社交群与二手论坛，缺乏统一入口，商品是否还在售不透明 |
| P-02 | **信任缺失** | 交易双方互不了解身份，无法判断对方是否为同校学生，也无法评估历史交易表现 |
| P-03 | **违规无人管** | 违禁品、虚假描述商品缺乏审核与事后处置机制 |

> **P-03 说明**：V1.2.1 中的「流程无保障（交易全程无记录、交付与付款靠口头约定）」问题，在本版下线。平台只做**撮合与成交登记**，不介入资金与交付，因此不宣称解决该问题——这一点必须在答辩时讲清楚，不能把「不做的部分」说成「已解决」。

## 1.3 业务目标分解

| 编号 | 目标 | 达成方式 |
|---|---|---|
| **G-01** | 让交易可信 | 学生证人工核验准入 · 双向交易评价 · 信用分机制 · 违规商品举报与处置 |
| **G-02** | 让交易便捷 | 商品快速发布 · 关键词搜索与分类浏览 · 下单即成交流程最短 |
| **G-03** | 让闲置物品流转起来 | 通过校内学生之间的买卖，使闲置物品转手给有需要的同学 |

> 分解类型为**「与」分解（AND）**：三个子目标须同时满足，缺任一则总体目标不成立。

> ⚠️ **G-03 措辞变化（重要）**：V1.2.1 的 G-03 指「捐赠、回收、借用」三条非买卖路径，本版已删除，故 G-03 改为「通过买卖让闲置转手」。若评审问「为什么不做捐赠」，标准回答是：**学校不提供代收点、回收人员与仓库，捐赠与回收的实物归集环节不成立；平台的边界是不碰实物、不碰资金**。

## 1.4 主要成功指标

| 编号 | 指标 | 目标值 | 来源性质 | 确认状态 |
|---|---|---|---|---|
| M-01 | 完成学生证核验的学生数 | 首学期 1000 人 | 分析推导 | 待确认 |
| M-02 | 每月成交笔数 | 1000 笔 / 月 | 分析推导 | 待确认 |
| M-03 | 违规商品平均处置时长 | 24 小时内 | 分析推导 | 待确认 |

> **口径对齐说明**：M-02 的 1000 笔/月与 §3 中下单用例「约 50 次/天」（按 30 天约 1500 笔）同量级；M-01 的 1000 人与 §3 中注册「约 40 次/天」同量级。**指标与用例发生频率必须保持同一数量级**，这是 V1.2.1 存在的问题之一。

# 2 范围

## 2.1 系统边界声明

本平台是一套**校内专用**的二手交易系统。以下五条边界为本版**组内定案**，全文所有需求均以此为前提：

| 边界项 | 声明 |
|---|---|
| **资金** | **平台完全不涉及资金**。平台**不托管、不代收、不代付、不记录收款状态**，也不采集、不存储任何支付信息（支付密码、卡号、验证码、收款码一律不进入平台）。商品价格只是**标价展示**，用于成交金额留档 |
| **交付** | **平台不提供物流，也不做交付确认**。下单成交后，取货时间、地点、方式由买卖双方**线下自行约定**，平台不记录、不校验、不担保。因此「成交」只表示**下单成功**，不表示货物已交接 |
| **身份** | **平台自建账号体系**。学生以**学号**为唯一键、用**密码**注册与登录；须**上传学生证**，由管理员**人工核验**学籍，通过后才取得发布与下单资格。**平台不接入任何学校统一身份认证或学籍数据库接口** |
| **实物** | **平台无任何物理节点**。不设代收点、自提点、回收点、仓库，也不配备工作人员或回收人员。平台只承载**信息与记录**，实物全程在学生之间直接流转 |
| **售后** | **平台不介入纠纷的资金与实物处置**。成交后的质量问题、纠纷由双方自行协商；平台只处理**平台内的违规内容**（下架商品、限制账号、扣信用分） |

> 上述边界直接决定本版没有订单状态机（§7.1）：平台拿不到支付回调，也没有交付确认，任何「已支付 / 待交付 / 待确认 / 退款中」的状态都**无法被平台观测到**，写进需求就是无法实现的空条款。

## 2.2 目标范围

### 2.2.1 目标内

| 范围块 | 内容 |
|---|---|
| 身份 | 注册、登录、学生证上传与管理员人工核验 |
| 交易 | 商品发布、管理员审核、关键词搜索、分类浏览、收藏、下单成交 |
| 治理 | 违规商品举报、管理员巡查与处置、信用分、交易评价 |
| 支撑 | 我的订单、我的商品、消息通知 |

### 2.2.2 目标外

| 不在范围内 | 原因 |
|---|---|
| 在线支付、平台代收代付、担保交易、资金池 | 需支付牌照与商户资质；且平台无支付回调，无法观测真实付款 |
| **支付状态与收款确认（标记已付款 / 确认收款）** | 平台不碰钱，无权也无能力判定「钱是否到账」，该状态无法被验证 |
| **交付流程与交付确认（约见面、交付记录、确认收货）** | 交付全程线下，平台无任何观测点；强行记录只能得到不可信的自述数据 |
| **订单取消、退款、退款中 / 已退款状态** | 依赖已付款事实，本版不存在付款事实，故无退款可退 |
| 物流配送、快递对接 | 交付全程线下完成 |
| 对接学校统一身份认证、学籍数据库 | 属学校信息化部门管辖的外部系统，需审批、注册应用与密钥，本项目不具备接入条件 |
| **捐赠、回收、借用三条物品流转路径** | **学校不提供代收点、回收人员与仓库**：捐赠需实物归集与保管，回收需接收方与处理渠道，两者都依赖平台不具备的物理节点；本期整体删除，不保留空壳 |
| 跨校交易 | 仅限本校学生 |
| 议价 / 竞价 | 平台不做议价，下单即以标价成交 |
| 商品推荐算法、广告位 | 非本期目标 |
| 账号注销 | 本期不做。账号只能被封禁或限制，不提供学生自助注销与物理删除 |
| 举报人对处置结果的申诉、卖家对下架的申诉 | 本期不做独立申诉流程。卖家可在站内消息中向管理员提出异议，由管理员在处置队列中人工复核，不设申诉实体与申诉状态 |

### UC-01 注册与登录

| 字段 | 内容 |
|---|---|
| 参与者 | 学生 |
| 目标 | 建立平台账号并登录；登出后可再次登录 |
| 前置条件 | 无（本人为本校在读学生，持有效学生证） |
| 触发条件 | 学生点击「注册」或「登录」 |
| 主事件流 | 1. 学生点击「注册」，填写学号、昵称、手机号，设置登录密码<br>2. 提交前须勾选《用户协议》与《隐私政策》<br>3. 系统校验学号未被占用、密码符合强度要求，创建账号，**认证状态置「未提交」**，账号状态置「正常」<br>4. 系统提示「请上传学生证完成核验」，引导进入 UC-02<br>5. 学生登录：输入学号与密码，系统校验通过后建立会话，**按当前认证状态与账号状态授予对应权限** |
| 辅事件流 | A. 密码错误 → 提示「学号或密码不正确」，**不回显密码**；连续失败按 NFR-05 处理（连续 5 次锁定 15 分钟）<br>B. 学号已被注册 → 提示「该学号已注册」，引导联系管理员处理，**不创建第二个账号**（一学号一账号）<br>C. 账号已封禁 → 拒绝登录并说明「账号不可用」；账号受限 → 允许登录但提示受限原因<br>D. 未认证学生登录成功 → 允许登录与浏览，发布与下单在下单前被拦截（见 UC-05 辅事件流 C、UC-10 辅事件流 B） |
| 后置条件 | 账号已创建或会话已建立；认证状态不变 |
| 发生频率 | 注册约 40 次/天；登录约 800 次/天 |
| 关联 | BR-01、BR-16、BR-17、BR-19；NFR-05、NFR-08；UC-02；AT-01 |

> **与 V1.2.1 的差异**：原 UC-01 把「注册」与「提交学生证核验」写在同一用例里，又与 UC-26 重复描述提交核验流程，且两处对「重提上限」的表述不一致。本版拆为 UC-01（注册登录）+ UC-02（提交核验），**提交核验只在一处定义**。

### UC-02 提交学生证核验申请

| 字段 | 内容 |
|---|---|
| 参与者 | 主要：学生；次要：管理员（接收申请） |
| 目标 | 上传学生证，向平台申请取得发布与交易资格 |
| 前置条件 | 已注册并登录；认证状态为「未提交」或「已驳回」；核验重提次数未达上限（BR-17） |

### UC-10 下单成交

| 字段 | 内容 |
|---|---|
| 参与者 | 学生（买家） |

# 5 权限需求

## 5.1 角色及判定口径

游客为未登录访问者。学生账号的**认证状态**有四态：**未提交**（已注册、尚未提交核验申请）、**待审核**（已提交、管理员未出结论）、**已驳回**（未通过，可修改后重提）、**已认证**（核验通过）。另有一个**独立的账号状态**：**正常 / 受限 / 封禁**。管理员是独立管理角色，**不经过学生证核验**，也不把管理员自动视为已认证学生。

**权限矩阵按基础权限划分**：未提交、待审核、已驳回三态的**基础权限完全相同**（可浏览、可收藏，不可发布、下单、评价、举报），故在 §5.2 合并为「未认证学生」一列；三者只在**拒绝提示语**上有区别。**未认证学生可以收藏商品**，收藏不构成交易行为。

「允许」仅表示通过角色权限条件，仍需通过对象归属、数据可见范围与账号状态条件；「拒绝」表示基础角色无权。**认证状态与账号状态分开记录，互不替代**（BR-19）。

## 5.5 权限控制业务规则

1. **角色与对象校验**：每次实际操作都检查有效身份、角色、对象归属与字段可见范围。隐藏按钮只能辅助交互；直接指定他人编号、换入口或重复提交也必须受同样限制。默认不返回拒绝访问对象的手机号、地址、信用分明细或举报人身份。
2. **权限拒绝不改变业务**：被拒绝时不创建商品、成交记录、评价、举报或信用记录，不变更商品状态与举报处理状态，不删除评价，不更新信用分；**不得因一次被拒绝操作扣信用分**。允许追加必要的安全审计记录。
3. **权限拒绝与状态拒绝区分**：角色无权时使用 §5.2 的提示语；角色有权但业务状态不满足时提示「当前业务状态不支持该操作」（如对已售出商品下单）。两类拒绝均保持操作前的业务数据与状态不变，审计原因分别记录。
4. **拒绝提示要准确**：未认证学生发布时提示完成核验（并区分未提交 / 待审核 / 已驳回），不能误报系统故障；管理员下单时提示角色无权，不能诱导管理员完成核验来绕过限制。
5. **必要审计**：记录权限拒绝、敏感个人信息读取与管理员审核 / 下架 / 删除 / 扣分等管理操作。审计至少含操作时间、操作者可得标识（游客使用会话标识）、有效角色、动作、目标可得标识、结果与原因类别；**不得写入登录密码、完整手机号、完整宿舍地址或学生证图片内容**。保留期限与审计访问权限待确认。
6. **登录失败是独立安全行为**：平台自建账号体系，登录失败计数与锁定由平台自行维护；连续失败 5 次锁定 15 分钟会改变计数与锁定截止时间。**不得顺带变更认证状态、商品状态、信用分或账号封禁状态**。
7. **并发下单**：以服务端在提交执行时检查到的商品状态为准；若商品已被他人成交，则本次下单失败，不留下新成交记录或错误的商品状态（BR-06）。识别唯一有效成交记录的依据是商品状态「在售」与服务端事务，不做客户端预占。
8. **处置的影响不混同于权限拒绝**：管理员下架、删除评价、扣分成功后的状态变化按 BR-04、BR-09、BR-14 执行；举报提交成功本身**不等于**违规已经成立，不得据此自动下架或扣分。

## 6.4 关联字段与条件约束

- 一件商品关联一个发布学生和一个分类；一笔订单关联一名买家、一名卖家与一件商品。分类不再以枚举描述，统一用分类编号引用分类实体。
- 评价关联评价人、被评价人与一笔订单。订单一方是买家，另一方是卖家；「仅交易双方互评、成交后可评、每人每单一次、7 天内」由 BR-08 定案，此处的一致性条件为：评价人学号 ≠ 被评价人学号，且二者须分别等于该订单的买家学号与卖家学号。
- 举报学生学号必填，举报人只能是已认证学生；举报对象仅限商品。处理状态、处理结果、处理人与处理时间须相互一致：`待处理` 时三者为空，`已处理` 或 `已驳回` 时三者必填。
- 一名学生有零到多条信用记录，每条记录可选关联一笔订单。**信用分不以记录累加实时推导**，须存为学生实体上的当前值，并由 BR-14 的每次变动同时写一条信用记录。拒绝访问不产生信用扣分。
- 连续登录失败次数、锁定截止时间由平台自行维护，只约束登录，**不等同于封禁账号，也不改变认证状态**。
- **学生证图片属敏感个人信息**，仅审核职责内的管理员在核验时读取；不随公开商品、评价、订单或消息通知暴露，不进入日志、导出与审计正文（NFR-08）。登录密码只存不可逆哈希，学生与管理员各自独立。
- **账号状态与认证状态分开记录**（BR-19）：封禁不撤销认证，认证通过不解封。

### 6.4.1 状态联动数据约束

下单成交时，`订单` 记录的创建与 `商品.商品状态` 由「在售」改为「已售出」必须在同一事务中成功，失败则整体回滚，不得留下「有成交记录但商品仍在售」或「商品已售出但无成交记录」的半成品（BR-06）。

商品进入「已下架」时必须同时写入 `商品.下架原因`；进入「已售出」时不得有下架原因。审核、撤回、卖家主动下架、违规处置四种原因与 §7.2 的转换一一对应，不允许出现转换表以外的原因取值。

信用分变动须同时写入 `学生.信用分` 的新值与 `信用记录` 的一条流水，两者不得分离（BR-14）。

> **本版数据字典的完整性声明**：V1.2.1 中「交付记录」「取消申请与同意记录」「退款标记」「物品流转记录（捐赠/借用/回收）」「人工处置标记」等实体与字段，因对应流程已删除而在本版**一并删除**，不是遗漏。反之，旧版被状态表反复引用却始终缺失的 `账号状态`、`订单—商品`的成交记录、`举报类型` 枚举，本版已补齐。

# 7 状态需求

## 7.1 状态定义与总体说明

本版只有**两套状态**：商品状态（§7.2，四态）与认证状态（§7.3，四态），外加一个独立的**账号状态**（三态，不是状态机）。**订单没有状态**。

| 对象 | 状态 | 含义 |
|---|---|---|
| 商品 | 待审核 | 已提交，尚未审核通过，只对发布者与管理员可见 |
| 商品 | 在售 | 审核通过，可被下单 |
| 商品 | 已售出 | 已被买家下单成交，终态 |
| 商品 | 已下架 | 审核不通过、卖家撤回、卖家主动下架或管理员违规下架，不可下单；必须保存下架原因 |
| 认证状态 | 未提交 | 已注册，尚未提交学生证核验申请；可浏览，不可发布与交易 |
| 认证状态 | 待审核 | 已提交学生证，管理员尚未作出结论；可浏览，不可发布与交易 |
| 认证状态 | 已认证 | 管理员核验通过；可发布、下单、评价、举报 |
| 认证状态 | 已驳回 | 核验未通过，可修改后重新提交；可浏览，不可发布与交易 |
| 账号状态 | 正常 / 受限 / 封禁 | 独立的管控标记，由管理员处置设置；**不是状态机**，不随商品或认证状态联动（BR-19） |
| 订单 | **（无状态）** | 订单即成交记录，创建即终态。**不存在待支付、已支付、待交付、待确认、退款中、已退款、已取消等任何状态** |

> **这是本版与 V1.2.1 差异最大的地方。** 旧版有订单八状态机（SM-01）、商品五状态（含「已预订」）、三条物品流转状态机（SM-03）。本版：**订单状态机整体取消**；商品由五态减为四态（删除「已预订」，因为下单即成交，不存在「被占用但未成交」的中间态）；**物品流转状态机整体删除**。

> **为什么可以删掉「已预订」**：旧版「已预订」存在的理由是「商品被下单但交易未完成，需要锁定」。本版下单即成交，商品立刻就是「已售出」，不存在锁定等待期，因此该状态没有存在意义。并发抢购由 BR-06 的「在售→已售出 原子切换」保证，不需要中间态。

## 7.2 商品状态机（SM-01）

> ⚠️ **图 7-1 待按 V2.0 重出**（旧图仍为五状态且含「已预订」）。**以本节文字与 §7.4 转换表为准。**

**状态集合**：`待审核`、`在售`、`已售出`、`已下架`（4 态）。

**允许的转换**：

1. `待审核` → `在售`：管理员审核通过（ST-02）
2. `待审核` → `已下架`：管理员审核拒绝（ST-03），或卖家撤回（ST-04）
3. `在售` → `已售出`：买家下单成交（ST-05）
4. `在售` → `已下架`：卖家主动下架（ST-06），或管理员违规处置（ST-07）
5. `已下架` → `待审核`：卖家修改后重新提交（ST-08，下架原因不得为「管理员违规下架」）
6. `已下架` → `在售`：管理员撤销违规处置（ST-09，仅限下架原因为「管理员违规下架」）

**终态**：`已售出`（不可再出，任何角色都不能下架或重新提交）；`已下架` 非终态（可回到 `待审核` 或 `在售`）。

**初始状态**：恒为 `待审核`。

**不存在的转换**（出现即为缺陷）：`已售出` → 任何状态；`在售` → `待审核`；`已下架` → `已售出`。

## 7.3 学生认证状态（SM-02）

> 认证状态与商品状态**完全独立**：任何一次认证状态转换都**不改变**商品状态与信用分（BR-19）；扣信用分只能由 BR-14 规定的事件触发。

**状态集合**：`未提交`、`待审核`、`已认证`、`已驳回`（4 态）。

**允许的转换**（详见 §7.4.2）：

1. 无账号 → `未提交`：提交注册（AT-01）
2. `未提交` → `待审核`：提交学生证核验申请（AT-02）
3. `待审核` → `已认证`：管理员核验通过（AT-03）
4. `待审核` → `已驳回`：管理员核验驳回（AT-04）
5. `已驳回` → `待审核`：修改后重新提交（AT-05，重提未达 3 次）
6. `已认证` → `已驳回`：事后核实证件伪造（AT-08）

**状态保持**（不是转换）：AT-06（审核超 24 小时，**不得自动通过**）、AT-07（注册满 7 天未提交，**不得自动驳回或封禁**）。

> **覆盖度自查**：18 个用例中，SC-01 覆盖 UC-01/02/03/05/06/07/10/14/15，SC-02 覆盖权限面，SC-03 覆盖 UC-10 并发，SC-04 覆盖 UC-05/06，SC-05 覆盖 UC-12/13，SC-06 覆盖 UC-07/08/09/11/16/17/18，SC-07 覆盖 UC-14/15，SC-08 覆盖 UC-01/02/03。**UC-04（管理员登录）无独立场景**，由权限场景间接覆盖，走查时须单独确认。

# 8 质量需求

## 8.1 验收测试共同前提

以下测试方案均为**未来验收设计，不是已经执行的真实系统测试**。建议测试前提、取样数量与观察窗口均为团队提议，不视为已有业务事实。

性能共同前提建议（待确认）：使用拟验收版本和同一套事先登记的测试环境，记录客户端／服务环境配置、浏览器版本、校园网络条件、往返时延与可用带宽；建议受控网络往返时延 ≤ 50 毫秒、每客户端可用带宽 ≥ 10 Mbps。使用不含真实隐私的测试数据；图片建议每张 ≤ 500 KB。所有端到端时间均从**用户动作发起**计至**明确结果呈现**，不能只量内部处理时间。系统异常、超时及失败必须保留并单列，不得只对成功样本宣称整体达标。

> **本版删除 NFR-05「支付信息安全」的原始形态**：平台已确定不涉及任何资金与支付信息（BR-07），该指标转为 §2.1 的边界声明与 §5.5 的审计禁令，不再作为独立 NFR。V1.2.1 的 NFR-05 自相矛盾（正文说「原文未明确平台是否提供在线支付」，而边界声明已定案不接入），本版一并消解。

| 需求编号 | NFR-02 |

## 8.6 NFR-05 登录安全

| 项目 | 内容 |
|---|---|
| 需求编号 | NFR-05 |
| 需求名称 | 登录安全 |
| 需求描述与依据 | 原文要求：同一账号连续登录失败 5 次，锁定 15 分钟。学生与管理员账号均按「同一账号」计数；跨设备不能各自重新累计 |
| 测试前提／适用范围 | 使用专用测试账号，从未锁定、失败计数为 0 开始；计时以系统可核对的时间为准。建议值，待确认：失败定义为凭据校验失败；成功后计数清零；锁定到期清零；锁定期间再次尝试不延长既有锁定截止时间 |
| 量化指标与统计口径 | 第 1～4 次失败不触发锁定；第 5 次失败时记触发时刻 t，在 [t, t+15 分钟) 内即使凭据正确也不能新建登录会话。到达 t+15 分钟后允许重新验证凭据。提示「账号已暂时锁定，请稍后重试」，不回显密码；安全日志中的秘密出现数为 0 |
| 验收方式 | 依次验证 4 次失败、第 5 次失败、锁定期内正确凭据、临近 15 分钟与满 15 分钟后的正确凭据；跨设备复查。**登录保护可变更计数与锁定时间，但不得改变认证状态、商品状态、信用分或账号状态**（§5.5 第 6 条） |

## 8.7 NFR-06 新用户发布易用性

| 量化指标与统计口径 | 每位受试者在无他人代操作、无操作步骤提示的情况下 ≤ 5 分钟完成首次发布；不改成平均值。完成定义为**提交合法商品并收到成功反馈**，商品状态应为 `待审核`；不要求管理员已审核通过。建议样本 10 人全部成功 |

## 8.10 与数据及权限的对应

## 二、身份与认证

| 术语 | 定义 |
|---|---|
| **平台账号** | 平台**自建**的账号体系。学生以**学号**为唯一键注册，用**密码**登录。平台**不接入**任何学校认证或学籍数据库接口 |
| **注册** | 学生填写学号、昵称、手机号（可选）并设置登录密码，在平台建立账号的动作 |
| **学号** | 由学校分配的学生唯一标识，**同时作为平台登录账号**（一学号一账号） |
| **登录密码** | 学生或管理员进入平台的凭据。**只存不可逆哈希**，任何场景不得回显 |
| **学生证核验** | 学生上传学生证照片，由**管理员人工核对**证件姓名、学号与账号所填学号是否一致的过程。**核验通过是取得发布与交易资格的前提** |
| **认证状态** | 学生账号的核验状态，取值：`未提交`、`待审核`、`已认证`、`已驳回`（四态，见 §7.3） |
| **账号状态** | 独立于认证状态的管控标记，取值：`正常`、`受限`、`封禁`。**认证状态变化不改变账号状态，反之亦然**（BR-19）；**不是状态机** |
| **核验重提次数** | 学生累计重新提交核验的次数，上限 3 次（BR-17）。**存于学生实体，全生命周期累计** |
| **认证申请** | 一次学生证核验的提交记录，含证件图片、提交时间、审核状态、审核人、驳回原因 |
| **管理员账号** | 系统**预置**的后台账号，不开放注册、**不由学生账号升级**；与学生账号相互独立，须分别登录 |

> ⚠️ **自 v1.2 起不再使用「学校统一身份认证」方案。** 它需接入学校认证系统（需审批、注册应用、配置回调域名），课程项目不具备条件；且统一认证只核验学生身份，**无法覆盖管理员登录**。

## 三、商品

| 术语 | 定义 |
|---|---|
| **商品** | 学生发布的一件待售二手物品，是平台的核心交易对象 |
| **分类** | 商品所属的类别，**用分类实体承载**，一件商品属于且仅属于 1 个分类；同一分类下可有 0..* 件商品。分类**不分层（单层）** |
| **商品状态** | 商品在其生命周期中所处的状态，共 **4 种**（见下） |
| **在售** | 商品已通过审核、未被成交，可被下单 |
| **在售上限** | 同一学号可同时处于「在售」状态的商品数量上限，数值见 BR-02（5 件） |
| **成色** | 商品新旧程度，封闭四值：全新、九成新、七成新、其他 |
| **下架原因** | 商品进入「已下架」的原因，四值：审核不通过、卖家撤回、卖家主动下架、管理员违规下架 |

### 商品状态取值（4 种，三处必须一致）

| 状态 | 含义 | 可否下单 |
|---|---|---|
| `待审核` | 已发布但尚未通过管理员审核，仅发布者与管理员可见 | 否 |
| `在售` | 已通过审核，可被下单 | **是** |
| `已售出` | 已被买家下单成交，终态 | 否 |
| `已下架` | 审核不通过、卖家撤回、卖家主动下架或被管理员违规下架 | 否 |

> **初始状态恒为 `待审核`。** 一件商品**最多拥有一条成交记录**（BR-06）。`已售出` 为终态，任何角色都不可再变更。

## 四、交易与订单

| 术语 | 定义 |
|---|---|
| **订单** | **成交记录**。买家对一件商品下单成功时生成的唯一记录。**订单没有状态**，创建即终态，之后不再发生变化 |
| **成交** | 买家下单成功的那一刻。**「成交」只表示下单成功，不表示已付款或已交货**（BR-07） |
| **成交金额** | 订单记录的金额，**必须等于下单当时商品的标价**（BR-05） |
| **自购** | 买家下单自己发布的商品，**平台禁止**（BR-01） |
| **价格** | 商品的标价。平台不做议价，下单即以标价成交；合法区间为大于 0 且不超过 50000 元 |
| **有效成交记录** | 一件商品最多 1 条；由商品状态 `在售`→`已售出` 的原子切换保证唯一性（BR-06） |

> ⚠️ **本版不存在「交付」「见面交付」「交付确认」「确认收货」「交付记录」「取消订单」「退款」「退款中」「已退款」「标记已付款」「确认收款」等术语。** 出现即为残留，必须删除。理由见 §2.1 边界声明：平台既拿不到支付回调，也没有任何交付观测点，这些状态无法被验证，写进需求就是不可实现的空条款。

## 五、信用与评价

| 术语 | 定义 |
|---|---|
| **信用分** | 反映学生交易行为的分数，用于限制其发布与下单权限。初始值 100，取值范围 0~150（BR-13）。**变动事件与幅度见 BR-14**，不由本条定义 |
| **信用分阈值** | `信用分 < 60` → **禁止发布新商品**（已发布商品仍可交易到底）；`信用分 < 40` → **禁止下单**（已有成交记录不受影响） |
| **信用记录** | 信用分的一次变动流水，含变动值、原因、时间、关联订单编号。**每次变动必须留一条**，不可直接改分数 |
| **评价** | 成交后，买方与卖方可对对方作出的文字评价。**双向**、每方每单 1 次、**不可修改**、**只有文字不设星级** |
| **评价资格** | 为该笔成交的买方或卖方，且距成交不超过 7 天，且尚未评价过该订单（BR-08） |

## 六、治理

| 术语 | 定义 |
|---|---|
| **举报** | 已认证学生对**商品**发起的违规申告。举报对象**仅限商品**；不得举报本人商品 |
| **举报类型** | 封闭五值：违禁品、虚假描述、价格欺诈、联系方式引流、其他 |
| **审核** | 管理员对 `待审核` 商品做上架前准入判断，结论：通过 / 不通过 |
| **处置** | 管理员对违规作出的处理，**手段固定为五项**：警告、强制下架、限制发布、封禁账号、扣信用分 |
| **强制下架** | 管理员处置导致的商品下架，与卖家主动下架**执行角色不同**，在转换表中分两行记录（ST-06 / ST-07） |
| **禁售品类** | 不允许在平台发布的商品类别。**清单待补充（BR-04）**，是本版最重要的待补项 |

| 术语 | 定义 |
|---|---|
| **需求** | 系统必须满足的条件或具备的能力 |
| **用例** | 参与者为达成某个目标而与系统进行的一次完整交互 |
| **业务规则** | 限制或指导业务处理的条件，编号 `BR-xx` |
| **状态转换** | 由事件触发的状态变化，编号 `ST-xx`（商品）或 `AT-xx`（认证） |

| **待确认** | 尚未取得确认的候选值或候选规则，**不得写成已确认** |
| **教学模拟** | 由学生扮演业务方或教师所做的确认。**必须注明，不代表真实确认** |
