## BUG-001 双方同意撤销必失败（P0 阻断）

**现象**：任一方发起撤销申请后，另一方审批通过时接口返回 `HTTP 500 / code 5000`。
更严重的是：该笔交易此后**永久卡死在「有效 + 已售出」**，商品无法重新上架，双方也无法重试。

**根因**（静态 + 运行双重证据）：

- `backend/src/main/java/com/campus/trade/service/OrderService.java` 的 `cancel()` 审批分支
  （约第 203–213 行）在 `cancel_judgement = '已免责'` 的同时写入 `judgement_at = NULL`；
- `backend/src/main/resources/db/schema.sql` 第 162–170 行的 `ck_order_cancel` 要求
  「`已免责` / `计违约` 时 `judgement_at IS NOT NULL`」；
- `docs/requirements/SRS.md` §「退货/撤销审批」注释（第 989 行）同样规定该字段「判定完成时必填」。

也就是说：**DDL 与需求一致，代码与二者冲突**。必须改代码，不应放宽 DDL。

**复现步骤**（隔离库，已实测）：

```bash
# 1. 任一方对一笔「有效」且商品为「已售出」的成交提交撤销申请
curl -X POST http://127.0.0.1:8080/api/orders/{orderId}/cancel \
  -H "Authorization: Bearer $BUYER_TOKEN" -H 'Content-Type: application/json' \
  -d '{"reason":"约不上时间"}'
# 预期：200，成交仍为「有效」、商品仍为「已售出」
# 实际：200，符合预期（第一步正常）

# 2. 对方审批通过（同一接口，再次提交）
curl -X POST http://127.0.0.1:8080/api/orders/{orderId}/cancel \
  -H "Authorization: Bearer $SELLER_TOKEN" -H 'Content-Type: application/json' \
  -d '{"reason":"约不上时间"}'
# 预期：200，成交转「已撤销」、商品回到「在售」
# 实际：500 {"code":5000,"message":"系统繁忙，请稍后重试"}
```

**实际输出**（本次取证原文）：

```
① 发起申请 200 成交状态=有效? 有效 商品= 已售出
② 对方审批 500 {"code":5000,"message":"系统繁忙，请稍后重试"}
```

**证据位置**：

| 证据 | 位置 |
|---|---|
| 冲突代码 | `backend/src/main/java/com/campus/trade/service/OrderService.java` 约 L203–L213 |
| 冲突 DDL | `backend/src/main/resources/db/schema.sql` L162–L170（`ck_order_cancel`） |
| 需求依据 | `docs/requirements/SRS.md` L989「审批处理时间…判定完成时必填」 |
| 运行日志 | 服务端日志原文：`Check constraint 'ck_order_cancel' is violated.` / `SQL state [HY000]; error code [3819]` |
| 数据库终态 | `orders` 该行 `status=有效`、`cancel_judgement=NULL`、`cancelled_at=NULL`；`products` 该行仍为「已售出」 |
| 卡死验证 | 再次调用详情接口返回 `canCancel=false`；再次审批返回 `409 撤销申请已提交，须等待对方审批` |

**影响**：

- 撤销功能（UC-31 / BR-21 / ST-10）**完全不可用**；
- 事务整体回滚，不写脏数据，但把订单变成**不可恢复的死状态**（`cancelRequesterId` 已写入、审批永远失败）；
- 商品被永久占用为「已售出」，卖家无法重新上架；
- 答辩演示此流程会当场报 500。

**责任人/建议**：模块实现 Bot（订单模块）。最小修复是把该分支的 `judgement_at` 置为审批时刻，
与 DDL 和需求对齐；**不改 DDL**、不改需求。修复后需回归：双方同意撤销、拒绝撤销、并发重复审批。

**未决项**：修复需产品负责人批准（本次已按要求停止修改）。

## BUG-002 管理员改密接口越权（P0 安全）

**现象**：持有**学生**登录令牌的调用者，只要提供管理员当前口令，就能改掉管理员密码并长期接管管理员账号。

**根因**：

- `SecurityConfig.java` L46 把 `/api/auth/**` 整体 `permitAll`，`/api/auth/admin/change-password` 也在其中；
- `AuthService.changeAdminPassword()` 直接用 `user.subjectId()` 查 `admins` 表，
  **不校验 `user.isAdmin()`**；
- 学生 id 与管理员 id 来自不同表，数值可重叠（种子数据中管理员 id=1、林同学 id=1）。

**复现步骤**（隔离库，已实测）：

```bash
# 1. 学生正常登录
curl -X POST http://127.0.0.1:8080/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"lin@campus.edu","password":"<学生口令>"}'     # 取 token

# 2. 用学生 token 调用管理员改密，oldPassword 填管理员真实口令
curl -X POST http://127.0.0.1:8080/api/auth/admin/change-password \
  -H "Authorization: Bearer $STUDENT_TOKEN" -H 'Content-Type: application/json' \
  -d '{"oldPassword":"<管理员当前口令>","newPassword":"Hijacked!2026"}'
# 预期：403（仅管理员可执行）
# 实际：200 {"code":0,"message":"密码已修改"}
```

**实际输出**（本次取证原文）：

```
学生身份: kind=student profile.id=1
学生令牌填管理员口令改密 → 200 {"code":0,"message":"密码已修改"}
原管理员口令登录 → 401 {"code":1001,"message":"账号或密码不正确"}
被篡改后的口令登录 → 200（拿到管理员 token）
```

**证据位置**：

| 证据 | 位置 |
|---|---|
| 缺失角色校验 | `backend/src/main/java/com/campus/trade/service/AuthService.java` `changeAdminPassword()`（约 L183–L194） |
| 路由放行 | `backend/src/main/java/com/campus/trade/config/SecurityConfig.java` L46 |
| 正确写法参照 | `PermissionService.currentAdmin()`（已含未登录→401、非管理员→403、账号不存在→401） |

**影响**：

- **权限提升**：任意已注册学生可获得管理员控制权（需知道管理员口令，而演示/初始口令常在文档中出现）；
- 改密后原口令立即失效，管理员被锁在门外，属于持久化接管；
- 违反 SRS UC-04 辅事件流 B「使用学生账号登录后台 → 拒绝」与 §5.2 权限面。

**责任人/建议**：模块实现 Bot（认证模块）。最小修复是让 `changeAdminPassword()` 复用
`permissionService.currentAdmin(user)`，**不新增接口、不改路由表**。

**未决项**：需产品负责人批准后再改。

## BUG-003 管理员改密接口匿名调用 500（P1）

**现象**：未登录直接调用 `/api/auth/admin/change-password` 返回 `HTTP 500 / code 5000`，
应为 `401`。

**根因**：路由 `permitAll` 使请求进入控制器；`@CurrentUser` 对游客返回 `null`，
`changeAdminPassword(null, req)` 在 `user.subjectId()` 处触发 `NullPointerException`，
被 `GlobalExceptionHandler` 兜底成 500。属于与 BUG-002 同源的**同一处代码**。

**复现步骤**：

```bash
curl -i -X POST http://127.0.0.1:8080/api/auth/admin/change-password \
  -H 'Content-Type: application/json' \
  -d '{"oldPassword":"x","newPassword":"NewPass!2026abc"}'
# 预期：401 {"code":1001,"message":"请先登录"}
# 实际：500 {"code":5000,"message":"系统繁忙，请稍后重试"}
```

**实际输出**（本次取证原文）：`匿名 -> 500 5000 系统繁忙，请稍后重试`

**证据位置**：

| 证据 | 位置 |
|---|---|
| NPE 触发点 | `AuthService.changeAdminPassword()` 第一行 `user.subjectId()` |
| 游客注入 null | `backend/src/main/java/com/campus/trade/security/CurrentUserArgumentResolver.java` |
| 兜底成 500 | `backend/src/main/java/com/campus/trade/common/GlobalExceptionHandler.java` `handleOther` |

**影响**：错误语义失真（500 掩盖真实原因、污染监控告警）；不泄露数据，但违反 SRS §5.5 对拒绝语义的要求。
与 BUG-002 用同一处修复即可一并解决。

**责任人/建议**：同 BUG-002。

**未决项**：同上。

## BUG-004 前端撤销文案冲突与不可达控件（P1）

**现象**：`frontend/src/views/student/Orders.vue` 仍保留「单方即时撤销 + 7 天判定」的旧交互，
与后端现行「双方审批」语义冲突；且判定入口在后端永远不可达。

**取证**（静态，逐行核对现状文件）：

| 行号 | 内容 | 问题 |
|---|---|---|
| L60 | `撤销单方即时生效，不需要对方同意；对方有 7 天时间判定「已免责」或「计违约」，超时默认计违约（−2）` | 与 BR-21 及后端行为相反 |
| L166 | `ElMessage.success('撤销已生效')` | 首次提交只是「申请」，并未生效，会误导用户 |
| L38 | `<el-button v-if="o.canJudge" ... @click="openJudge(o)">撤销审批</el-button>` | `canJudge` 在后端恒为 `false`（`OrderService` L358），控件不可达 |
| L71–L77 | 「撤销免责判定」弹窗与「同意免责 / 判定违约」按钮 | 依赖 `orderApi.judge`，后端 `judge()` 首行即抛 409（`OrderService` L259） |
| L33 | `o.cancelJudgement === '待判定'` 分支 | 新流程下不会再产生「待判定」，恒不显示 |
| — | 已提交申请但尚未审批时页面无任何「等待对方审批」提示 | 用户无法得知申请是否成功 |

**复现步骤**：

1. 以任一方登录，进入「我的订单」，对一笔可撤销成交点「撤销成交」；
   弹窗提示「单方即时生效」，实际提交后订单仍为「有效」，需对方审批 → **文案与实际不符**。
2. 前端调用 `POST /api/orders/{id}/cancel-judgement`（经「同意免责」按钮）：
   实际返回 `409 {"code":3001,"message":"当前规则要求双方审批撤销，不再支持撤销后的免责/违约判定"}`。
3. 任何情况下 `canJudge` 都是 `false`，故「撤销审批」按钮与判定弹窗**不会出现**（死代码）。

**证据位置**：`frontend/src/views/student/Orders.vue` L33、L38、L60、L71–L77、L166；
后端对应 `OrderService.java` L259（`judge()` 恒抛 409）、L358（`canJudge = false`）、
`Views.OrderVo` 未暴露 `cancelRequestReason`（无法直接渲染「等待审批」原因）。

**影响**：用户对撤销流程理解错误（以为已撤销/可单方撤销）；评审与答辩时页面文案与实测行为矛盾；
死代码增加维护与误改风险。**不涉及业务规则变更**。

**责任人/建议**：前端负责人。最小改法是改文案（改为「提交申请，需对方同意后生效」）、
按 `canCancel` 状态切换「撤销成交 / 同意撤销」、移除不可达的判定弹窗与 `judge` 调用；
**不改后端规则**。若要展示「等待审批」原因，需 VO 增加字段，属**扩大范围**，需另行批准。

**未决项**：是否新增 VO 字段以显示申请原因，待产品裁定。

## BUG-007 冒烟脚本撤销断言与「双方审批」规则不符（P2 测试资产）

**现象**：`tools/smoke.mjs` L187–L212（当前工作区行号 L192–L205）仍断言「撤销即时生效（不需对方同意）」「撤销后判定为待判定」，
并调用 `/cancel-judgement` 期望 `计违约`。

**版本说明**：该段断言在 `origin/main` 与当前工作区**相同**，即上一轮的脚本修复只处理了
「重置令牌」与「演示口令读取」，**未触及撤销断言**。

**取证**（现状代码实际返回）：

| 断言 | 期望 | 实际 |
|---|---|---|
| 「撤销即时生效」 | `status=已撤销` | 首次提交后仍为 `有效`（需对方审批） |
| 「撤销后判定为待判定」 | `cancelJudgement=待判定` | 不再产生该值 |
| `POST /cancel-judgement` | 200 | `409 当前规则要求双方审批撤销，不再支持撤销后的免责/违约判定` |

**影响**：冒烟套件在撤销段必然失败，无法作为回归基线。

**建议**：按 BR-21 重写断言（发起→对方审批→校验 `已撤销/已免责/judgement_at`）。
但注意：**在当前 BUG-001 未修复前，即使改写断言也会失败**。

**未决项**：测试判据变更需产品确认（避免「改测试迁就代码」）。

## BUG-008 SRS 7 天免责判定在后端已不可达（P1 需求一致性）

**现象**：SRS UC-31 辅事件流 F/G 与 BR-14 ④ 仍描述「撤销后 7 天内由对方判定 `已免责`/`计违约`，
超时默认 `计违约` −2」。但后端 `OrderService.judge()` 首行即抛
`409 当前规则要求双方审批撤销，不再支持撤销后的免责/违约判定`，调度任务的自动判定也一并失效。

**取证**：

| 证据 | 位置 |
|---|---|
| 需求原文 | `docs/requirements/SRS.md` L471（辅流 F/G）、L634（BR-14 ④） |
| 后端禁用 | `OrderService.java` L259 |
| 前端残留 | `Orders.vue` L71–L77（BUG-004） |
| 冒烟断言 | `tools/smoke.mjs` L200–L205（BUG-007） |

**影响**：需求与实现出现**方向性不一致**。这不属于「可安全补的配置问题」，
而是需要产品明确取舍：以需求为准恢复判定，或以新规则回写需求（后者必须走需求变更流程）。

**建议**：由产品负责人在两种方案中择一并留痕；在此之前**不改代码、不改需求原文**。

**未决项**：**本项必须由产品裁定**，是本次唯一「需要改变需求或业务行为才能收敛」的项。
