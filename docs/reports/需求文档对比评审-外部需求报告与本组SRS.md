# 需求文档对比评审：外部《软件工程课程需求报告》 vs 本组《SRS V2.1》

> 评审日期：2026-11-24　评审对象：`D:\software-engineering\软件工程课程需求报告(1).pdf`（44 页） vs `docs/requirements/SRS.md`（1815 行）
> 评审方式：两份文档全文通读 + 编号/引用逐条核对 + PDF 关键页渲染抽查（第 8、17、30 页的用例图、领域类图、订单状态机）+ 本组图源资产比对。

## 0 结论摘要

**综合判断：外部 PDF 这份文档更好（综合 4.6 / 5，本组 SRS 4.1 / 5）。**

但它赢的不是"内容更多"——**需求颗粒度、领域规则深度、质量需求可度量性这三项，本组 SRS 明显更强**。PDF 领先的是**交付完成度与自洽性**：

1. **模型是齐的、且与正文一致**：PDF 8 张图（上下文/用例/领域类/2 张泳道/物品状态机/订单状态机/顺序图）全部成型并与表格对得上（已抽查第 8、17、30 页确认可读）；本组 SRS 需交付的 4 张 UML 图**全部标注"待重出/待出"**，正文还得写一句"冲突时以表格为准"。
2. **编号体系闭合、跨章节可追**：PDF 用 `US→FR→UC→BR→ST-B→AC-D→SC/PV` 一条链贯通，且每条 FR 都标了关联用例与规则，7.4 给出追踪摘要表；本组 SRS 的关联靠每条用例末尾的"关联"字段 + 文档外的《需求覆盖矩阵》，**文档内部没有独立的追踪矩阵**。
3. **同一件事只有一个口径**：PDF 全文对"订单、占用、撤销、拒绝"只给一套说法；本组 SRS 在**成交撤销**上正文与 BR-21 打架（11 处），另有多处"数据字典与规则互相否定"（下面 §4.2 列了行号）。

**反超条件很明确**：本组 SRS 只要（a）补齐 3 张确实缺的图、修掉 1 张图的旧编号，（b）清掉 9 处"双方同意撤销"的旧口径，（c）补一张文档内需求追踪表，综合分即可到 4.7 以上，反超 PDF。这两件事都是**改文档、不用改需求**。

> 前提说明：两份文档不是同一份作业的两个版本——PDF 是另一组（张霖、蒋正友、郑思远、潘奕喆）按"课程需求报告"体例写的（8 章：项目概述→用户需求→类分析→规则与权限→行为分析→质量→验收→基线与人机协作），本组 SRS 是按"软件需求规格说明书"体例写的（8 章 + 3 附录），且**本项目主动砍掉了支付与交付链**（SRS §2.1）。因此本评审只比"文档作为需求工程交付物的质量"，不比"功能多少"。

## 4 五个关键差异（展开）

### 4.1 模型交付：8 张成型图 vs 3 张真缺 + 1 张旧编号

PDF 的图不是装饰：图 2-1 用例图里能看到 UC01/UC10 被画成"概览分组"，图 3-1 领域类图带约束图例（"隐藏标记不改变生命周期状态"等 6 条），图 5-4 订单状态机把"已拒绝/已取消/已异常终止"三个终态和 ST-B-S 状态保持单独用图例说明。抽查渲染结果（第 8、17、30 页）确认**图可读、与正文编号一致**。

本组 SRS 的图问题不是"画得不好"，而是**没画完还要靠正文免责**：

- 图 3-1 用例图：旧图含已删的支付/交付/确认收货等 11 个用例，且不含 UC-29/UC-30（SRS 行 217）；
- 图 6-1 概念类图：旧图含"交付方式"、缺私信/收藏/验证码（行 906）；
- 图 7-1 商品状态机：旧图五态含"已预订"，本版四态（行 1241）；
- 图 7-2 学生认证图：SRS 说"待出"（行 1282、1510），但 A 报告资产里已有（见 §3.6 补正）。

**影响**：答辩时"你的用例图呢"是最容易被追问的一问；"以表格为准"这句话在评审眼里等于承认模型交付不合格。

### 4.2 自洽性：一个"撤销"两种说法

SRS 的 BR-21、UC-31、ST-10、§5.2、§5.3 与术语表都写"**单方即时生效、不需要对方同意**"（行 544、642、760、808、1302、1620），但同一份文档另有 **11 处**仍写"双方同意 / 一致同意"：

| 行号 | 原文片段 |
|---|---|
| 377 | "唯一出口是买卖双方同意撤销" |
| 974 | "表达的是「**双方是否一致同意**终止这笔成交」" |
| 1225 | "可经双方同意撤销回到「在售」" |
| 1253 | "`已售出` → `在售`：买卖双方同意撤销成交" |
| 1257 | "经双方同意撤销可回到 `在售`" |
| 1259 | "这条口子只对**双方合意**开放，不对单方开放" |
| 1603 / 1606 | 术语表"可经双方同意撤销""唯一出口是双方同意撤销" |
| 1612 | 术语表"表达双方是否一致同意终止（BR-21）" |
| 1758 / 1783 | 附录 C.2/C.4 "成交撤销（双方同意、回滚商品）" |

行 1259 甚至与行 555（"为什么不用「双方同意」"）**在同一章内直接对立**。这不是设计分歧（BR-21 已明确单方生效），而是**改稿没扫尾**——但需求文档的验收标准是"不同人阅读不产生不同理解"，11 处反例足以让评审判"不自洽"。

更值得警惕的是，**数据字典和 §6.3 里有几处直接否定了正文规则**，这类缺陷会让实现无法收敛：

| 行号 | 缺陷 | 为什么严重 |
|---|---|---|

### 4.3 需求颗粒度：SRS 更深，但"深"也有代价

SRS 的单条需求信息量大约是 PDF 的 2–3 倍：以"下单"为例，PDF 的 UC05（§2.4.2）约 400 字，SRS 的 UC-10 约 700 字且多出"信用分 ≥ 40""重复提交仅第一次有效""写入失败整体回滚"三个可测分支。SRS 还额外给了"为什么必须补这一条""为什么在售编辑必须重审"这类**决策理由**——这在评审时是加分项。

代价是：全文 1815 行里有相当比例是**过程叙事与版本对照**（"与 V1.2.1 的差异""答辩时必须说明"），作为"规格说明书"读起来偏重；PDF 通篇是"规定"，读起来更像标准。**这是体例选择，不是质量高低**。

### 4.4 可验证性：两条不同的路

- PDF 走"**验收标准表**"路线：12 条 AC，每条"前提与操作 → 可判定预期 → 规则依据"，一条 AC 可覆盖多条 FR（如 AC-D-05 覆盖 FR09/15/20/22）。
- SRS 走"**测量协议**"路线：每条 NFR 写清取样、窗口、统计口径、失败样本如何处理（如"计时超限与系统失败不得删除"）。

两者都合格，但适用面不同：**AC 表更适合功能验收，NFR 协议更适合性能/安全验收**。最佳实践是两者都要——这也是本组 SRS 目前最值得补的一块（补一张 AC 表，直接对齐 §3.2 的 24 个用例）。

### 4.5 范围取舍：可建模性 vs 可观测性

PDF 保留了完整订单链（待卖方确认→待交付→待买方确认→已完成/已取消/已拒绝/已异常终止），因此**有状态机可画、有并发可讲、有争议可处置**，模型展示面更宽。本组 SRS 主动砍掉支付与交付，理由是"平台拿不到支付回调、也没有交付确认，任何「已支付/待交付/退款中」都不可观测"（行 125）——这个论证是**正确且更严谨的**，也是 PDF 最容易被质疑的点（"卖方登记交付"本质上仍是不可核验的自述）。

但代价也真实：功能覆盖面窄、状态机只剩 2 套、可讲的行为模型少一半。**这一项不应算谁的错，属于项目定位差异**，本评审按"文档质量"计分，不按"功能多少"计分。

## 6 结论与建议

### 6.1 结论

- **按"能不能直接交、经不经得起评审逐条追问"判，外部 PDF 更好**。它的强项是**成品的完整度**：模型齐、编号闭合、需求能一路追到验收标准，且对"平台观测不到的事实"划了硬边界。
- **按"需求挖得多深、规则写得多可测"判，本组 SRS 更好**。九字段用例、18 类禁售闭集、逐字段数据字典、10 条带测量协议的 NFR，都是 PDF 没有的深度。
- 因此更准确的说法是：**PDF 是更成熟的"交付物"，SRS 是更扎实的"分析成果"**；差距主要来自 SRS 尚未收尾，而不是方法错误。

### 6.3 PDF 可借鉴的 3 个做法

1. **一条流水号贯通到底**：`US→FR→UC→BR→ST-B→AC-D→SC/PV`，每层只引用不重复，改一处能顺着号找到所有受影响位置。

3. **验收标准带"规则依据"列**：一条 AC 后面直接标 BR 编号，评审时能反向验证"每条规则是否都有验收"。

- 补附录术语表（现在只有 13 条，跨章术语靠上下文猜）；
