> 项目：校园二手交易平台（拾光二手）  
> 评价对象：AI辅助生成、整理和修改后的当前代码实现  
> 评价日期：2026-11-25  
> 依据：`第七章-高质量编码.pdf` 的可理解性、可维护性、可靠性、信息安全性、高效性、可移植性要求，以及仓库源代码、静态度量和已有测试记录。

## 1. 评价范围与方法

本次评价区分课程材料中的编码质量要求与项目已有的AI使用记录。课程材料提供评价维度和示例，不能直接证明本项目代码通过；代码结论均以当前仓库文件、脚本输出或测试记录为依据。检查范围包括 `backend/src/main/java`、`backend/src/main/resources`、`frontend/src`、`tools` 和 `docs/test`。

采用以下方法：

1. 阅读后端和前端目录结构、分层约定及关键配置。
2. 执行 `python tools/metrics.py`，统计Java文件规模、包依赖、服务类规模和分层依赖。
3. 对认证、异常处理、开发开关、配置、服务层复杂度和前端接口封装进行抽样检查。
4. 对照已有测试记录。仓库记录后端冒烟72项、浏览器E2E 20项通过，性能抽样最大385 ms、下单37 ms。该记录只能支持已覆盖场景，不替代完整代码审查。

## 3. 分维度评价

### 3.1 可理解性：良好，建议进一步降低大类复杂度

**优点**

- 包名、类名和方法命名总体使用Java驼峰命名，`ProductService`、`OrderService`、`PermissionService`等名称能够表达业务职责。
- 项目通过`dto`、`vo`、`entity`分离请求、对外视图和持久化实体，README明确约定实体不直接暴露给前端。
- `common/ApiResponse`、`PageResult`、`BizException`、`GlobalExceptionHandler`提供了统一的响应和错误处理入口。
- 前端将`api`、`router`、`stores`、`components`和页面视图分开，阅读入口较明确。

**问题与证据**

- `ProductService`达到669行、30个方法，`AuthService`达到364行、18个方法。一个类同时承载多个用例和状态分支，会增加理解成本。
- `service`包对`config.AppProperties`有17次依赖，多个业务类直接读取配置，业务逻辑与配置结构耦合。
- `tools/metrics.py`检测到`util.TimeProvider → mapper.SettingMapper`，时间工具直接依赖持久层，抽象层次不够清晰。

**评价**：4.0/5。命名和目录结构达到课程要求，复杂业务类和跨层依赖仍影响快速理解。

### 3.2 可维护性：良好，需补充自动化质量门禁

**优点**

- 业务规则集中在service层，控制器主要负责参数接收和响应包装，修改一个用例时定位路径较直接。
- 配置集中于`application.yml`，接口封装和状态管理已有统一位置。
- 统一异常、审计、时间提供器和内容过滤器体现了复用意识。
- AI使用报告记录了人工纠正AI误建模、版本漂移和“页面通过不等于后台实现”等情况，说明代码和文档没有完全依赖AI自审。

**问题与证据**

- 当前仓库未见统一的Java格式化、静态检查或覆盖率门禁配置。代码能运行不等于后续修改能持续保持质量。
- 大型service类使变更容易触及多个职责，建议按商品查询、商品审核、商品状态变更等职责拆分，并以测试保护行为。
- 前端页面中存在演示账号默认填充，修改登录流程或发布配置时需要额外检查是否误带入生产环境。

**评价**：3.8/5。

### 3.3 可靠性：良好，测试证据较充分但仍有覆盖边界

**优点**

- DTO使用校验注解，服务层有业务异常，`GlobalExceptionHandler`统一转换错误响应。
- 密码使用`PasswordEncoder`进行哈希，令牌、会话、权限服务分工明确。
- README记录72项后端冒烟和20项浏览器E2E，覆盖认证、商品生命周期、交易、私信、通知、举报和管理端页面。
- 数据库DDL包含约束，服务层使用状态和权限检查，降低非法业务状态写入概率。

**风险与证据**

- `catch (Exception e)`在审计、邮件、种子数据、定时任务等位置出现，若未统一记录错误上下文，可能掩盖部分失败。
- README明确记录“订单没有状态机”是设计取舍。该取舍减少实现复杂度，但交易一致性、并发下单和异常恢复需要依靠数据库约束和测试持续证明。
- 现有性能和冒烟记录是项目记录中的已执行结果，不能推断所有异常分支、并发冲突和重启恢复均已覆盖。

**评价**：4.0/5。

### 3.4 信息安全性：中上，交付前必须收口演示配置

**已有措施**

- 密码通过BCrypt类编码器处理，数据库字段使用`password_hash`，未直接保存用户密码。
- 认证采用不透明令牌和会话表，支持密码重置后会话失效。
- 权限入口集中在`PermissionService`，控制器和服务层均有身份边界。
- DTO/VO白名单设计降低实体字段和隐私信息直接暴露风险。

**高优先级问题**

- `backend/src/main/resources/application.yml`仍含数据库密码`123456`，属于配置密钥硬编码风险，应改为环境变量或部署密钥管理。
- 配置中`app.features.enable-dev-tools: true`，README也说明演示接口默认开启。生产配置必须关闭开发接口，并确认`/api/dev/state`等接口受开关保护。
- 前端`Login.vue`和`AdminLogin.vue`预填演示账号密码，适合课程演示，正式部署前应移除。
- `DataSeeder`包含演示账号和固定初始密码。应仅在开发配置或初始化脚本中启用，并强制管理员首次改密。

**评价**：3.2/5。基础认证设计较完整，配置和演示数据的生产隔离尚未达到交付安全要求。

### 3.5 高效性：良好，已具备基础性能证据

- `tools/bench.mjs`记录列表50并发最大385 ms、下单37 ms，说明主要演示链路达到当前课程验收目标。
- 后端采用分页结果、MyBatis-Plus和独立mapper，具备控制查询规模的基础。
- 仍需关注service内多次数据库访问、消息和通知联动，以及批量场景下的N+1查询。当前静态检查未进行数据库执行计划和真实生产数据量压测。

**评价**：3.8/5。满足当前规模演示，生产规模性能仍需基准数据和查询计划支撑。

### 3.6 可移植性：良好

- 后端使用Java/Spring Boot，前端使用Vue/Vite，技术栈跨平台能力较好。
- 启动脚本按环境变量和常见安装路径查找JDK、Node、MySQL，并使用相对目录定位。
- 主要限制来自MySQL 8、3307端口、Windows批处理脚本编码和本地上传目录。部署到Linux或容器时，需要替换启动脚本、数据库连接和文件存储配置。

**评价**：4.0/5。

## 5. 整改优先级

### P0：提交或部署前完成

1. 将数据库密码、邮件密钥和其他敏感参数移出`application.yml`，改用环境变量或部署密钥。
2. 将`enable-dev-tools`默认设为关闭，验证所有开发接口在关闭后返回受控错误。
3. 移除前端默认账号密码和生产构建中的演示入口。
4. 为下单、商品售出、撤销等跨对象操作补充并发和失败回滚测试。

### P1：下一迭代完成

1. 拆分`ProductService`、`AuthService`和`MessageService`中的高复杂度职责。
2. 将`TimeProvider`与持久化设置解耦，通过配置或端口注入时间偏移能力。
3. 用明确异常类型替代不必要的`catch (Exception)`，并统一记录错误上下文。
4. 增加Java格式检查、静态分析、单元测试覆盖率和前端构建检查作为CI门禁。

### P2：持续改进

1. 为关键查询建立索引和执行计划基线，补充更大数据量的性能测试。
2. 为公共业务术语、状态枚举和错误码建立代码级约束，减少字符串散落。
3. 将部署参数、上传存储和启动脚本整理为环境无关的部署配置。
