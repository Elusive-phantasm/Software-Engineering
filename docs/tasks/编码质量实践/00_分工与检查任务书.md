# 高质量编码评价实践 · 五人分工与检查任务书

> 用途：把课堂实践的四步要求（读懂代码 → 依需求判质量 → 构造验证 → 审查 AI 建议）拆到 5 个人、5 段代码、5 个质量维度，互不重叠、可交叉复核。
> 个人交付：每人一份按模板填写的评价表（`01_个人评价表_模板.md`）。
> 集体交付：组长汇总的《五人评价汇编》+ 一张问题汇总表。

---

## 0 一句话原则

**每人只评一段代码、只认一个需求编号、只下一个三选一的判断，但必须能复现。**
"我觉得这里可能有问题"不算结论；"在 X 条件下执行 Y 会得到 Z，而 BR-xx 要求 W"才算。

---

## 1 实践要求速记（四段模板）

| 段 | 要写什么 | 合格线 |
|---|---|---|
| 1 这段代码如何执行 | 输入 / 关键条件 / 调用顺序 / 会修改的数据 | 能让没看过这段代码的人照着走一遍 |
| 2 依据什么质量要求 | 需求或设计约束的**编号**＋**代码位置** | 编号要能翻到原文；位置要精确到方法+行 |
| 3 我的判断 | 已发现问题 / 暂有风险需核验 / 当前证据支持符合 | 三选一，不许"可能"；理由用"在__条件下，代码会__，因此__" |
| 4 如何验证 | 前置条件 / 输入或操作 / 按需求应得的结果 / 还要检查的数据或副作用 | 别人按第 4 段能跑出同样结果 |

> 判断为"暂有风险需核验"时，必须写清：**缺哪条信息、下一步看哪段代码或哪张表**。这一项不是免责，是诚实。

## 4 五人任务书

> 下面每题都是**核对问题**，不是结论。答完要给出"代码位置 + 需求编号 + 复现方式"。

### 4.1 林初仁｜成交与撤销（`OrderService.java`）

- 主对象：`create()` L49-116、`cancel()` L150-254、`judge()` L258-259
- 依据：BR-06（下单即成交、唯一有效成交）、BR-21（撤销口径）、UC-10 辅流 F/G、ST-10/ST-11
- 核对问题：
  1. 代码里的"撤销"是**单方即时生效**还是**一方发起+另一方审批**？BR-21 写的是哪一种？两者不一致时，谁该改、依据是什么？
  2. `judge()` 现在直接抛异常，为什么？它对应的接口、前端入口、定时任务是否同步下线？
  3. 通知与审计写在 `@Transactional` 里面：如果通知抛异常，成交会不会回滚？BR-15 对"通知失败"是什么要求？
  4. 订单上的 `deliveryDeadline`（L99）在 SRS 的订单实体里有定义吗？谁在写入、谁在消费？
  5. `create()` 里"个人有效订单上限"的检查（L73-79）和后面的条件更新是不是原子的？并发下会怎样？
- 验证建议：两个会话同时点同一商品下单 → 数订单；让通知服务抛异常（本地分支）→ 看订单是否还在；一方发起撤销后换另一个账号"审批" → 看状态变化。
- 产出重点：这一条大概率会落到"**需求与代码不一致**"或"**失败处理会把已成立的结果回滚**"，请明确选一个判断并给证据。

### 4.2 赵俊豪｜发布与审核（`ProductService.java`）

- 主对象：`create()` L53、`update()` L92、`approve()` L387、`reject()` L410、`forceOff()` L442
- 依据：BR-02（在售上限 5 件）、BR-03（发布即待审）、BR-04（禁售清单闭集）、BR-22（编辑重审）
- 核对问题：
  1. "同一学号最多 5 件在售"是怎么数的？只数"在售"，还是把待审核也算进去？并发发布 6 件会怎样？
  2. 在售商品编辑（ST-12：在售→待审核）与买家下单同时发生，代码靠什么保证只有一个赢？
  3. 审核驳回（`reject`）是否强制要求引用 §4.3 的类目编号？不填会怎样？这与 UC-06 主流程第 5 步一致吗？
  4. `forceOff` 与 `ReportService` 的强制下架是两条路径吗？会不会重复扣信用分或重复通知？
  5. 图片 1～9 张、价格 0～50000 的校验放在哪一层？有没有绕过路径（比如 `update` 不走 `create` 的校验）？
- 验证建议：同账号并发发 6 件；在售商品开两个窗口（一个编辑、一个下单）；驳回时不填类目编号；上传 0 张图。
- 产出重点：优先回答"**上限与重审这两条规则在并发下还成立吗**"。

### 4.3 吕锦浩｜账号状态与处置（`PermissionService.java` + `ReportService` + `BanService`）

- 主对象：`PermissionService` L70-104（`assertNotBanned` / `requirePublishRights` / `requireOrderRights` / `requireCertifiedStudent`）、`ReportService.handle` L200-259、`BanService.ban`
- 依据：BR-10（封禁/受限）、BR-18（伪造应封禁）、BR-19（认证状态与账号状态分离）、§5.2 权限矩阵、ST-13
- 核对问题：
  1. 账号状态有"正常/受限/封禁"三值，代码里**哪一处**拦了"受限"？如果只拦了"封禁"，那"限制发布"这个处置手段实际生效吗？
  2. 举报成立时，"扣信用分"是处置手段里的**可选项**还是**必做**？代码怎么做的？与 UC-13 主流程 4a 一致吗？
  3. 封禁是否连带把该卖家名下"在售"和"待审核"商品下架？"已售出"是否被误伤？与 ST-13 对得上吗？
  4. 管理员会不会被当成学生执行操作？封禁会不会顺手改掉认证状态（违反 BR-19）？
  5. `PermissionService` 是否只有一个鉴权入口？有没有 service 绕过它直接查库？
- 验证建议：把某账号置"受限"后调发布/下单接口；举报只勾"警告"看信用分；封禁一个有"在售+待审核+已售出"的卖家，逐件查状态。
- 产出重点：**权限类问题最容易"看起来有、实际没有"**，一定要用接口实测，不要只读代码下结论。

### 4.4 马歆远｜信用分（`CreditService.apply`）

- 主对象：`apply()` L41-80；旁证：`SchedulerService` 的 `noReviewPenalty()` 与 `cancelJudgeTimeout()` 两处调用
- 依据：BR-13（0～150、越界截断、60/40 阈值）、BR-14（四类事件、每次变动一条流水、幂等）
- 核对问题：
  1. 类注释说"读当前值 → 计算 → **条件更新**，禁止丢失更新"，代码里对应的"条件"在哪一行？如果只是 `updateById`，并发两次 +2 会得到 +4 还是 +2？
  2. 同一 `sourceKey` 并发提交两次，唯一索引冲突会冒泡成什么？用户看到的是"已处理"还是 500？
  3. 分数封顶/触底时（如 150 分再 +2），`applied == 0` 还会写信用流水吗？BR-13 要求"截断值写入信用记录"，这条还成立吗？
  4. 扣分与通知在同一事务里，通知失败会不会把扣分回滚？这是想要的副作用吗？
  5. 定时任务给"未评价"和"撤销超时"扣分，用的幂等键是什么？重复跑会重复扣吗？
- 验证建议：JMeter/两个并发请求同时评价加分；同一举报重复提交；把分数改到 149/150 再触发 +2；断开邮件服务观察事务。
- 产出重点：这是五份里**唯一纯数据一致性**的题目，结论要么"已发现问题（丢失更新）"，要么"证据支持符合（若确实有条件更新）"，必须给出那行代码。

### 4.5 过振宇｜私信与前端（`MessageService.java` + 两个 .vue）

## 9 纪律与常见坑

1. **不要先看 AI 结论再找证据**——顺序反了，判断会被带跑；先自己读代码、写结论，再让 AI 挑错。
2. **不要把"设计选择"当"缺陷"**：比如"平台不记录交付"是 SRS 的边界声明，不是 bug；要评的是"代码有没有违背它自己声称的规则"。
3. **不要只评"代码风格"**：命名、缩进不算本次重点；重点在业务规则、权限、副作用、失败处理。
4. **不要改 main**：本次是评价实践，发现问题只记录；要验证改法就开本地分支，且不合并。
5. **不要拿旧图/旧文档当依据**：SRS 的 UML 图仍标注"待重出"（附录 A.1），依据以**正文表格**为准。
6. **数据要重置后再复现**：`POST /api/dev/reset`，否则别人的测试数据会让你的结论不可复现。
