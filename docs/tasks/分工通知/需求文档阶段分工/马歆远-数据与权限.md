### 2.2 类图

画系统里有哪些「东西」，以及它们之间的关系。

```
学生 1 ──发布──> * 商品
```

### 2.5 质量需求

⚠️ **必须带数字**。写「系统要快」「界面要友好」会被判不合格。

| 编号 | 需求 | 指标 |
|---|---|---|
| NFR-01 | 商品列表页加载 | 200 条商品、50 人同时用时，响应时间 ≤ 2 秒 |
| NFR-02 | 下单操作 | 响应时间 ≤ 3 秒 |
| NFR-03 | 同时在线人数 | 支持 ___ 人 |
| NFR-04 | 个人信息保护 | 手机号、宿舍地址，非本人和非管理员不可见 |
| NFR-05 | 支付信息 | 不存储支付密码等敏感信息 |
| NFR-06 | 登录安全 | 同一账号连续失败 5 次，锁定 15 分钟 |
| NFR-07 | 易用性 | 新用户从登录到发布第一件商品，不超过 5 分钟 |
| NFR-08 | 可用性 | ≥ 99%（考试周等高峰期也要可用） |

NFR-03 那个数字你估一个合理的填上，比如「同时在线 500 人」。
如果你想不出依据，问我或者问吕锦浩——他那边有各功能的「发生频率」，可以推算。

## 三、三条要注意的

⚠️ **1. 术语要统一**：你写的「商品」「订单」「学生」这些词，我会在术语表里定死，
你交之前我们对一下，全文用同一个词。

⚠️ **2. 别写数据库细节**：像「建索引」「分表」「用 MySQL」这些是**设计**，不是需求，
不要写进数据字典。数据字典只写「存哪些信息」，不写「怎么存」。

⚠️ **3. 质量需求不要写实现方式**：写「响应时间 ≤ 2 秒」是对的，
写「用 Redis 缓存加速」是错的——那是技术方案。
