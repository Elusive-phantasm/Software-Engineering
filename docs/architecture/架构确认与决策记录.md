### Q-05 信用分截断时信用记录的变动值口径

| 字段 | 填写内容 |
|---|---|
| Q编号/标题 | Q-05 / 149+2 与 1−10 的信用记录记什么 |

### ADR-001 以 Spring Boot + Vue 重写替代 Node 单体

```text
编号/标题：ADR-001 / 以 Spring Boot 3.5 + Vue 3 重写替代 Node 单体
状态：已接受（待补签）
背景：旧实现为 Express + 原生 JS 单体，前端 student.js 近 2000 行、admin.js 单体，无构建与组件边界；
      课程要求体现分层、模块化与可维护性。关联 Q-04、Q-06。
比较：
  A. 继续维护 Node 单体：改动小，但架构问题（单体前端、无类型、无构建）无法在课程周期内解决；
  B. Spring Boot 3.5 + Vue 3 + Element Plus：分层清晰（controller/service/mapper）、前端组件化；
  C. 拆微服务：对本项目规模明显过度，运维与交付成本不可接受，仅列作反例。
决定：采用 B。明确不采用 A 与 C。
理由：后端分层与 SRS 的 UC/BR 一一对应，便于审核与追踪；前端组件化后页面可独立测试；
      团队已有 Java 基础，学习成本可控。
代价：运行环境变重（JDK 17+、MySQL 8、Node 18+）；启动链长；前后端两套语言与两套依赖；

验证：① 从干净环境按 README 启动成功；② tools/smoke.mjs 72 项通过；③ tools/e2e.mjs 20 项通过；
      ④ 新人按 README 30 分钟内跑通。证据位置见 evidence/。
确认：待填（架构负责人/复核人/日期）
重新评估条件：课程要求单文件部署、或考核环境不提供 MySQL/JDK。
替代关系：无（本 ADR 取代旧实现的隐式技术选型，旧实现代码保留在历史仓库，不删）
```

### ADR-002 使用 MySQL 8 并以库内约束表达业务不变量

```text
编号/标题：ADR-002 / 数据库选型与不变量落点
状态：已接受（待补签）
背景：SRS §6.4.1 要求「有效成交记录每商品最多一条」「已下架必须有下架原因」等强约束；
      旧实现用 SQLite，单写者、无 CHECK 生态。关联 Q-05。
比较：
  A. SQLite：部署零成本，但并发写弱、约束表达与课程演示环境不匹配；
  B. MySQL 8：CHECK 约束、生成列 + 唯一索引可模拟部分唯一索引（uk_order_one_valid），
     并能用真实多连接验证并发；
  C. H2 内存库：便于单测，但不适合作为交付数据库。
决定：采用 B，DDL 集中在 db/schema.sql，应用启动自动执行。
理由：把「有效成交唯一」「价格区间」「状态枚举」「信用分 0～150」写进库，而不是只靠 service 判断，
      使越权与半成品数据在数据层就被拒绝。
代价：需要独立 MySQL 实例（本项目用 3307，避开系统 3306）；部署与备份复杂度上升；
      schema.sql 只做 CREATE TABLE IF NOT EXISTS，不含在线迁移方案。
验证：① 重复执行 schema.sql 不报错；② 并发下单后 uk_order_one_valid 生效且仅 1 条有效订单；
      ③ 直接插入非法状态/价格被 CHECK 拒绝。证据见 evidence/db-constraints.txt。
确认：待填
重新评估条件：考核环境无法提供 MySQL；或需要引入在线迁移工具。
替代关系：无
```

### ADR-003 鉴权采用不透明令牌 + 会话表，而非 JWT

```text
编号/标题：ADR-003 / 鉴权方案
状态：已接受（待补签）
背景：NFR-10 ⑥ 要求「密码重置后该账号所有既有会话立即失效」；会话需可审计、可吊销。
比较：
  A. JWT：无状态、易水平扩展，但「立即失效」需要额外黑名单，反而引入第二份状态；
  B. 不透明令牌 + login_session 表：吊销即 UPDATE，天然满足 NFR-10 ⑥；
  C. Cookie 会话：浏览器体验好，但前后端分离 + 演示脚本需要跨域与 CSRF 处理。
决定：采用 B。令牌 64 位随机串，库内存放，请求头 Authorization: Bearer <token>，默认 72 小时过期。
理由：课程项目单实例，会话表开销可忽略；吊销语义简单可验证。
代价：每次请求多一次会话查询；令牌需前端持久化（localStorage），有 XSS 面，需配合前端输出转义。
验证：① 登出后旧令牌 401；② 重置密码后旧令牌 401；③ 过期令牌 401；④ 伪造令牌 401。
确认：待填
重新评估条件：需要多实例水平扩展且会话表成为瓶颈。
替代关系：无
```

### ADR-004 订单不建状态机，只保留两个标记

```text
编号/标题：ADR-004 / 订单模型
状态：已接受（待补签）
背景：SRS §7.1 明确本版订单没有状态机；平台不碰钱、不碰货，无法观测支付与交付。
比较：
  A. 八状态订单机（待支付/已支付/待交付/…）：表达力强，但每个状态都需要平台观测不到的事实；
  B. 两标记：成交状态（有效/已撤销）+ 撤销免责判定（待判定/已免责/计违约）；
  C. 只保留成交记录、不设任何标记：无法表达撤销与判责。
决定：采用 B。明确不采用 A。
理由：只记录平台能确认的事实（是否成交、谁撤销、对方是否认可）；
      「行为不设闸、声誉记账」避免一方失联导致商品锁死。
代价：平台无法证明货已交付、款已支付；撤销不可回滚，救济只能靠判违约 + 举报；
      前端不能用「订单状态」做流程引导，需按两个标记组合展示。
验证：① 订单表无支付/交付字段；② 撤销后商品回在售且判定为待判定；
      ③ 7 天自动计违约且 −2 只发生一次。证据见 evidence/order-cancel.txt。
确认：待填
重新评估条件：平台接入支付或交付确认（超出当前课程边界）。
替代关系：无
```

### ADR-005 禁售判定保持人工，系统只记录类目编号

```text
编号/标题：ADR-005 / 禁售判定方式
状态：已接受（待补签）
背景：§4.3 给出 18 类闭集与 5 条判定口径；判定依赖物品主体的语义（如「仿真枪」与「玩具枪」）。
比较：
  A. 规则引擎/关键词自动判定：可拦截明显词，但误杀与漏判都高（如「二手 iPad」不应被拦）；
  B. 人工判定 + 系统记录类目编号：与 SRS 一致，可追溯，可逐类目验收；
  C. 混合（关键词先筛、人工复核）：成本最高，课程周期内收益有限。
决定：采用 B。管理员必须选择 A1–E2 之一；清单外走 Q-03 的标注方式。
理由：审核责任在人，系统负责留痕与统计；避免自动判定把「教材含印制答案」误判为 D2。
代价：审核人力成本；判定一致性依赖培训；无法做到毫秒级拦截。
验证：① 18 个类目逐条驳回并记录正确编号；② 二手 iPad、含印制答案教材必须通过；
      ③ 无类目编号的驳回被拒绝。证据见 evidence/forbidden-18.txt。
确认：待填
重新评估条件：清单规模扩大到无法人工覆盖，或学校提供违禁词库。
替代关系：无
```

### ADR-006 分三阶段交付

```text
编号/标题：ADR-006 / 阶段划分与顺序
状态：已接受（待补签）
背景：24 个用例存在依赖：没有商品无法下单；没有下单无法评价与撤销；治理依赖商品与用户。
比较：
  A. 按 UC 编号顺序开发：会把「下单」排在「审核」之前，无法演示完整链路；
  B. 按业务链分三段：身份与商品 → 交易与信用 → 治理与沟通；

代价：S1 结束前无法演示交易；阶段间需要回归，测试成本前移。
验证：每阶段按验收单演示主链 + 抽测异常 + 前阶段回归通过。
确认：待填
重新评估条件：课程验收时间提前，需压缩为两阶段（S1 与 S2 合并）。
替代关系：无
```

## 3 关闭标准与复核流程

1. **关闭标准**（四项同时满足）：人已作决定；受影响文档已同步；预期可检验；另一成员已复核。
2. 只回答了问题但未同步文档 → 状态只能标「已决定待同步」。
3. 状态流转：`待确认 → 已决定待同步 → 已关闭`；出现新证据可 `已重新打开`。
4. 每次关闭须在 §4 变更记录留一行，写明 Q 编号、结论、同步的资产与复核人。
5. **AI 不参与签字**：AI 可起草 Q/ADR 与影响分析，但「确认身份」「关闭证据」必须由人填写。
