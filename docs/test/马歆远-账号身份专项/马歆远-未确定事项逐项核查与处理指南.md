# 未确定事项逐项核查与处理指南

本文把 [测试清单](./马歆远-测试用例与安全检查完成清单.md) 与五份专项记录中的“未验证、未覆盖、待确认”项逐一展开。接口说明以本地 Swagger 为准：`http://127.0.0.1:8080/swagger-ui.html`；前端地址见仓库 README（默认 `http://localhost:5173`）。

## 开始前：准备安全的测试环境

1. 只在本机开发环境操作。`POST /api/dev/reset` 会清空业务表并重新灌入演示数据；不要对生产库或存有个人数据的库执行。
2. 浏览器打开 Swagger。测试游客请求时清除 **Authorize**；测试学生/管理员时分别用对应账号登录并填入它自己的 Bearer token。不要把 token 放进 URL，也不要把 token、验证码、真实手机号或证件图写进证据。
3. 一次只跑一个有状态的场景。开始前记下 `/api/dev/state` 的计数；结束后按需重置，并确认 `offsetHours=0`。调度、密码重置、下单等场景可能改变数据或会话。
4. 每次记录：编号、环境、身份、请求方法和路径、去敏后的输入、HTTP 状态、业务 `code`/提示语、前后状态、证据文件名。失败项保留，不要覆盖旧日志。

## A. SC-02 权限矩阵未覆盖部分

### A1. 已认证学生、三态学生和管理员的剩余权限格

1. 用 Swagger 的 API 名称查接口，不要只点前端按钮。权限面对应商品发布/编辑/下架、订单/撤销、收藏、评价、举报、私信、管理员审核/扣分等写接口。
2. 每个操作准备一个合法请求体和一个确定属于他人的对象 ID。依次用游客、`lv`（未提交）、`ma`（待审核）、`guo`（已驳回）、`zhao`（已认证）、管理员令牌请求；不要用管理员 token 代替学生 token。
3. 逐项对照 SRS §5.2：授权者应成功；无权者应为 401/403，业务码非 0；未提交/待审/已驳回三态提示逐字不同。学生编辑/撤销只用本人对象，再换他人对象验证所有权边界。
4. 保存每一格的身份、动作、响应状态、`code`、`message`。某一格未请求就标“未验证”，不可用“同类操作已拒绝”推断它也安全。

**本次已确认的文案缺陷**：BUG-001（游客发布/下单）和 BUG-002（管理员操作）。修复时查看 `PermissionService.currentStudent()` 及相应的操作级权限守卫。不要把一个通用提示全局替换成某一操作的文案；按发布、下单、评价、举报分别返回 SRS 指定文字，并保留其他接口合适的通用登录提示。修复后分别重放游客发布/下单及管理员四类请求，逐字比对。

### A2. SC02-07：单独证明“已售出”状态拦截

之前的自动化请求拿到 `3001`，但实际原因是“不能购买自己发布的商品”，没有测到“已售出”。

1. 复位到演示数据，读取商品列表和订单列表，选一个**已经售出且卖家不是当前买家**的商品。先用管理员/列表响应确认商品状态和 seller ID。
2. 用另一位已认证学生（非卖家）调用 `POST /api/orders`，请求体只带该商品 `productId`。
3. 预期是 409/3001，提示“该商品不可购买”或需求规定的状态提示；不能出现“不能购买自己发布的商品”。
4. 另用该商品卖家自己下单作为对照，记录自购拒绝。两条结果分别保存。

若演示数据没有合适的已售商品，就先用两个不同学生完成一次交易，再以第三方已认证买家尝试下单；结束后复位。不要把“本人商品”和“已售商品”混成一条判据。

### A3. SC02-08：补齐拒绝后的四查

1. 选一个确定会被拒绝的操作，记录拒绝前 `/api/dev/state` 的商品、订单、评价、举报计数；再记录商品/订单状态、被测学生信用分（`/api/me/credit`）。
2. 发起拒绝请求后，用相同查询再查一次。业务计数和对象状态应不变，信用分差应为 0。
3. 用管理员身份读取 `/api/admin/audit`，检查拒绝请求对应的日志正文：不能有明文密码、完整手机号、宿舍、验证码或图片内容。
4. 将前后数值和审计扫描结果写进证据。测试拒绝操作时如果某项操作本来会成功，应立即复位后重跑，不要把成功业务混入比较。

## B. SC-08 身份核验异常未覆盖部分

### B1. SC08-01：未提交与待审核分别拦截

1. 复位后登录 `lv@campus.edu`，记商品/订单数。以 `lv` 调 `POST /api/products` 和 `POST /api/orders`，预期均拒绝，提示“请先上传学生证”，计数不变。
2. 用该学生提交一张合成 PNG 和唯一测试学号：`POST /api/verifications`。读取 `/api/verifications/mine`，确认 `待审核`。
3. 再次发布和下单，预期提示“核验审核中，请等待”；商品/订单数继续不变。
4. 保存两次拒绝和两次计数对比。只有发布或只有下单测过时，另一项仍标未验证。

### B2. SC08-03：反复驳回/重提和上限

1. 先让需求负责人确认计数口径。清单发现 SRS 写“驳回 +1、重提再 +1”，实现/本次结果呈现的是“仅重提 +1”；未确认前不要自行选一个口径并把它写成 BUG 结论。
2. 复位；管理员对 `ma` 的待审申请用非空原因驳回。保存审核前后 `resubmitCount`、`certStatus` 和通知内容。
3. `ma` 重新提交后，再由管理员驳回，循环至系统声称的 3 次上限。每轮都记录“操作前值 → 操作后值”、状态和响应码。
4. 再尝试第 4 次提交，预期拒绝、保持已驳回，并提示联系管理员；确认没有新增申请。
5. 结果对照负责人确认后的 SRS 口径。若最终确认“驳回+1、重提再+1”，修复计数逻辑并复测；若需求改为只在重提时计数，先更新需求基线再改清单判据。

## C. NFR-05 登录锁定：失败项及依赖项

### C1. 先解决 BUG-005，再测 NFR05-04/05

本次第 5 次失败没有建立锁定，因此“15 分钟后能登录”和“锁定期间状态未变”不能据此判通过。

1. 代码排查点：`AuthService.loginStudent()` 在事务中更新失败次数后抛出认证异常；外层事务可能将更新一起回滚。修复方向是让无效密码的失败计数能够提交（例如独立、受控的失败计数事务），同时确保成功登录清零、已锁定的尝试不延长截止时间。
2. 修复后复位，用专用账号在设备 A 输错 4 次；设备 B 错第 5 次。第 5 次必须出现锁定响应，管理员详情能看到计数和 `lockedUntil`。
3. `POST /api/dev/time-shift` 传 `{"hours":0.233333}`（约 14 分钟），另一设备用正确密码登录：预期仍被拒，`lockedUntil` 与之前相同。
4. 再偏移约 1 分钟，到 `t+15m` 用正确密码登录；预期成功且失败计数清零。比较锁定前后 `certStatus`、`creditScore`、`accountStatus` 与商品状态不变。
5. 最后 `POST /api/dev/time-reset`。如果该次又失败，记录真实边界和 BUG，不要只改报告。

### C2. 修复缺陷的代码检查点

登录锁定位置在 `AuthService.countLoginFailure()`；时间偏移只用于服务业务时钟。失败计数应跨设备共享同一账号记录。测试中不得使用常用演示账号长期锁定；每轮使用独立测试账号或复位。

## D. NFR-08 留存期限待确认

这项无法由接口测试者单方面决定。向产品负责人/老师确认并留存书面答案：学生证图片和申请记录保留多久、从什么事件起算、驳回/撤回/毕业后如何删除、备份和审计是否也删除。

拿到决定后：把期限、依据、删除触发条件写入需求或数据管理说明；设计一个过期样本，检查到期后图片文件和数据库引用都不可读；保留去敏证据。**确认之前仍写“范围已覆盖、期限待确认”**，不要写“合规”或“通过”。

## E. 信息安全 SEC 项目

### E1. SEC-02：会话过期和令牌不出现在 URL

1. 登录后打开浏览器开发者工具 → Network，访问一个受保护页面；检查地址栏、请求 URL 和重定向 URL，不得含 token。token 只应经授权头或安全 Cookie 发送；保存去敏后的请求信息。
2. 当前会话有效期配置为 72 小时，`TokenService` 使用真实时钟，`/api/dev/time-shift` 不会让会话过期。为了不等待 72 小时，在**本地测试配置**临时把 `security.session-ttl-hours` 改为 0（或用隔离测试库把该测试会话 `expires_at` 设为过去），重启后登录并立即请求 `/api/me/orders`。
3. 预期过期令牌 401，不能返回 200；检查完恢复配置原值 72 并重启。不得在共享/生产环境改这个参数。

### E2. SEC-06：纵向越权补齐游客与学生矩阵

按以下接口分别使用“无令牌游客”和普通学生（如 `lin`）请求；再用管理员令牌做正向对照：

| 请求 | 游客 | 学生 | 管理员对照 |
|---|---|---|---|
| `GET /api/admin/dashboard` | 401 | 403 | 200 |
| `GET /api/admin/students/{已有学生ID}` | 401 | 403 | 200 |
| `POST /api/admin/verifications/{待审申请ID}/approve` | 401 | 403 | 200（会改变数据，结束后复位） |
| `GET /api/admin/audit` | 401 | 403 | 200 |
| `POST /api/admin/students/{学生ID}/credit` | 401 | 403 | 200（会改信用分，结束后复位） |

若游客返回 200 或学生不是 403，记录响应体并开 BUG。审核/扣分接口会改变状态，只在可复位的本机种子库执行；不能用真实环境试。

### E3. SEC-07：公开评价隐私检查

1. 以游客请求 `/api/students/{id}/profile`，预期 401；以另一学生请求同一主页，预期返回公开信息但不含手机号、宿舍、密码哈希、异常堆栈或 SQL 表名。
2. 打开商品详情和个人主页的“收到的评价”，选一条确实已公开的评价。在 Network 检查 API 响应和页面显示；只搜字段和值，不复制真实个人资料到证据。
3. 测试串可用 `passwordHash|SQLException|Exception:|手机号测试串|宿舍测试串`；记录每个接口是否命中。公开评价未验证前结论仍为“未验证”。

### E4. SEC-10：注入和超长输入

1. 在商品搜索关键词依次输入 `' OR '1'='1` 和 `1; DROP TABLE students;--`（作为**只读搜索字符串**）。检查均无 500、SQL 错误文本或表结构泄露；查询后用 `/api/dev/state` 确认学生表仍存在。不要把这类语句放入任何会执行 SQL 的管理工具。
2. 用资料编辑接口提交 1000 字昵称，预期 422/业务校验错误，不出现 500。
3. 用一个可复位的待审申请测试 1000 字驳回原因；再用本地测试数据提交长举报理由。预期输入校验拒绝且状态未变。记录实测长度边界，不要只记录“很长”。
4. 若应用接受超长文本，检查 DTO 的 `@Size`/校验是否生效，并在服务端校验请求字段；修复后对边界长度和超过边界 1 字各测一次。

### E5. SEC-11：浏览器 XSS 显示

1. 用合成账号通过私信输入无害载荷 `<script>alert('xss')</script>`；也用测试商品标题或描述输入同样文本。禁止用真实用户内容。
2. 重新打开会话、商品列表和详情页，观察是否弹窗；在 DevTools Elements 检查它是否作为文本节点显示，而不是生成 `<script>` 元素。页面无弹窗且只显示字面文本才符合预期。
3. API 原样保存文本本身不等于浏览器安全；如果页面执行了弹窗，修复前端输出编码，避免把不可信内容交给 `v-html`/`innerHTML`。修复后清理测试数据，再用同一载荷复测并保存截图。

### E6. SEC-12：价格/状态篡改

1. 复位本地开发库，选一件由其他学生发布的在售商品，记商品 ID 和服务端价格。用买家 token 在 Swagger 调 `POST /api/orders`，正常请求是 `{"productId":商品ID}`。
2. 再用一个全新的可复位商品做篡改请求，额外加入 `"price":0.01`、`"status":"已成交"` 等客户端字段。检查服务端是拒绝多余字段，或忽略这些字段；订单金额必须来自数据库中的商品价格，状态必须由服务端交易流程改变。
3. 查询订单详情和商品状态核对；若订单价格/状态跟随客户端值，开 BUG。结束后重置演示数据。

## F. 已知 BUG 的修复方向与复测点

| BUG | 怎么查看 | 修复方向 | 修复后必须复测 |
|---|---|---|---|
| BUG-001 游客提示 | `PermissionService.currentStudent()` 和游客写接口响应 | 发布/下单使用 SRS §5.2 指定提示；不要影响其他需登录接口 | 游客 POST 商品、订单，逐字核对提示和 401 |
| BUG-002 管理员提示 | `PermissionService.currentStudent()` 对管理员的通用分支 | 让发布、下单、评价、举报各走操作专用提示 | 管理员四种请求逐一检查 403 与文案 |
| BUG-003 封禁登录提示 | `AuthService.loginStudent()` 的封禁分支 | 将登录提示与已确认的需求文案对齐 | 封禁账号登录 403/1004；密码重置仍不能解封 |
| BUG-004 重提计数 | `VerificationService.reject()` 和重新提交逻辑 | 先由需求负责人决定“驳回+1”是否要求；按确认后的口径统一实现和文档 | 逐次记录驳回/重提后的计数，直到上限及超限拒绝 |
| BUG-005 登录锁定 | `AuthService.loginStudent()` / `countLoginFailure()` 事务边界 | 使失败计数更新在认证失败后仍提交；成功时清零、锁定时不延长 | NFR05-01~05，全时限和跨设备都测 |
| BUG-006 错码次数 | 注册校验调用 `EmailCodeService.verify()` 的事务边界 | 让错误次数达到上限后能持久化，正确码不能绕过已作废记录 | 连续错 5 次，第 6 次即使是真码也失败；重新发码可正常注册 |
| BUG-007 10 分钟边界 | `EmailCodeService.java` 过期判断；当前 `isBefore(now)` 会让恰好相等的时刻通过 | 边界应按左闭右开处理：`now >= expiresAt` 即失效 | +9m59s 成功，+10m00s 失败，+10m01s 失败 |
| BUG-008 管理员旧会话 | `AuthService.changeAdminPassword()` 与 `TokenService.revokeAll()` | 管理员改密成功后撤销该管理员所有旧 session | 改密前 token 调 dashboard 为 401；新密码重新登录成功 |
| BUG-009 开发接口匿名访问 | `DevController.state()`、`mailbox()`；当前它们未调用 `assertEnabled()` | 给所有 dev 路由统一加启用开关/访问控制；生产配置关闭 `app.features.enable-dev-tools` | 本地关闭时所有 `/api/dev/*` 均拒绝；生产 profile 检查状态和邮箱接口不可匿名读取 |

## G. 两项需要别人确认/参与，不能自己判

### G1. 证件图片留存期限

把问题发给项目需求负责人/老师：期限多长、触发点、删除范围（文件/数据库/备份/审计）是什么。收到明确答复后更新需求和测试判据，再测到期删除。未答复前保持“范围已覆盖、期限待确认”。

### G2. RV-01 商品模块交叉验收

约赵俊豪共同准备本地演示数据。按原分工要求，只依据 SRS V2.1 §7.5 黑盒复跑 SC-04、SC-11，不看他的代码或自测记录：驳回（有/无类目编号）→修改重提并比对商品编号→卖家下架后重提→审核通过；然后在售编辑→确认回待审且搜索不可见→尝试下单→管理员重新审核。逐步记真实结果和证据；不一致开 BUG。执行人、时间、对方记录一致性、签字都由实际参与者填写。

### G3. 防账号枚举响应时延建议值

NFR-10 的 20 对请求已观察到均值差 2.23ms，记录“未发现显著差异”；SRS 的“差 ≤100ms”标为建议值、待确认。由需求负责人确认是否升级为硬判据；确认之前不要写“已达标”。若要重测，应同环境交错执行存在/不存在邮箱各 20 次，同时记录均值和 P95，不保存验证码正文。

## H. 复测结束后怎么关闭事项

1. 修复代码后先只复测对应 BUG，不要直接把旧记录改成通过；保留原失败证据，新增带日期/序号的新证据。
2. 逐项对照本指南验收条件。未跑、环境不满足或等需求决定，分别写“未验证 / 阻塞 / 待确认”，不写“无问题”。
3. 把实际 HTTP 状态、业务码、提示、关键前后值和证据路径回填专项表及总清单；状态为已修复的 BUG 还要有“待复测/复测通过”的新证据。
4. 测试结束执行 `/api/dev/time-reset`；如需回到演示数据再执行 `/api/dev/reset`，并确认时间偏移归零。不要对非本地测试库复位。
5. 按分工通知要求保存 AI 生成边界数据/检查清单时的实际提示词与对话截图；截图由你从本次会话实际保存，不要用重制图片冒充记录。
