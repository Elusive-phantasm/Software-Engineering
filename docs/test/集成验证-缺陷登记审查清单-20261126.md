## 3 我独立定位的缺陷候选（登记时逐条对齐）

> 全部为只读定位，级别为建议值。D01–D05、D12 是撤销链路与流程的 P0/P1。

### D01 撤销审批通过必然被库 CHECK 拒绝（建议 P0）

- **证据（已读）**：`service/OrderService.java:208` 写 `cancel_judgement = 已免责`，`:212` 写 `judgement_at = null`；`db/schema.sql` 的 `ck_order_cancel` 要求「`已撤销` 且 `已免责/计违约`」时 `judgement_at IS NOT NULL`。实测 `campus_trade` 的 `information_schema.check_constraints` 中 `ck_order_cancel` 确实包含该分支。
- **静态推断**：UPDATE 触发 CHECK 失败 → `GlobalExceptionHandler.handleIntegrity` 返回 HTTP 422 / `code=2001`「数据不满足约束」→ 事务整体回滚 → **撤销永远不生效**，商品不回到「在售」。
- **集成复现（待执行）**：
  1. 查约束：`select check_clause from information_schema.check_constraints where constraint_schema='<验证库>' and constraint_name='ck_order_cancel';` → 预期含 `judgement_at is not null`。
  2. A 下单 → A 调 `POST /api/orders/{id}/cancel {"reason":"买家不想要了"}` → 预期 200，DB `cancel_requester_id` 非空、`status` 仍 `有效`。
  3. B（对方）再调同一接口 → **预期 422 / 2001**。
  4. 复核：`select id,status,cancel_judgement,judgement_at,cancel_requester_id from orders where id={id};` → 预期仍 `有效`。
- **影响**：核心交易出口不可用；ST-10 / BR-21 / SC-10 无法演示；冒烟该段必挂。
- **关闭条件**：第 3 步改为 200；DB 出现 `status=已撤销`、`cancel_judgement=已免责`、`judgement_at` 非空、`cancel_requester_id IS NULL`；商品 `status=在售`、`off_shelf_reason IS NULL`。反向验证：改前必须复现 422（同一脚本、同一库）。

### D02 前端撤销/判定文案与后端语义相反，并提示「撤销已生效」而实际未生效（建议 P0）

- **证据（已读）**：`frontend/src/views/student/Orders.vue:5`「撤销必须由一方发起、另一方审批同意后生效」；`:60`「撤销单方即时生效，不需要对方同意……超时默认计违约（−2）」；`:73`「撤销必须由双方同意，审批通过后才生效」——同页三套口径。`:164` 提交后一律提示「撤销已生效」。`:71–77` 仍保留判定弹窗（同意免责 / 判定违约），而后端 `canJudge` 恒为 `false`（`OrderService.java:358`）、`judge()` 首行即抛 409（`:259`）。
- **复现（待执行，浏览器）**：学生登录 → 我的订单 → 「撤销成交」→ 弹窗显示「单方即时生效」→ 确认 → 提示「撤销已生效」→ 刷新后订单仍「有效」、无待审批标识。
- **影响**：用户被明确误导（承诺即时生效 + 7 天判责）；判定入口点击必报错；答辩会出现「提示成功但状态没变」。
- **关闭条件**：产物与页面上不再出现「即时生效」「7 天时间判定」「超时默认计违约」；提交后提示与真实状态二分一致；`canJudge=false` 时判定入口不可达。

### D03 撤销申请在界面上不可辨识，审批人不知道「有申请待我处理」（建议 P1）

- **证据（已读）**：`vo/Views.java` 的 `OrderVo`（165 行起）不含 `cancelRequesterId / cancelRequestReason / cancelRequestedAt`；`Orders.vue`（20:19:42 版本）已无「撤销申请待处理」提示与 `awaitingApproval` 计算；前端全目录检索 `cancelRequestReason|cancelRequesterId` **0 命中**。

- **影响**：申请→审批链在界面断裂；审批人被迫重选原因才能提交，与「同意」语义不符。
- **关闭条件**：`GET /api/orders/{id}` 返回申请三元组；页面显示「对方申请撤销 · 原因 · 时间」并把按钮改为「同意撤销」；接口输出与页面截图同时归档。

### D04 没有「拒绝 / 撤回」路径，申请可永久挂起（建议 P1）

- **证据（已读）**：`OrderService.cancel()` 是唯一入口——首发=申请（`:178–195`），同人再调=409（`:196–198`），对方再调=同意（`:199`）。`controller/*.java` 检索无撤销相关 `reject/withdraw`。`SchedulerService.cancelJudgeTimeout` 只扫 `cancel_judgement='待判定'`（`:209–216`），新流程从不写 `待判定` → 超时兜底对该流程空转。
- **影响**：对方无法拒绝，申请人无法撤回；订单长期停在「有效 + 隐性申请」，商品一直「已售出」；申请人看到的 `canCancel=false`（`:353–356`）。
- **关闭条件**：登记文档须明确该能力是「需求缺口」还是「本期不做」；若不做，须给出申请超时回收策略与可观测证据（如 `cancel_requested_at + N 小时` 自动清空，附调度计数）。
