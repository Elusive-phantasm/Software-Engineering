## 五、我要拍板的两个边界问题

这两个问题队友写不了，必须我定，定完要通知赵俊豪：

### 问题 1：付款（UC-07）的边界

如果用第三方支付，**真正收钱的是支付平台**，我们系统只是「选支付方式 + 记录结果」。

要定的：
- 我们系统到底做到哪一步？（生成支付请求 → 跳转 → 接收结果 → 改订单状态？）
- 支付失败了谁负责提示？

### 问题 2：约见面交付（UC-08）算不算一个功能

如果买卖双方是在微信或线下自己约时间地点，**系统什么都不做**，那它就不是软件功能。

两个选择：
- **A**：改成「买卖双方在系统内约定交付时间地点」→ 那才算功能，需要做
- **B**：系统完全不介入 → 从 19 条清单里删掉，只在商品描述里留个备注字段

> 建议选 **A**，因为这个项目叫「校园二手交易与物品流转平台」，
> 交付环节是核心体验。但要在需求里写清楚「双方确认」的流程。

## 六、术语表

把容易理解错的词定死。这份表**马歆远那边要用**，所以早点定。

| 术语 | 定义 |
|---|---|
| 物品流转 | 指捐赠、回收、借用，**不含**买卖交易 |
| 在售 | 商品已发布且未被任何买家预订 |
| 在售上限 | 同一学号可同时处于「在售」状态的商品数量上限 |
| 已预订 | 商品被某个买家下单、订单尚未取消或完成 |
| 自提点 | 校内设置的线下取货地点 |
| 实名认证 | 通过学校统一身份认证核验学号与身份的过程 |
| 信用分 | 反映学生交易行为的分数，具体算法见业务规则 BR-xx |

> 后面想到新的词就往里加。**全文用词要一致**——不能一处叫「商品」一处叫「物品」。
