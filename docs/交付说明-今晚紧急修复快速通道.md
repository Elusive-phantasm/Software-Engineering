# 今晚交付紧急修复快速通道

适用于今晚交付前发现的问题。紧急可以简化审批，但不能跳过问题说明、责任指派、修复验证和结果留痕。

## 1. 问题分级

| 级别 | 判定 | 处理方式 |
|---|---|---|
| 致命/阻塞 | 核心功能无法运行，或演示流程会失败 | 立即联系对应开发，当面说明问题；修复后马上按原步骤验证 |
| 一般 | 不影响主流程的缺陷或界面瑕疵 | 优先记录；能修复则修复并验证，无法修复则列入交付说明的已知问题 |
| 建议/优化 | 不影响本次交付的体验改进或重构建议 | 今晚不处理，登记为后续迭代事项 |

## 2. 最小留痕格式

不要求今晚补齐完整缺陷系统，但必须在共享文档或协作群中记录：

```text
【问题】xxx｜【复现步骤】xxx｜【影响】阻塞/一般｜【指派】@某人｜【状态】待修复/已修复待验证/已验证
```

## 3. 修复与验证

修复完成后，开发或测试人员必须按原复现步骤重新执行一次。记录实际结果，并确认修复没有破坏原本可用的主流程。未完成验证的问题不得标记为“已验证”。

## 4. 交付前已知问题清单

交付时附上尚未修复或尚未完成验证的问题，至少包含问题描述、影响范围、当前状态和后续计划。已知问题应如实说明，不以“已修复”代替未完成的验证。

## 一句话原则

可以跳过正式审批环节，不能跳过“说清楚问题、指定负责人、修复后验证、留下记录”这四个动作。正式缺陷单可在交付后补录。
