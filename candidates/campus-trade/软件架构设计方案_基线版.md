# 软件架构设计方案（基线版）

> **状态**：基线草案 v1.0（2026-11-12），随 ADR-001～006 一同接受后生效。
> **来源**：由《软件架构设计方案_讨论稿》经 Q/ADR 评审收敛而来；未关闭的 Q 不影响本基线，但对应功能条款保持「待确认」。
> **配套**：《架构确认与决策记录》《接口与关键设计说明书》《分阶段实现与测试计划》《基线索引》。
> **声明**：本基线由 AI 依模板起草，**须经架构负责人与交叉审查人签字后方可作为实现依据**。

## 1 架构目标与约束

| 目标 | 架构回应 | 验证手段 |
|---|---|---|
| 把 SRS 的 24 UC / 22 BR 落到可审查的模块 | 后端按 UC 族划分 service，一个文件对应一组 UC | 需求覆盖矩阵逐条映射 |
| 权限与隐私不出后端 | 鉴权单入口 `PermissionService`，出参白名单 `Views` | 越权脚本 + 字段扫描 |
| 业务不变量不靠自觉 | MySQL CHECK / 唯一索引 / 生成列唯一索引 | 并发与约束测试 |
| 需求变更可控 | Q/ADR + 基线索引 + 阶段计划 | 变更记录与复核签字 |

**外部约束**：课程周期、四人团队、考核环境需 JDK 17+ / MySQL 8 / Node 18+；平台不接支付、物流与学校统一身份认证（SRS §2.1）。

## 2 系统上下文

| 角色/系统 | 与本系统的关系 | 接口 |
|---|---|---|
| 学生（浏览器） | 注册登录、发布、交易、私信 | 前端 5173 → 后端 8080 |
| 管理员（浏览器） | 审核、处置、扣分、看板 | 同上 |
| 邮件服务 | 注册与找回密码验证码 | 默认本地开发邮箱（`/api/dev/mailbox`），可切 SMTP |
| MySQL 8 | 唯一持久化存储（17 张表） | JDBC，实例 3307 |
| 定时任务 | 7 天/24 小时类判定 | 应用内调度，可手动触发 `/api/dev/scheduler/run` |

**不做**（SRS §2.2.2）：在线支付、退款、物流、交付确认、捐赠/回收/借用、跨校交易、账号注销、独立申诉流程、音视频/附件/群聊。

## 3 分层与模块

### 3.1 后端（`backend/src/main/java/com/campus/trade`）

| 层/包 | 职责 | 约束 |
|---|---|---|
| `controller` | 参数接收、响应包装 | 不做业务判断 |
| `service` | 用例与规则的唯一落点 | 权限先于业务；写操作加 `@Transactional` |
| `mapper` | MyBatis-Plus 数据访问 | 不写业务分支 |
| `entity` / `dto` / `vo` | 持久化对象 / 入参 / 出参 | entity 不出 controller；出参统一经 `Views` |
| `security` | 令牌解析、`@CurrentUser` | 只识别身份，不做授权 |
| `common` | 统一响应、错误码、全局异常 | 所有异常映射为 `{code,message,data}` |
| `constant` | 状态/原因/事件/类目闭集 | 与 SRS 编号一一对应 |
| `audit` | 敏感操作与拒绝审计 | 不写密码、完整手机号、宿舍、图片内容 |
| `config` / `seed` | 参数、跨域、OpenAPI、演示数据 | 业务参数集中在 `application.yml` |

**依赖方向**：`controller → service → mapper`，`common/security` 被各层使用但**不反向依赖 service**。

### 3.2 前端（`frontend/src`）

| 目录 | 职责 |
|---|---|
| `views/student`、`views/admin` | 页面（登录、首页、详情、发布、订单、私信、审核、看板等） |
| `layouts` | 学生端/管理端骨架 |
| `components` | 商品卡、状态标签等复用组件 |
| `api` | axios 封装与接口定义，统一处理令牌与错误提示 |
| `router` / `stores` | 路由守卫、登录态与红点 |

**约定**：页面不直连接口字符串，统一走 `api/`；错误提示直接展示后端 `message`，不在前端改写文案。

## 4 运行时视图

### 4.1 一次写请求的路径

```text
浏览器 → Vite 代理 /api → TokenAuthenticationFilter（解析 Bearer）
      → controller（校验入参 DTO）→ service（PermissionService 鉴权 → 业务规则 → @Transactional）
      → mapper → MySQL
      → Views 白名单整形 → ApiResponse{code,message,data}
```

### 4.2 定时任务

`SchedulerService` 每轮执行：核验超时提醒（AT-06）、注册 7 天未提交提醒（AT-07）、未评价扣分（BR-14③）、撤销判定超时（BR-21）。任务可手动触发，重复执行不重复扣分（`uk_credit_source` 幂等）。

## 5 关键机制

| 机制 | 做法 | 对应需求 |
|---|---|---|
| 鉴权 | `PermissionService` 统一校验角色、认证状态、账号状态、对象归属 | §5.1～§5.5 |
| 出参白名单 | `Views` 按角色返回字段；他人视图不含手机号/宿舍/真实姓名/学号 | NFR-04、§6.5 |
| 统一错误 | `ErrorCode`：1001/1003/1004/1005/1006/2001/3001/3002/3003/4001/5000 | §5.5 第 3 条 |
| 事务 | 下单、撤销、审核+扣分、封禁+联动下架在单事务内完成 | BR-06/BR-10/BR-14/BR-21 |
| 约束兜底 | `uk_order_one_valid`、`uk_review_order_reviewer`、`uk_report_reporter`、`uk_credit_source`、`uk_cert_pending` | §6.4.1 |
| 时间源 | `TimeProvider` 统一取服务端时间，支持演示偏移 | §4.1.1 |
| 通知 | 业务点触发，7 类消息（含「账号」） | BR-15 |
| 审计 | 拒绝与敏感读取留痕，写入前脱敏 | §5.5 第 5 条 |
| 文件 | `StorageService` 落 `./data/uploads`，学生证目录不对外 | NFR-08 |
| 幂等 | 信用流水按 `source_key` 唯一；撤销/判定条件更新 | BR-14、BR-21 |

## 6 数据架构

- **17 张表**：students、admins、login_sessions、certification_applications、categories、products、product_images、favorites、trade_orders、reviews、reports、credit_records、notifications、chat_messages、email_codes、settings、audit_logs。
- **关键约束**（详见 `docs/数据库设计.md`）：`ck_student_credit`（0～150）、`ck_product_price`（>0 且 ≤5000000 分）、`ck_product_reason`（已下架 ⇔ 有下架原因）、`uk_order_one_valid`（生成列，仅「有效」订单唯一）、`ck_order_self`、`uk_review_order_reviewer`、`ck_report_type_match`、`uk_credit_source`、`ck_credit_sign`。
- **金额**：整数「分」存储，出参转两位小数字符串。
- **时间**：`LocalDateTime`，`Asia/Shanghai`，序列化为 `yyyy-MM-dd HH:mm:ss`。

## 7 部署视图

| 组件 | 运行方式 | 端口 | 说明 |
|---|---|---|---|
| 前端 | `npm run dev`（或 `dist` 静态托管） | 5173 | 代理 `/api`、`/uploads` 到 8080 |
| 后端 | `java -jar` 或 `mvn spring-boot:run` | 8080 | 启动时执行 `schema.sql`，库空时灌种子数据 |
| 数据库 | MySQL 8 独立实例 | 3307 | 库 `campus_trade`，账号 `campus` |
| 邮件 | local（开发邮箱）或 SMTP | — | `app.mail.transport` 切换 |

**配置**：业务参数集中在 `application.yml`（价格上限、图片 1～9、在售 5 件、收藏 100、信用分阈值、各类期限、验证码频控）；演示工具由 `app.features.enable-dev-tools` 总开关控制。

## 8 质量属性与验证映射

| 质量属性 | 架构手段 | 验证方式 |
|---|---|---|
| 安全（越权/隐私） | 单入口鉴权 + 出参白名单 + 审计 | 越权脚本（未登录/他人/管理员交叉）、字段扫描 |
| 一致性 | 单事务 + 库约束 + 幂等键 | 并发脚本、约束直插测试、重复执行定时任务 |
| 性能 | 索引（状态/分类/卖家）、分页、连接池 20 | autocannon：列表 50 并发、下单时延 |
| 可用性 | 全局异常兜底、统一响应 | 异常注入、月度探针（NFR-07 需长期监测） |
| 可维护性 | 分层、UC 与 service 对照、闭集常量 | 需求覆盖矩阵 + 代码审查 |
| 可测试性 | dev 工具（重置/时间/邮箱/定时）、种子账号 | smoke / e2e / bench 三套脚本 |

## 9 已知限制与风险（须在验收时如实说明）

1. **订单无状态机**：只能证明「有人下单成功」，不能证明货已交付、款已支付（ADR-004）。
2. **撤销不可回滚**：救济仅「判违约 −2 + 举报」，无法追回货物或款项。
3. **禁售判定依赖人工**：系统只记录类目编号，不做语义判断（ADR-005）。
4. **演示工具默认开启**：`enable-dev-tools: true`，且 `GET /api/dev/state` 未受开关保护，会暴露表条数与时间偏移；生产前必须关闭并补鉴权。
5. **管理员初始密码不强制修改**：种子数据 `must_change_password=0`，正式部署应置 1 并加拦截。
6. **单实例假设**：SQLite→MySQL 后仍按单实例设计，未做水平扩展与分布式锁。
7. **未关闭的 Q**：Q-01～Q-06 影响若干判据，相关功能只能判「与实现一致」，不能判「符合需求」。

## 11 变更控制

1. 任何跨模块接口、数据库结构、状态语义的变更，先开 Q 或新 ADR，再改实现。
2. 已接受的 ADR 若被替换，新增 ADR 并在「替代关系」互相引用，旧记录不删。
3. 基线版每次变更递增版本号，并在《基线索引》登记提交标识与复核人。
4. 未关闭的 Q 不得在代码里「先按某方案实现」而不在 Q 记录中体现——否则视为绕过基线。
