# 软件架构设计方案（讨论稿）

> **性质**：讨论稿，**不是基线**。本文只记录候选方案与初步倾向，供 Q/ADR 评审使用；任何实现不得以本文为依据。
> **基线版**：`软件架构设计方案_基线版.md`。**决策记录**：`架构确认与决策记录.md`。
> **日期**：2026-11-12　　**状态**：待评审

## 0 讨论背景

项目已有一版可运行实现（Express + 原生 JS 单体），课程要求补充架构设计与确认过程。团队讨论集中在以下 6 个议题：技术栈是否重写、数据库选型、鉴权方式、订单模型、禁售判定方式、交付阶段划分。每个议题的候选与代价记录如下，最终取舍见对应 ADR。

## 1 议题一：技术栈是否重写（→ ADR-001）

| 候选 | 收益 | 代价 |
|---|---|---|
| A 继续 Node 单体 | 零迁移成本，已有 403 项断言 | 前端两个单体文件（近 2000 行/个）、无构建、无类型、模块边界靠约定 |
| B Spring Boot + Vue 重写 | 分层清晰、前端组件化、与 UC/BR 可一一对应 | 环境变重（JDK/MySQL/Node）、断言重写、工期风险 |
| C 拆微服务 | 理论可扩展 | 对本项目规模明显过度，运维不可接受 |

**初步倾向**：B。**待确认**：重写后的工期是否覆盖 S1～S3（见 ADR-006）。

## 2 议题二：数据库选型（→ ADR-002）

| 候选 | 收益 | 代价 |
|---|---|---|
| A SQLite | 零安装，单文件 | 单写者；CHECK 与「部分唯一索引」表达弱；并发验证说服力不足 |
| B MySQL 8 | CHECK、生成列唯一索引、真实多连接 | 需独立实例；部署与备份成本 |
| C H2 内存 | 测试快 | 不能作为交付数据库 |

**初步倾向**：B。**关键点**：「同一商品最多一条有效成交」必须在库层兜底，不能只靠 service。

## 3 议题三：鉴权方式（→ ADR-003）

| 候选 | 收益 | 代价 |
|---|---|---|
| A JWT | 无状态、易扩展 | 「重置密码后所有会话立即失效」需黑名单，引入第二份状态 |
| B 不透明令牌 + 会话表 | 吊销即失效；可审计 | 每请求一次会话查询；令牌需前端持久化 |
| C Cookie 会话 | 浏览器原生 | 前后端分离需跨域与 CSRF 处理，脚本调用不便 |

**初步倾向**：B。**待确认**：令牌存储位置（localStorage 的 XSS 面）与过期策略（72h 是否合适）。

## 4 议题四：订单模型（→ ADR-004）

| 候选 | 收益 | 代价 |
|---|---|---|
| A 八状态订单机 | 表达力强，流程可视 | 每个状态都依赖平台观测不到的支付/交付事实，写出来就是空条款 |
| B 两个标记（成交状态 + 撤销免责判定） | 只记录可确认事实；不死锁 | 无法证明货已交付；撤销不可回滚 |
| C 只留成交记录 | 最简单 | 无法表达撤销与判责 |

**初步倾向**：B。**待确认**：撤销后的救济路径是否只有「判违约 + 举报」两条（SRS 如此，需业务确认可接受）。

## 5 议题五：禁售判定方式（→ ADR-005）

| 候选 | 收益 | 代价 |
|---|---|---|
| A 关键词/规则自动判定 | 快 | 误杀（二手 iPad）与漏判都高；无法处理语义边界 |
| B 人工判定 + 记录类目编号 | 与 SRS 一致、可逐类目验收 | 人力成本；一致性靠培训 |
| C 混合：机器初筛 + 人工复核 | 理论最优 | 本期成本最高 |

**初步倾向**：B。**待确认**：清单外商品的标注方式（Q-03）。

## 6 议题六：阶段划分（→ ADR-006）

| 候选 | 收益 | 代价 |
|---|---|---|
| A 按 UC 编号顺序 | 编号整齐 | 「下单」会排在「审核」前，无法演示完整链路 |
| B 按业务链三段 | 每阶段可演示、依赖清晰 | 测试前移，阶段间需回归 |
| C 全量后统一测试 | 开发连续 | 与「不要等全部代码完成才测试」的要求冲突 |

**初步倾向**：B：S1 身份与商品 → S2 交易与信用 → S3 治理与沟通。
