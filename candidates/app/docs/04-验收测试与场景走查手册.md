# 验收测试与场景走查手册

> 本文说明**怎么证明系统符合需求 V2.1**：自动化套件怎么跑、每条断言对应哪条需求、
> 以及自动化覆盖不到的部分（界面走查、性能/可用性）应该怎么做。

---

## 1. 怎么跑

```bash
# 终端 A：启动服务（测试需要真实 HTTP 服务）
npm start

# 终端 B：一键跑全部套件
npm test

# 或分套件跑
npm run test:smoke   # 冒烟（9 项）
npm run test:uc      # UC 级回归（238 项）
npm run test:sc      # 场景走查 SC-01～SC-13（127 项）
npm run test:ui      # 前端渲染检查（29 项，jsdom 真实执行 student.js / admin.js）
```

**测试设计原则**

1. **只走公开接口**：接口类测试全部通过 `http://127.0.0.1:3081` 调用，断言"用户能看到的行为"，不断言内部函数返回值，避免"测试与实现一起错"。
2. **每个场景先清库重灌**（`POST /api/dev/reset`），用例之间不互相污染。
3. **断言失败即打印期望值与实际值**，并给出对应的需求条目（如「BR-14 ②」），便于直接对照需求文档。
4. **不依赖第三方测试框架**：`tests/lib/harness.js` 自带 HTTP 客户端（Cookie jar）与断言器。
5. **前端必须被执行**：`test:ui` 用 jsdom 把真实的 `student.js` / `admin.js` 跑起来，断言"页面上真的渲染出了商品卡片/列表/表单"，并捕获任何未处理异常。
   （这条是踩坑后补的：接口全绿但前端渲染层有签名错误时，页面会只剩标题区，接口测试完全发现不了。）

最近一次执行结果：

| 套件 | 断言数 | 结果 |
|---|---|---|
| 冒烟 | 9 | 全部通过 |
| UC 级回归 | 238 | 全部通过 |
| 场景走查 SC-01～SC-13 | 127 | 全部通过 |
| 前端渲染检查（jsdom） | 29 | 全部通过 |
| **合计** | **403** | **全部通过** |

## 2. 场景走查对照（§7.5 SC-01～SC-12 + SC-13）

| 编号 | 需求文档的预期 | 自动化断言要点 |
|---|---|---|
| **SC-01** 正常主流程 | 认证 未提交→待审核→已认证；商品 待审核→在售→已售出；1 条成交；双方各 1 条评价各 +2 | 状态逐步断言；成交记录 `status=有效`；评价后分数 = 原值+2；主页展示评价、不含手机号 |
| **SC-02** 权限 | 未认证发布/下单拒绝；管理员发布/下单/举报拒绝；指定他人学号读手机号拒绝 | 拒绝时**商品总数不变**、商品保持「在售」；主页/信用接口响应中检索不到手机号与宿舍地址 |
| **SC-03** 并发抢购 | 仅一笔成功；商品已售出；仅 1 条成交记录；失败方提示"该商品已售出" | `Promise.all` 同时下单 → 成功 1 / 失败 1；库内该商品订单数 = 1 |
| **SC-04** 审核与重提 | 拒绝→已下架(审核不通过)；重提→待审核→通过；撤回→已下架(卖家撤回)；编号不变 | 驳回原因含类目编号；重提后 `id` 不变；**另测**：审核通过与卖家撤回并发只有一方成功 |
| **SC-05** 违规处置与撤销 | 成立→已下架(管理员违规下架)+−10+信用记录；复核后回在售、下架原因清空、扣分不回滚 | 阈值与状态断言；管理员能在异议会话中读到卖家申诉 |
| **SC-06** 浏览与自助管理 | 搜索只含在售；收藏不锁定、下架后"已失效"；下架→卖家主动下架；通知生成 | 收藏记录保留；收藏者收到「商品审核」类通知；我的商品分组正确 |
| **SC-07** 评价与信用分边界 | 单方评价立即 +2；7 天未评价方 −1；信用 55 发布被拒、35 下单被拒 | 断言每笔只扣一次（幂等）；已发布商品不受影响 |
| **SC-08** 身份核验异常 | 三态发布/下单均被拒且提示不同；驳回重提 +1；超 24h 保持待审核；通过后不影响信用分 | 超时后 `certStatus` 仍为「待审核」；通过后信用分仍 100 |
| **SC-09** 私信与沟通 | 未认证拒绝；首条创建会话 + 私信通知；同一（商品,双方）一条会话；未读数准确；成交后可继续；非成交买家被拒；第三方读 0 条 | 会话未读=1 → 打开即清零；第三方 403；管理员可读异议会话 |
| **SC-10** 撤销与免责判定 | 撤销即时生效、商品回在售；判计违约 −2、已免责不扣；同商品 2 条记录但有效 1 条；7 天自动计违约；已评价撤销被拒；二次撤销被拒 | 幂等：`撤销违约` 记录每单最多 1 条；重复执行定时任务 `cancelAutoJudgements=0` |
| **SC-11** 在售编辑与重审 | 在售→待审核、下架原因清空、发布时间刷新、编号不变、立即消失；已售出不可编辑；系统字段修改被丢弃 | 编辑未通过前下单被拒；重审通过后重新可售；已售出后 PATCH 全部被拒 |
| **SC-12** 封禁联动下架 | 账号封禁；在售与待审核均转已下架(管理员违规下架)；已售出不受影响；认证状态不变；被封卖家发布/下单/编辑被拒 | 逐条断言；`certStatus` 仍为「已认证」（BR-19） |
| **SC-13**（本项目追加）§4.3 十八类 | 每个类目构造一件测试商品，期望全部驳回并记录正确类目编号 | 循环 18 类逐个驳回，断言 `status=已下架`、`offShelfReason=审核不通过`、`reviewNote` 含该类目编号；另测教材与二手 iPad **允许通过** |

## 3. 自动化覆盖不到的部分

### 3.1 界面走查（需人工，建议 15 分钟）

自动化只验证接口契约，**界面仍需人工过一遍**。建议按以下顺序走：

| 步骤 | 期望 |
|---|---|
| 打开 `/` 首页 | 顶部导航、分类胶囊、在售商品卡片（含图片、价格、成色、浏览数）正常渲染，无控制台报错 |
| 点搜索结果里的商品 | 详情页画廊可切换缩略图、价格/成色/状态徽标正确、卖家卡片可点进主页 |
| 未登录点「立即购买」 | 提示"请先登录后再下单"并跳登录页 |
| 用 `lv@campus.edu` 登录后点「立即购买」 | 提示"请先完成学生证核验（BR-01）"并跳核验页 |
| 用 `zhao@campus.edu` 对 `lin` 的在售商品下单 | 弹出确认框 → 成功弹窗显示订单编号 → 商品变「已售出」；可一键「去私信卖家」 |
| 我的 → 我的订单 | 「我买到的」可见该笔；提供「撤销成交」「去评价」入口；显示评价剩余时间 |
| 撤销成交 | 确认后商品回到首页在售列表；订单标「已撤销 / 待判定」 |
| 换 `lin@campus.edu` 登录 → 我的订单 → 判定免责 | 选「计违约」后对方信用分 −2（可在对方信用分页复核） |
| 右下角扳手 → `+7 天` → `执行定时判定` | 提示扣分次数；信用分页出现「未评价扣分 / 撤销违约」流水 |
| 发布闲置 | 不填标题/价格/图片时逐项就地提示；上传 1–9 张图片；提交后进入「我的商品 → 待审核」 |
| 打开 `/admin` → 登录 `ADM-001` | 看板 KPI 正常；侧边栏待审数量与数据一致 |
| 商品审核 → 不通过 | 必须选择 §4.3 类目编号才能提交；卖家收到驳回通知且原因含编号 |
| 学生证审核 → 查看学生证 | 弹窗显示证件图片（仅此处可见）；通过后学生端认证状态变「已认证」 |
| 举报处置 → 核实成立 | 勾选处置手段后商品下架、卖家扣分；学生对象举报时列表不含「强制下架商品」 |
| 学生与账号 → 详情 → 封禁 | 联动下架数量提示；商品列表状态变「已下架（管理员违规下架）」 |
| 侧边栏「处置异议会话」 | 可读卖家申诉并回复；对非违规下架商品不可发起 |

### 3.2 性能与可用性（NFR-01/02/03/06/07）

需求 §8.1 明确了测试前提（受控网络、200 条商品、50 会话、500 在线、可用性按月统计）。
本系统**未执行**这些验收，实施建议：

- **NFR-01/02 响应时间**：用浏览器 Performance 面板或 `curl -w "%{time_total}"` 采样 500 次，看最大值是否 ≤ 2s / 3s（文档要求"每次样本上限"，不是平均值）。
- **NFR-03 容量**：用 500 个测试账号会话压测；本实现的容量瓶颈在 SQLite 单写者，浏览类请求影响很小，下单类并发需实测。
- **NFR-07 可用性**：需要至少一个自然月的监测数据，不能以压测结果代替。
- **NFR-06 易用性**：需邀请 10 名已认证学生受试，本项目**未邀请真实用户**，不得声称已达标。

> 结论口径：**功能类需求（UC/BR/ST/AT 与 NFR-04/05/08/09/10）有自动化证据；性能与易用性类需求只有实现手段与验证方法，没有实测数据。** 这句话要如实写进答辩材料。

## 5. 手工回归清单（改动后自查，10 条）

1. 未登录能浏览商品与详情，点购买/收藏被引导登录。
2. 未认证学生能登录、能收藏、不能发布/下单/私信/评价/举报，提示语各不相同。
3. 发布 → 管理员不通过 → 修改后重提 → 通过 → 在售，商品编号始终不变。
4. 在售商品编辑任意字段 → 立刻从首页消失 → 审核通过后重新出现。
5. 两个会话同时抢同一商品，只有一笔成交。
6. 下单后商品售出，双方都能在该商品的私信里继续沟通；第三方读不到正文。
7. 撤销成交 → 商品回到在售 → 对方判定 → 撤销方 −2（只扣一次）。
8. 管理员封禁卖家 → 其在售与待审商品全部下架，已售出不受影响，认证状态不变。
9. 举报「收款不履约」成立 → 封禁 + 争议数 +1，主页可见。
10. 任何操作被拒绝时，业务数据与信用分都不变（可对照审计日志的 `denied` 记录）。
