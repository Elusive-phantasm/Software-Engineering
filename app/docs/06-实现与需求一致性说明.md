# 实现与需求一致性说明

> 用途：把「实现时遇到的需求内部矛盾」「为落地必须做的工程取舍」「本期没做的部分」一次性讲清楚。
> 答辩时被问"这里为什么和文档不一样"，答案就在本文；**不要临场辩解，直接翻到这里**。

---

## 0. 一句话结论

- **功能类需求（24 用例 / 22 规则 / ST-01～ST-13 / AT-01～AT-08 / NFR-04·05·08·09·10）全部实现，并有自动化证据**（UC 221 项 + SC 126 项断言）。
- **性能与可用性类需求（NFR-01/02/03/06/07）只给了实现手段与验证方法，没有实测数据**，不得声称已达标。
- 与文档存在差异的共 **6 处**（下文 §2），其中 **1 处是文档自身矛盾**（消息类型六值闭集 vs 登录成功通知），其余为工程必然取舍，均已标注。

## 1. 数据结构层面的实现口径

| 口径 | 实现方式 | 为什么这样做 | 是否影响需求验收 |
|---|---|---|---|
| **学生主键** | `students.id`（如 `STU-LIN`）为代理主键；`email`、`student_no` 各自唯一 | 未认证学生**尚无学号**（学号在核验通过后才绑定），无法用学号做主键；而收藏/私信允许未认证学生参与，这些表若引用学号会出现空外键 | 不影响。业务唯一性（邮箱唯一、一学号一账号）由唯一索引保证，且 UC-02 辅事件流 C 的"学号已被占用"校验直接基于 `students.student_no` |
| **金额** | 以「分」存整数（`price_cents`、`amount_cents`），对外转两位小数字符串 | 浮点存钱会出现 `0.1+0.2` 类误差，导致"成交金额 ≠ 标价"（BR-05 要求相等） | 不影响。接口返回的 `price`/`amount` 仍是两位小数字符串 |
| **时间** | ISO-8601 UTC、**秒精度**字符串（`2026-11-05T08:30:00Z`） | 字典序即时间序，可直接排序比较；§4.1.1 要求"精度到秒" | 不影响 |
| **会话令牌** | 随机 48 字节，库内只存 SHA-256；HttpOnly Cookie | 支撑 NFR-10 ⑥"重置后既有会话立即失效"（一次 UPDATE 即可） | 不影响 |
| **「会话」不建表** | 私信按（商品, 对方）聚合，未读数/最后消息由应用层算 | §6.2.1 明确"会话不是实体，不单独建表" | 完全遵循 |
| **举报「证据」** | **未实现证据图片上传** | §6.2.1「举报记录」实体只有 12 个字段，**没有证据字段**；而 UC-12 主事件流第 3 步写"可选上传证据"。二者冲突时以数据字典与「处理结果」留档为准 | **有差异**：UC-12 第 3 步与辅事件流 E（证据无法辨认）在界面上没有对应入口。见 §2.2 |

## 2. 需求内部矛盾及本项目的处理

### 2.1 「消息类型」六值闭集 vs BR-15「登录成功通知」

**矛盾**：§6.2.1「消息通知」的 `消息类型` 是**封闭六值**（核验、商品审核、成交、处置、信用、私信）；
而 BR-15 的通知事件清单里包含**「登录成功」**——六值中没有容纳它的位置。

**处理**：按 BR-15 实现登录成功通知，并把消息类型扩展为**第 7 值 `账号`**；同时提供开关
`config/default.json → features.loginSuccessNotification`，置 `false` 即完全不产生该通知、严格保持六值。

**建议**：V2.2 明确二选一——要么把「登录成功」从 BR-15 删除（登录审计已记录在 `audit_logs`），要么在 §6.2.1 增加 `账号` 类型。

### 2.2 UC-12「可选上传证据」 vs 举报记录无证据字段

**矛盾**：UC-12 主事件流第 3 步"填写说明，可选上传证据（截图、图片或私信记录）"，
辅事件流 E"举报证据无法辨认 → 提示补充材料"；但 §6.2.1 举报记录**没有证据字段**，§6.4 也未见相应约束。

**处理**：**不实现证据上传**，举报仅提交类型 + 文字说明；管理员的核实依据是"私信记录 + 成交记录 + 商品内容"（UC-13 主事件流 2 已要求管理员查看双方记录与私信记录，本项目该路径可用）。

**理由**：凭空加一个实体里没有的字段，会造成"数据字典与实现不一致"，这比缺一个辅助功能更严重；且举报记录一旦存图片，还要与 NFR-08 类同的留存/访问规则，而文档未定。

**建议**：V2.2 要么给举报记录加 `证据图片` 字段并定义可见性，要么从 UC-12 删除该步骤。

### 2.3 BR-14 ③「7 天未评价 −1」与 BR-08「7 天后失去评价资格」

**表面矛盾**：BR-08 说 7 天后未评价方"失去评价资格"，BR-14 ③ 说 7 天未评价"−1 分"。

**处理**：两者并存、互不冲突——**先扣分（达到 168 小时即扣），后禁止提交**。扣分由定时任务在跨过 168 小时的第一个执行周期写入，提交评价的接口同时做 `now >= 成交时间+168h` 的时间校验。
**已撤销的成交记录不适用第 ③ 项**（BR-14 明文排除），本项目在定时任务里只处理 `status='有效'` 的订单。

### 2.4 附录 B「历史订单」引用「已完成」状态

**矛盾**：术语表「历史订单」写"（`已完成`／`已撤销`）"，但 §7.1 明确订单**没有**「已完成」状态。

**处理**：按 §7.1 实现，订单只有 `有效` / `已撤销`；术语表该处措辞视为残留。
**建议**：V2.2 把「历史订单」改为"（`有效` 且已超保留期／`已撤销`）"。

### 2.5 附录 B「学生」定义与「未认证学生」

**矛盾**：v1.2.1 曾把"已通过核验"写进「学生」定义，导致"未认证学生"在逻辑上不成立。术语表 v2.1 已修正为"以学号注册的在校学生"，但同段又说"以**学号注册**"——而 §2.1 与 §6.2.1 定案是**邮箱注册、学号核验时申报**。

**处理**：按 §2.1 / §6.2.1 实现（邮箱为登录账号，学号在核验时申报并绑定），术语表该句按"平台账号"词条理解。
**建议**：V2.2 修正术语表「学生」词条首句。

## 3. 主动取舍（文档未明确、实现时做的决定）

| 决定 | 依据与理由 | 影响 |
|---|---|---|
| **收藏仅允许「在售」商品** | BR-11 说"收藏不锁定商品"，未说可收藏已售出/已下架；若允许收藏已售出商品，客户端拿不到"已失效"的语义起点 | 已收藏商品状态变化后仍显示"已失效"，符合 BR-11；对已售出商品点收藏会被拒 |
| **内容安全过滤=拒绝提交** | BR-04 要求"评价含辱骂、联系方式、广告 → 系统过滤或转管理员删除"。本项目选择**在提交时直接拒绝**并给出原因（更可判、不留脏数据） | 商品描述、评价、站外导流关键词会被拒；**私信内互留电话不受限**（BR-20 明文允许，因为那是履约必需） |
| **「受限」账号状态只由管理员设置** | BR-10/BR-13 要求的是"按信用分阈值限制对应行为"，并未要求自动改账号状态 | 信用分 <60/<40 时**操作被拒**，但 `account_status` 仍是「正常」；管理员可显式设「受限」 |
| **通知保留期 90 天只影响展示** | §6.2.1 保留期是"建议值，待确认"；物理删除会让"消息指向内容已不可用"的告警失效 | 超过 90 天的通知不在列表出现（可查库），不物理删除 |
| **成交记录 3 年归档未实现独立实体** | 文档没有"归档表"设计，且保留期是建议值 | 本期成交记录永久保留、不归档；不影响 UC-16 的视图 |
| **删除商品对管理员也返回「不存在」** | UC-11 辅事件流 G 要求"不得泄露其历史信息" | 管理员只能通过成交记录/举报记录看到历史，不能通过商品接口反查 |
| **撤销原因必须取自固定五项** | UC-31 主事件流第 1 步给了选项列表，`撤销原因` 字段说明"取值来自 UC-31 主事件流第 1 步的选项" | 自由文本会被拒（含"其他"这一项兜底） |
| **卖家回复私信必须指定会话对方；未指定视为「不能与自己对话」** | 「会话」不建表，会话标识是（商品, 对方），服务端无法从商品推断"回复给哪个买家" | 前端会话页始终带上 `toId`；直接构造无 `toId` 的请求按 UC-29 辅事件流 B 拒绝 |
| **评价数 `review_count` 统计"收到的全部评价"** | §6.2.1 字段义为"学生收到的评价数量，由评价实体统计得出"；而 BR-08 只约束**展示**需双方均提交 | 主页的「评价数」可能大于「可见评价条数」，这是文档两处口径叠加的必然结果；建议 V2.2 明确 |
| **种子管理员初始密码不强制修改** | 便于验收与答辩直接登录（`ADM-001 / Admin@12345`） | UC-04 主事件流第 4 步"首登强制修改"在演示数据上被关闭；改密接口已实现，正式交付请把 `must_change_password` 置 1 |
| **演示/测试工具（`/api/dev/*`）** | 需求里的 7 天/24 小时判定与并发场景无法现场自然发生；验收也需要构造前置状态 | 默认开启，生产一键关闭；关闭后这些接口全部 403 |
| **种子商品图用程序生成的 SVG** | 避免引入版权不明的图片；保证离线可用 | 仅影响演示观感，不影响任何规则 |

## 5. 遗留待确认项（与文档附录一致）

以下均为需求文档标注"建议值，待确认"的条目，本项目把它们**全部做成可配置项**（`config/default.json`），确认后改配置即可，无需改代码：

1. 分类目录的具体类别与数量（现为 8 类）。
2. 举报处理时限、商品审核时限（24 小时）、评价时限（7 天）、消息保留（90 天）、收藏上限（100 件）、成交记录保留（3 年）。
3. **撤销免责判定窗口（7 天）与违约扣分（−2）**——这两个值直接决定撤销的成本。
4. 学生手机号、宿舍地址的管理员可见场景与审计范围。
5. 认证申请留存期限与删除规则（NFR-08）。
6. 私信相关阈值：单条长度（500 字）、同一用户对同一商品的每日发送条数是否设限（**本项目未设限**，仅受 500 字与认证约束）、私信记录保留期。
7. 禁售清单 18 类的合法性依据需学校学工/保卫部门或指导教师最终确认（尤其 A1、A3、E1、E2）。
8. 验证码相关的建议值（6 位/10 分钟、60 秒与 24 小时频控、错误 5 次作废、枚举防护响应时差 ≤100ms）。

## 6. 建议的 V2.2 修订清单（按优先级）

1. **§6.2.1 消息类型**：增加 `账号` 类型，或从 BR-15 删除"登录成功"。（否则每条实现都只能二选一地违背某处）
2. **UC-12 证据上传**：给举报记录加 `证据图片` 字段并定义可见性/留存，或删除该步骤与辅事件流 E。
3. **术语表**：修正「学生」词条的"以学号注册"为"以邮箱注册、核验时申报学号"；修正「历史订单」引用的「已完成」状态。
4. **§6.2.1 评价数**：明确 `评价数` 是"收到的全部评价"还是"双方均提交后公开的评价"。
5. **§5.4**：明确管理员查看学生联系方式是否需逐次审计与留存多久。
6. **UC-11 / BR-09**：明确"被管理员违规下架"的商品是否允许卖家删除（本项目按 UC-11 辅事件流 B 禁止）。
