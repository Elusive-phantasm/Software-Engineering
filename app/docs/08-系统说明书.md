# 系统说明书

> 系统名称：**拾光二手 · 校园二手交易平台**
> 依据：《校园二手交易平台 软件需求规格说明书 V2.1》
> 本文面向**使用者与评审**：系统是做什么的、谁能用、怎么用、有哪些规则、边界在哪。
> 技术实现细节见 `01-工程设计说明书.md`；逐条需求对照见 `03-需求追踪矩阵.md`。

---

## 1. 系统概述

一句话：**一个只服务校内学生的二手物品交易系统，负责"撮合 + 成交登记 + 站内沟通 + 违规治理"，不碰钱、不碰货。**

| 维度 | 内容 |
|---|---|
| 系统类型 | 校内 B2C/C2C 撮合平台（Web 应用，学生端 + 管理端） |
| 服务对象 | 本校在读学生（发布/购买）、平台管理员（审核与处置） |
| 核心价值 | ① 让交易可信（学生证核验 + 双向评价 + 信用分 + 举报处置）② 让交易便捷（快速发布、关键词搜索、分类浏览、站内私信）③ 让闲置流转（校内买卖） |
| 交易链 | **发布 → 审核 → 在售 → 下单成交**（四步，之后没有支付、没有交付确认、没有退款） |
| 沟通方式 | **绑定商品的站内私信**，平台不展示、不转交手机号与宿舍地址（含成交对家） |
| 平台边界 | 不涉及资金、不做交付确认、无物流、无物理节点、不接入学校统一身份认证 |

> **最重要的一句话（答辩必说）**：本系统的"成交"只表示**下单成功**，不表示已付款、也不表示货已交付。
> 平台既拿不到支付回调，也没有任何交付观测点，因此不写"已支付 / 待交付 / 待确认 / 退款中"这类无法被验证的状态。

## 2. 目标用户与角色

### 2.1 角色

| 角色 | 定义 | 能做什么 | 不能做什么 |
|---|---|---|---|
| **游客** | 未登录访问者 | 浏览商品列表、搜索、分类、查看"在售"商品详情 | 收藏、发布、下单、私信、评价、举报、看用户主页 |
| **未认证学生** | 已注册但学生证核验未通过（未提交 / 待审核 / 已驳回 三态） | 浏览、搜索、**收藏**、查看本人订单与商品、查看通知、提交核验 | 发布、下单、私信、评价、举报（三态权限相同，仅提示语不同） |
| **已认证学生** | 学生证核验通过 | 上述全部 + 发布、下单、私信、评价、举报、撤销成交、编辑商品 | 审核、处置、删评价（管理员专属） |
| **管理员** | 平台预置账号，不开放注册、不由学生账号升级 | 审核学生证、审核商品、处理举报与违规处置、封禁/限制账号、扣信用分、删除他人评价、回复处置异议私信 | 发布、下单、评价、举报、收藏；**不得读取学生之间的交易会话** |

### 2.2 两个彼此独立的标记（BR-19）

| 标记 | 取值 | 谁能改 | 关系 |
|---|---|---|---|
| **认证状态** | 未提交 / 待审核 / 已认证 / 已驳回 | 学生提交、管理员审核 | 决定能否交易 |
| **账号状态** | 正常 / 受限 / 封禁 | 管理员处置 | 决定能否发布与下单 |

> 关键点：**核验通过不解封，封禁也不撤销认证**。这两个维度互不替代。

## 4. 核心业务流程

### 4.1 注册与核验（取得交易资格）

```
注册（邮箱 + 6 位邮箱验证码 + 昵称/真实姓名/密码）
   → 认证状态 = 未提交  → 账号状态 = 正常  → 信用分 = 100
提交核验（申报学号 + 上传学生证照片）
   → 认证状态 = 待审核
管理员审核（比对"证件姓名 ↔ 账号真实姓名""证件学号 ↔ 申报学号"、图片是否清晰）
   ├─ 通过 → 认证状态 = 已认证，学号写入并全局唯一锁定 → 可发布、下单、私信、评价、举报
   └─ 驳回 → 认证状态 = 已驳回，重提次数 +1（上限 3 次），可修改后重新提交
          └ 若标记「疑似伪造」→ 按 BR-18 封禁账号 + 连带下架其全部在售与待审核商品
```

### 4.2 发布 → 审核 → 在售 → 下单成交（主交易链）

```
卖家发布（标题/分类/价格/成色/描述/1–9 张图）
   → 商品状态 = 待审核（此时其他人看不到）
管理员审核
   ├─ 通过 → 在售（对外展示、可被搜索与下单）
   └─ 不通过 → 已下架（原因 = 审核不通过，须引用 §4.3 禁售类目编号）
            → 卖家修改后可重新提交（沿用原商品编号，需重新审核）
买家点「立即购买」确认
   → 同一动作内：生成成交记录（状态=有效）+ 商品状态 在售 → 已售出
   → 双方收到成交通知，并被引导进入该商品的站内私信约定取货
（此后：无支付、无交付确认、无退款；成交默认就是最终结果）
```

### 4.3 沟通（站内私信）

```
已认证买家在商品详情点「联系卖家」
   → 若商品在售，或商品已售出且本人是该笔成交的买家 → 可发起/进入会话
   → 会话绑定该商品；同一（商品, 双方）只有一条会话，重复进入复用
   → 接收方收到一条「私信」类型站内通知 + 未读数 +1
   → 打开会话即把本人未读全部置为已读
管理员仅在"商品下架原因为管理员违规下架"时，才能在该商品会话中被联系、且只能回复
```

### 4.4 成交撤销与免责判定（"已售出"的唯一出口）

```
任一方在订单详情点「撤销成交」并选择原因
   → 立即生效（不需要对方同意）：成交状态 = 已撤销，商品回到「在售」
   → 撤销免责判定 = 待判定，对方有 7 天时间选择：
       ├─ 同意免责 → 已免责 → 撤销方不扣分
       └─ 计违约  → 计违约 → 撤销方信用分 −2（每笔成交最多一次）
   → 7 天内对方未处理 → 系统自动置「计违约」，撤销方 −2
   （若撤销时卖家账号已封禁：商品不回在售，而转「已下架（撤销后不可交易）」）
```

### 4.5 违规治理

```
学生举报（对象 = 商品 或 学生；类型六选一）→ 举报状态 = 待处理
管理员核实
   ├─ 成立 → 记录处置手段（警告 / 强制下架商品 / 限制发布 / 封禁账号 / 扣信用分，可多选）
   │        · 强制下架 → 商品「已下架（管理员违规下架）」+ 卖家 −10 分
   │        · 封禁账号 → 同一动作内把其在售与待审核商品全部下架（连带处置）
   │        · 对象为学生时：被核实争议数 +1（公开显示在主页）
   │        · 收款不履约成立 → 应同时封禁
   └─ 不成立 → 已驳回，不产生任何处置、不扣分、不公开
被处置卖家可在该商品私信中向管理员提出异议 → 管理员复核 → 可通过（商品恢复在售，扣分不回滚）
```

## 5. 状态与标记一览

| 对象 | 状态 / 标记 | 取值 | 说明 |
|---|---|---|---|
| **商品** | 状态（4 态） | 待审核 / 在售 / 已售出 / 已下架 | 初始恒为「待审核」；「已售出」默认终态，唯一出口是撤销成交 |
| 商品 | 下架原因（5 值） | 审核不通过 / 卖家撤回 / 卖家主动下架 / 管理员违规下架 / 撤销后不可交易 | 只有「已下架」才有该字段 |
| **学生** | 认证状态（4 态） | 未提交 / 待审核 / 已认证 / 已驳回 | 决定交易资格 |
| 学生 | 账号状态（3 态） | 正常 / 受限 / 封禁 | 与认证状态**互相独立** |
| **订单** | **（无状态机）** | 成交状态：有效 / 已撤销；撤销免责判定：待判定 / 已免责 / 计违约 | 不存在"待支付/已支付/待交付/退款中"等状态 |
| **私信** | （无状态机） | 每条消息：未读 / 已读 | 会话不单独建表、无状态、不可关闭、不可撤回 |
| 通知 | 已读状态 | 未读 / 已读 | 通知红点与私信未读**分别统计** |
| 举报 | 处理状态 | 待处理 / 已处理 / 已驳回 | 成立时另外记录「处置手段」与「处理结果」 |

## 6. 关键业务规则摘要

| 编号 | 规则 | 系统的具体表现 |
|---|---|---|
| BR-01 | 已认证且未封禁才可发布/下单；不可自购 | 未认证点购买 → "请先完成学生证核验"；买自己的商品 → "不能购买自己发布的商品" |
| BR-02 | 同一学生最多 5 件"在售" | 第 6 件发布被拒；"待审核/已售出/已下架"不占额度 |
| BR-03 | 发布即待审核，通过才在售 | 新商品只有发布者与管理员可见 |
| BR-04 | 禁售清单 18 类闭集；举报须核实后处置 | 审核驳回**必须**选类目编号（如 A1）；同一个举报只处理一次、只扣一次分 |
| BR-05 | 价格 > 0 且 ≤ 50000 元、最多 2 位小数；下单即以标价成交 | 越界直接拒绝；成交金额 = 下单时标价，平台不议价 |
| BR-06 | 下单即成交，原子且唯一 | 并发抢购只有一笔成功；重复提交返回同一订单 |
| BR-07 | 平台不参与资金与交付 | 界面上没有任何支付、收款、交付、收货入口；成交弹窗明确提示"不记录交付事实" |
| BR-08 | 仅有效成交双方可各评一次，只有文字，7 天内，双方均提交后展示 | 无星级；不可修改；已撤销成交不可评价 |
| BR-09 | 卖家只能下架自己的在售商品；已售出任何角色不可下架；只有"已下架"可删除 | 在售点删除 → "请先下架再删除"；删除后访问 → "该商品已不存在" |
| BR-10 | 封禁后禁止发布与下单，仍可浏览；**封禁须连带下架** | 封禁一个卖家，其在售与待审核商品同一步全部下架；已售出不动作 |
| BR-11 | 只展示在售；收藏不锁定、唯一、上限 100；状态变化不删收藏 | 商品售出/下架后收藏列表标"已失效"，记录仍在 |
| BR-13 | 信用分 100 起、0–150 截断；<60 禁发布、<40 禁下单 | 达到阈值时操作被拒，已发布商品与已有成交不受影响 |
| BR-14 | 四类信用变动：评价 +2 / 违规 −10 / 未评价 −1 / 撤销违约 −2 | 每次变动都有一条可见的信用流水；重复触发不重复扣分 |
| BR-15 | 系统主动通知（核验结果、审核结果、成交、私信、撤销与判定、下架与恢复在售、举报处置、信用变动） | 所有通知都在消息列表里，点击跳转到对应对象 |
| BR-16/17 | 注册 7 天内须提交核验（每日提醒）；核验最多重提 3 次 | 超时只提醒、**不自动通过**；第 4 次重提被拒 |
| BR-18 | 伪造证件必须封禁 | 管理员勾选"疑似伪造"驳回 → 账号封禁 + 商品连带下架 + 认证改回"已驳回" |
| BR-20 | 私信绑定商品、仅已认证可发起、同一（商品,双方）一条会话、管理员仅可回复异议 | 未认证点"联系卖家"被拒；第三方按会话编号读不到正文 |
| BR-21 | 撤销单方即时生效、不可回滚；对方 7 天内判定，超时自动计违约 | 撤销后商品立即回到在售；−2 每笔成交最多一次 |
| BR-22 | 卖家可改内容字段，系统字段不可改；在售编辑必须重审 | 改价后商品立刻从首页消失，重新审核通过才回来（防止"先过审再改成禁售品"） |

## 8. 系统边界：本系统明确**不做**什么

| 不做 | 原因（一句话） |
|---|---|
| 在线支付、代收代付、担保交易、资金池 | 需支付牌照与商户资质；且平台拿不到支付回调，无法观测真实付款 |
| 标记"已付款 / 确认收款" | 平台不碰钱，无权也无能力判定钱是否到账 |
| 交付流程与交付确认（约见面、交付记录、确认收货） | 交付全程线下，平台没有任何观测点 |
| 订单取消 / 退款 / 退款中 | 依赖已付款事实，本系统不存在付款事实 |
| 物流与快递对接 | 交付线下完成 |
| 接入学校统一身份认证 / 学籍库 | 属学校信息化部门管辖的外部系统，需审批与密钥 |
| 捐赠 / 回收 / 借用三条流转路径 | 学校不提供代收点、回收人员与仓库，物理环节不成立 |
| 跨校交易 | 仅限本校学生 |
| 议价 / 竞价 | 下单即以标价成交 |
| 商品推荐算法、广告位 | 非本期目标 |
| 账号自助注销 | 本期不做；账号只能被封禁或限制 |
| 独立申诉流程 | 卖家可在该商品私信中向管理员提异议，管理员人工复核，不设申诉实体与状态 |
| 语音视频、图片/文件消息、群聊、消息撤回 | 站内私信只做纯文本单聊，先把"能联系上、有留痕"做扎实 |
| 通讯录 / 加好友 / 跨商品全局聊天 | 私信必须绑定一件具体商品，不做社交关系链 |

## 9. 非功能特性

| 类别 | 本系统的做法 | 是否有实测数据 |
|---|---|---|
| 隐私（NFR-04） | 手机号、宿舍地址对**任何其他学生（含成交对家）**都不可见；他人信用分只给分数不给明细 | 有：接口响应正文检索断言 |
| 学生证图片（NFR-08） | 仅审核管理员通过专用接口可读；不进列表、通知、导出、审计正文 | 有 |
| 登录安全（NFR-05） | 连续 5 次密码错误锁定 15 分钟；锁定期内正确密码也拒绝；不改变认证/账号/信用状态 | 有 |
| 验证码安全（NFR-10） | 6 位、10 分钟、一次性、只存摘要；60 秒与 24 小时双重频控；错误 5 次作废；找回密码不泄露邮箱是否存在；重置后全部会话失效 | 有 |
| 消息可达（NFR-09） | 私信落库成功才返回成功；未读数按会话实时聚算；打开即置读 | 有 |
| 响应性能（NFR-01/02） | 单请求 3–4 ms（单机无并发）；列表查询走索引 | **无 50 并发压测数据** |
| 容量（NFR-03） | SQLite 单写者，浏览类请求压力小 | **无 500 在线压测数据** |
| 易用性（NFR-06） | 发布为单页表单、必填项就地校验、图片自动压缩 | **无真实受试者测试** |
| 可用性（NFR-07） | 单进程、异常统一兜底 | **无月度监测数据** |

> 口径要求：功能类需求（UC/BR/ST/AT + NFR-04/05/08/09/10）有 347 项自动化断言作证；性能与易用性类需求只有实现手段与验证方法，**不得声称已达标**。

## 12. 已知限制与待确认项

### 12.1 已知限制

1. **单实例部署**：SQLite 单写者 + 本地文件存图，不支持多实例水平扩容。
2. **未做性能与可用性实测**：见 §9 的"无实测数据"部分。
3. **举报证据上传未实现**：需求 UC-12 提到"可选上传证据"，但 §6.2.1 举报记录实体没有证据字段，本项目以数据字典为准未实现（详见 `06-实现与需求一致性说明.md` §2.2）。
4. **移动端未适配测试**：有响应式断点，但未做真机验证。
5. **学生证核验依赖人工**：这是需求规定的做法（不接入学校认证），不是技术缺陷。
6. **演示工具默认开启**（时间推进、测试钩子、开发邮箱）：生产部署须在 `config/default.json` 关闭 `enableDevTools`。

### 12.2 需求侧待确认项（本系统已做成可配置项）

分类目录数量、审核/举报时限、评价时限、消息保留天数、收藏上限、成交记录保留期、撤销免责判定窗口与违约扣分幅度、管理员可查看手机号的场景与审计范围、认证申请留存期限、私信长度与防骚扰阈值、禁售清单的合法性依据。
