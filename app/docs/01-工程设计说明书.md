## 1. 总体架构

```
┌──────────────────────────────────────────────────────────────────┐
│  浏览器                                                          │
│  ├─ 学生端  public/index.html  + assets/student.js（hash 路由）   │
│  └─ 管理端  public/admin.html  + assets/admin.js                 │
│        共用 assets/ui.js（DOM/图标/弹窗）· assets/api.js（HTTP）  │
└───────────────────────────┬──────────────────────────────────────┘
                            │ JSON over HTTP（Cookie 会话）
┌───────────────────────────▼──────────────────────────────────────┐
│  Express 应用（src/app.js）                                       │
│  中间件：express.json → attachActor（解析 Cookie 会话）            │
│  路由层：src/http/routes/*                                        │
│    /api           学生端（auth / product / verification / order / social）
│    /api/admin     管理端（统一 requireAdmin 门禁）                 │
│    /api/dev       演示与测试工具（可关闭）                          │
│  错误处理：errorHandler（业务错误 → 状态码 + 统一 JSON + 审计）     │
└───────────────────────────┬──────────────────────────────────────┘
                            │ 服务调用（同步）
┌───────────────────────────▼──────────────────────────────────────┐
│  领域层（src/domain/*.service.js）                                │
│  guards.js 统一鉴权 → 各 service 执行状态机与业务规则               │
│  view.js 统一出参整形（防内部字段/隐私泄露）                        │
│  scheduler.service.js 时间判定（AT-06/07、−1、自动计违约、超时提醒）│
└───────────────────────────┬──────────────────────────────────────┘
                            │ tx() / get / all / run
┌───────────────────────────▼──────────────────────────────────────┐
│  基础设施（src/core/*）                                           │
│  db.js（node:sqlite，WAL，串行事务）  schema.sql（DDL + 约束）      │
│  crypto.js（scrypt / HMAC / 令牌）  time.js（服务端时间 + 演示偏移）│
│  mailer.js（SMTP + 本地发件箱）  notifier.js（BR-15 通知）          │
│  audit.js（审计）  storage.js（图片落地）  session.js（会话）       │
└──────────────────────────────────────────────────────────────────┘
```

**分层原则**

1. **路由层只做参数传递与响应包装**，不写业务判断——所有规则都在 domain 层，便于逐条对照需求。
2. **鉴权只有一个入口**：`domain/guards.js`。§5.2 权限矩阵的每一行都对应一个守卫函数或 service 内的对象归属判断；隐藏按钮只是辅助，直接构造请求也无法绕过（§5.5 第 1 条）。
3. **出参只有一条通道**：`domain/view.js`。任何响应都经过白名单整形，因此手机号、宿舍地址、真实姓名、密码哈希、内部计数不会因为某个接口疏忽而泄露（NFR-04/NFR-08）。
4. **时间只有一处来源**：`core/time.js` 的 `nowMs()`。业务判定不读客户端时间，也不散落 `Date.now()`。

## 2. 技术选型与约束

| 项 | 选择 | 约束与代价 |
|---|---|---|
| 运行时 | Node.js ≥ 22.5（ESM） | `node:sqlite` 在 22.x 仍标记 experimental（运行输出中有 ExperimentalWarning，`npm start` 已用 `--no-warnings` 屏蔽）；升级 Node 大版本时需回归 |
| 数据库 | SQLite（单文件，WAL） | 单写者模型；课程项目（≤500 并发浏览）足够；不适用于多实例水平扩容 |
| Web 框架 | Express 4 | 唯一直接依赖；无 ORM，SQL 手写（便于把约束写到 DDL 里） |
| 前端 | 原生 ES Module + 手写 CSS | 零构建、零 CDN，断网可演示；代价是没有组件化框架的抽象，页面代码偏"直白" |
| 邮件 | 自研 SMTP 客户端（`net`/`tls`） | 支持 465 隐式 TLS 与 587 STARTTLS，AUTH PLAIN / LOGIN；不支持的服务器需自行扩展 |
| 密码 | scrypt(N=16384,r=8,p=1) + 16 字节随机盐 | 单次哈希约 50–80 ms，登录与注册均同步执行 |
| 会话 | 随机 48 字节令牌，库内只存 SHA-256，HttpOnly Cookie | 无 JWT：撤销会话只需 `UPDATE sessions SET revoked=1`，天然支持 NFR-10 ⑥ |

## 3. 数据模型

### 3.1 表与实体的对应

| 需求文档实体（§6.2.1） | 表 | 关键约束（DDL 里真实存在） |
|---|---|---|
| 学生 | `students` | `email UNIQUE`、`student_no UNIQUE`（可空）、`cert_status`/`account_status` 枚举 CHECK、`credit_score BETWEEN 0 AND 150`、`resubmit_count BETWEEN 0 AND 3` |
| 认证申请 | `certification_applications` | 部分唯一索引 `ux_cert_pending(student_id) WHERE review_status='待审核'`（同时最多一条待审） |
| 商品 | `products` | `price_cents` CHECK、`condition` 四值 CHECK、`status` 四值 CHECK、**`(status='已下架') = (off_shelf_reason IS NOT NULL)`**（§6.4.1 双向一致性） |
| 商品图片 | `product_images` | 主键 `(product_id, seq)`，`seq BETWEEN 1 AND 9` |
| 分类 | `categories` | `name UNIQUE`、`active`（入口可停用） |
| 收藏 | `favorites` | `UNIQUE(student_id, product_id)` |
| 订单（成交记录） | `orders` | `CHECK (buyer_id <> seller_id)`；**`CREATE UNIQUE INDEX ux_orders_one_valid ON orders(product_id) WHERE status='有效'`**；撤销五字段一致性 CHECK（有效时全为空；已撤销时前三者非空、判定与判定时间配套） |
| 评价 | `reviews` | `UNIQUE(order_id, reviewer_id)`、`CHECK (reviewer_id <> target_id)` |
| 举报记录 | `reports` | `UNIQUE(reporter_id, target_type, target_key)`；对象两字段恰好一个非空；举报类型×对象匹配；处理状态与处理人/结果/时间一致性 |
| 信用记录 | `credit_records` | `UNIQUE(event_type, source_key)`（幂等）、`delta <> 0`、符号与事件类型一致 |
| 消息通知 | `notifications` | `msg_type` 枚举 CHECK、`read_status` 两值 |
| 私信 | `messages` | 必绑商品外键、`sender_type/receiver_type`、`read_status` 两值、发送人≠接收人 |
| 管理员 | `admins` | 主键即登录账号、`must_change_password` |
| 邮箱验证码 | `email_codes` | `purpose` 两值 CHECK、`code_hash`（只存摘要）、`fail_count` |
| （会话，需求未列实体） | `sessions` | `token_hash UNIQUE`、`revoked` |
| （审计，§5.5 要求） | `audit_logs` | 无敏感明文（写入前按键名脱敏） |
| （系统设置） | `settings` | 键值，用于持久化演示时间偏移 |

> **代理主键说明**：`students` 用内部 `id`（如 `STU-LIN`）作主键，`email` 与 `student_no` 各自唯一。
> 原因：未认证学生**没有学号**（学号在核验通过后才绑定），无法用学号做主键；
> 而收藏、私信等需求允许未认证学生参与，这些表引用 `students.id` 才不会出现空外键。业务唯一性仍由 `email`/`student_no` 保证。

### 3.2 金额与时间

- **金额一律以「分」存整数**（`price_cents`、`amount_cents`），对外经 `toYuan()` 转两位小数字符串。避免浮点误差导致"成交金额与标价不一致"（BR-05）。
- **时间一律存 ISO-8601 UTC 秒级字符串**（如 `2026-11-05T08:30:00Z`），字典序即时间序，便于直接 `ORDER BY` 与比较；`§4.1.1` 的"秒精度"由 `toISOString().slice(0,19)` 保证。

## 4. 状态机的实现方式

需求只有两套状态机（商品四态、认证四态），**订单与私信没有状态机**。实现上不引入通用状态机引擎，而是：

1. **写路径收敛**：每种转换只在一处实现，并在注释里标出编号。例如

```js
// ST-12：在售编辑 → 待审核（清空下架原因，刷新发布时间，编号不变）
run('UPDATE products SET status=?, off_shelf_reason=NULL, ... WHERE id=?', P.PENDING, id);
```

2. **状态前置校验**：每次转换前显式判断 `if (row.status !== P.PENDING) throw E.state(M.NOT_PENDING)`，即"当前业务状态不支持该操作"（§5.5 第 3 条），与"权限拒绝"区分开。
3. **DTO 层拦截非法写入**：系统字段（发布人、状态、下架原因、发布时间）不在卖家可写白名单内，直接丢弃（UC-32 辅事件流 G）。
4. **数据库 CHECK 兜底**：即便服务层写漏，"已下架必须有下架原因""有效成交记录每商品最多一条"这类结构约束也写进了 DDL。

**未画出、也不应存在的转换**：`待审核 → 已售出`、`已下架 → 已售出`、`已售出 → 待审核`。代码中无对应路径，且 `createOrder` 只接受 `status='在售'`。

## 5. 事务、并发与幂等

### 5.1 事务边界

`core/db.js` 的 `tx(fn)` 使用 `BEGIN IMMEDIATE ... COMMIT/ROLLBACK`，并对嵌套调用复用外层事务。
`node:sqlite` 是**同步 API**，Node 单线程又保证一个请求的临界区不会被其它请求插入，因此"读-判-写"天然不可分割——这正是 §5.5 第 7 条"以服务端先成功者为准"的实现基础。

需要原子的动作（需求点名的）：

| 动作 | 需求出处 | 同一事务内完成的事 |
|---|---|---|
| 下单成交 | BR-06、ST-05 | 条件更新商品「在售→已售出」+ 插入订单 + 双方通知 |
| 撤销成交 | BR-21、ST-10/11 | 订单置已撤销（带状态条件）+ 商品回在售或转已下架 + 双方通知 |
| 免责判定 | BR-14 ④、§6.4.1-5 | 条件更新判定字段 + 信用分 + 信用记录 + 通知 |
| 举报处置 | UC-13、ST-07/13 | 商品下架 + 账号封禁 + 联动下架 + 扣分 + 信用记录 + 举报结论 + 通知 |
| 核验伪造处置 | BR-18、AT-08 | 认证状态改回已驳回 + 封禁 + 联动下架 + 扣分 + 通知 |
| 信用变动 | BR-14 | `UPDATE students SET credit_score = MAX(0, MIN(150, credit_score + ?))` + 插入信用记录 |

### 5.2 三道防重复的护栏

1. **数据库唯一索引**：`ux_orders_one_valid`（同商品最多一条有效成交）、`UNIQUE(order_id, reviewer_id)`（每单每人一次评价）、`UNIQUE(student_id, product_id)`（收藏）、`UNIQUE(reporter_id, target_type, target_key)`（同对象举报一次）、`ux_cert_pending`（同时一条待审申请）。
2. **条件更新**：`UPDATE ... WHERE status='在售'` / `WHERE cancel_judgement='待判定'`，以 `changes === 0` 判定"已被别人抢先"。
3. **幂等键**：信用记录 `UNIQUE(event_type, source_key)`，键形如 `review:<订单>:<学生>`、`noreview:<订单>:<学生>`、`cancel:<订单>`、`violation:report:<举报>`。定时任务重复执行也不会重复扣分。

> 换句话说：**不依赖前端防抖**（§5.5 第 7 条要求）。前端重复点击只会拿到 409 或同一笔订单结果。

### 5.3 并发对照（§5.5 第 7 条）

| 并发对 | 本系统行为 |
|---|---|
| 两人同时下单同一商品 | 后到者 `changes=0` → 提示"该商品已售出"，不产生订单（SC-03 断言） |
| 下单 vs 卖家下架 | 先成功者生效，后到者按状态拒绝 |
| 编辑在售商品 vs 下单 | 下单先成功 → 编辑按"已售出商品不可修改"拒绝；编辑先成功 → 商品已回待审核，下单被拒 |
| 封禁 vs 下单 | 封禁连带下架只作用于在售与待审核；已售出不受影响 |
| 审核通过 vs 卖家撤回 | 条件更新，后到者拿到 409 |
| 两人同时处理同一举报 | 举报状态条件更新，后到者"该举报已被处理"，不重复扣分 |
| 双方同时撤销同一成交 | 订单状态条件更新，后到者提示"该成交已撤销" |
| 人工判定 vs 7 天超时判定 | 都以 `WHERE cancel_judgement='待判定'` 落库，先落库者为准；−2 由 `source_key` 保证只一次 |
| 撤销 vs 对方评价 | 评价先落库 → 撤销被拒（已评价）；撤销先落库 → 评价被拒（已撤销不可评价） |
| 两笔扣分作用于同一学生 | 库内 `credit_score + ?` 原子增减，不会互相覆盖（无"读-改-写"） |

## 6. 安全与隐私设计

| 关注点 | 实现 |
|---|---|
| 密码 | scrypt + 随机盐，`scrypt$N$r$p$salt$hash` 格式；只存哈希；登录/注册响应均不含密码字段 |
| 验证码 | 6 位数字，只存 `HMAC-SHA256(email|用途|验证码)`；比较用 `timingSafeEqual`；10 分钟过期、一次性、错误 5 次作废；按邮箱 60 秒 / 24 小时频控 |
| 防账号枚举 | 找回密码对存在/不存在邮箱返回同一提示；不存在的邮箱不创建验证码记录（因此"验证码无效"与"邮箱不存在"不可区分） |
| 会话 | 48 字节随机令牌，库内只存 SHA-256；HttpOnly + SameSite=Lax；重置密码吊销全部会话 |
| 登录锁定 | 学生按邮箱、管理员按编号分别计数；第 5 次失败写 `locked_until`；锁定期内正确密码也拒绝，且不延长锁定时间 |
| 越权访问 | 每个 service 先 `guards.*` 再校验对象归属；私信另有"会话参与方"校验——指定他人会话编号读不到正文（§5.6） |
| 隐私字段 | 手机号/宿舍地址/真实姓名/学号只在 `view.selfStudent` 与管理员接口出现；他人视图与成交对家视图都没有 |
| 学生证图片 | 落 `data/uploads/cert`（随机文件名）；仅 `GET /api/admin/verifications/:id/image` 下发；不进列表、通知、导出、审计正文 |
| 审计 | `audit_logs` 记录角色/动作/对象/结果/原因类别；写入前对 `password|code|token|phone|dorm|cardImage` 等键名脱敏 |
| 拒绝操作 | 权限拒绝与状态拒绝**不改变任何业务数据、不扣信用分**，只追加审计（§5.5 第 2 条） |

## 7. 时间口径（§4.1.1）

- 所有期限计算集中在 `core/time.js`：`addHours` / `isOverdue`（`now >= deadline`，即**左闭右开**）/ `humanRemaining`。
- 期限常量集中在 `config/default.json` 的 `deadlines`：评价 168h、未评价 −1 168h、核验提交 168h、核验审核 24h、商品审核 24h、举报处理 24h、撤销判定 168h。
- **演示时间偏移**：`time.nowMs()` = 真实时间 + 偏移；偏移持久化在 `settings` 表，重启仍生效，可用 `POST /api/dev/time-reset` 归零。
  用途是让"7 天 / 24 小时"这类判定在答辩现场可被验证（否则只能口述）。
- **会话 TTL 例外**：`session.js` 用真实时钟判断过期。理由是会话有效期属基础设施参数，不是 §4.1.1 的业务期限；若也用偏移，一次"+7 天"演示会把所有人踢下线。

## 9. 前端设计

- **两个单页应用**：学生端 `student.js`（hash 路由，20 个视图）、管理端 `admin.js`（9 个视图），共享 `ui.js`/`api.js`/`app.css`。
- **无构建步骤**：浏览器直接加载 ES Module；`api.js` 统一封装 `fetch`，把 `{ok:false,code,message}` 转成 `ApiError`，视图只需 `handleError(err)` 即可弹出**后端下发的原始提示语**——这样走查时界面文案与需求 §5.2 表格逐字一致。
- **图片上传**：浏览器端用 canvas 压缩（最长边 1200px、JPEG 0.82）后以 data URL 提交，服务端落盘为随机文件名，避免大图拖慢答辩演示。
- **演示工具浮层**（右下角扳手）：查看开发邮箱验证码、时间偏移（+1 小时 / +1 天 / +7 天 / −7 天）、立即执行定时判定、重置演示数据。
- **视觉**：参考墨刀原型的深绿主色（`#165c46`）+ 暖白背景（`#f7f7f3`）+ 圆角卡片，但全部为手写 CSS，不引用任何外部 CDN。

## 10. 关键取舍（答辩可能被问）

| 取舍 | 理由 | 代价 |
|---|---|---|
| 用 SQLite 而非 MySQL | 课程环境零安装；能用 DDL 表达 §6.4.1 的一致性约束 | 单写者，不适合多实例部署 |
| 订单不做状态机 | 平台拿不到支付回调、无交付观测点；写无法观测的状态就是不可实现的空条款（§2.1） | 只能证明"有人下单成功"，不能证明"货已交付"——必须在答辩里主动说明 |
| 撤销单方即时生效 | 若要求对方同意，对方失联就把商品永久锁死（BR-21 设计说明） | 撤销不可回滚，只能靠"判违约 −2 + 举报"约束 |
