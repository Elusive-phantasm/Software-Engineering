# 拾光二手 · 校园二手交易平台

> 依据《校园二手交易平台 软件需求规格说明书 **V2.1**》（`../需求文档/需求规格说明书_V2.1.md`）实现的完整可运行系统。
> 视觉与页面流程参考墨刀原型（`../../原型-可自行修改`），**但所有业务规则、状态流转、权限口径、拒绝提示语一律以 V2.1 正文表格为准**。

---

## 一、这套系统做了什么

| 维度 | 数量 | 说明 |
|---|---|---|
| 用例 | **24 个** | UC-01～UC-18 + UC-29～UC-34（UC-19～UC-28 按文档刻意留空） |
| 业务规则 | **22 条** | BR-01～BR-22，全部在代码中可定位、可验证 |
| 状态转换 | **ST-01～ST-13 + AT-01～AT-08** | 商品四态、认证四态；**订单没有状态机**，只有「有效/已撤销」+「撤销免责判定」两个标记 |
| 非功能需求 | **NFR-01～NFR-10** | 登录锁定、验证码安全、个人信息保护、学生证图片保护、私信可达性等 |
| 实体 | **13 个** | 学生、认证申请、商品、分类、收藏、订单、评价、举报记录、信用记录、消息通知、私信、管理员、邮箱验证码（「会话」不建表） |

**平台边界（§2.1，务必讲清楚）**：完全不涉及资金、不做交付确认、不展示手机号与宿舍地址、不接入学校统一身份认证、无任何物理节点、不介入纠纷的资金与实物处置。
「成交」只表示**下单成功**，不表示已付款或已交货。

## 二、快速开始

```bash
# 1. 环境：Node.js >= 22.5（使用内置 node:sqlite，无需额外数据库）
node -v

# 2. 安装依赖（只有 express 一个直接依赖）
cd app
npm install --cache ./.npm-cache

# 3. 灌入演示数据（分类、账号、商品、订单、评价、举报、私信）
npm run seed

# 4. 启动
npm start

# 可选：配置真实 SMTP 发信（不配则用本地开发邮箱，验证码在页面里就能看）
npm run mail:setup
```

## 三、技术栈与选型说明

| 层 | 选型 | 理由 |
|---|---|---|
| 运行时 | **Node.js 22（ESM）** | 课程环境零配置；`node:sqlite` 为内置驱动，**不需要 MySQL、不需要编译原生模块** |
| Web | **Express 4**（唯一直接依赖） | 常规写法、易读易讲；其余能力全部手写，避免依赖地狱 |
| 数据库 | **SQLite（WAL + 外键 + 部分唯一索引）** | 真 SQL、真事务、真约束；单文件便于交付与答辩演示 |
| 前端 | **原生 ES Module + 手写 CSS**，零构建、零 CDN | 离线可运行；不依赖 Tailwind/Iconify 等外部资源（原型用了 CDN，断网会白屏） |
| 邮件 | 自研 SMTP 客户端（465 隐式 TLS / 587 STARTTLS + AUTH）＋本地开发邮箱 | NFR-10 需要真实可达的验证码通道；本地模式保证无凭据也能完整演示 |

> GitHub 上同类校园二手项目主流是「Vue + Spring Boot + MySQL」，其二是「Node.js + Express（+ uni-app）」。
> 本机仅有 JDK 1.8、无 Maven 与 MySQL，无法编译运行 Spring Boot 3，故选择 Node.js + SQLite 路线，
> 并**用数据库约束与事务把需求里最容易做假的几条（BR-06 原子成交、BR-14 幂等扣分、ST-10 原子撤销）做成硬保证**。

## 六、答辩现场怎么演示「做不出来的那几条」

需求文档里最容易被质疑的三条，本系统都用**服务端时间与可观测事实**做成了当场可验证：

| 要演示的规则 | 操作路径 |
|---|---|
| BR-06 下单即成交（并发只成功一笔） | 两个浏览器分别登录 `zhao@` 与任一已认证账号，同时对同一在售商品点「立即购买」 |
| BR-14 ③「成交 7 天未评价 −1」 | 学生端点右下角**扳手图标** → `+7 天` → `执行定时判定` → 打开「信用分」看流水 |
| BR-21「撤销后 7 天未判定自动计违约」 | 先撤销一笔成交，再 `+7 天` + `执行定时判定`，双方都会收到判定结果通知 |
| BR-16/AT-06「审核超 24 小时不自动通过」 | 提交核验后 `+1 天`，学生仍为「待审核」，管理员收到超时提醒 |
| NFR-05「连续 5 次失败锁 15 分钟」 | 同一账号连续输错 5 次密码，第 6 次即使密码正确也被拒；`+0.26 小时` 后可正常登录 |
| §4.3 十八类禁售清单 | 后台「商品审核」→「查看禁售清单」，驳回时**必须**选择类目编号 |

> 演示工具（时间推进 / 开发邮箱 / 重置数据）默认开启，生产部署时把 `config/default.json` 的
> `server.enableDevTools` 置为 `false` 即可整体关闭。

## 八、与需求文档的口径对齐（摘要）

1. **订单没有状态机**：只有 `成交状态`（有效/已撤销）与 `撤销免责判定`（待判定/已免责/计违约）。不存在「待支付/已支付/待交付/待确认/退款中」等无法观测的状态。
2. **收藏、私信、邮箱验证码**三个实体已落库；**「会话」不建表**，由同一（商品, 双方）的私信行聚合。
3. **学生证图片**只经审核管理员专用接口下发，不进入任何列表、通知、导出与审计正文。
4. **手机号与宿舍地址**即使成交对家也不可见；他人信用分只给分数不给明细。
5. 所有「N 天 / N 小时」判定都是**左闭右开**，以服务端时间为准，位图在 `src/core/time.js`。

详见 `docs/06-实现与需求一致性说明.md`。
